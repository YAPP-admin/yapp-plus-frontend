# 기능 명세: 회원 웹과 iOS 앱의 개발·운영 배포 분리

**이슈**: [#512](https://github.com/YAPP-admin/yapp-plus-frontend/issues/512)
**작성일**: 2026-11-23
**브랜치**: `DongjaJ/expo-ci/cd-plan` — 기능 디렉터리 번호와 독립적으로 유지한다.
**상태**: 1B 외부 증빙 대기. 웹 API 환경 입력 검증은 구현·로컬 검증을 마쳤으며 외부 배포 설정은 아직 변경하지 않았다.
**입력**: 개발 검증과 운영 출시를 분리하고 공통 태그와 영향 판정으로 회원 웹·iOS를 배포한다.

## 사용자 시나리오와 검증

### US1 — 운영에 영향을 주지 않는 회원 웹 검증 (P1)

개발자는 main에 병합한 화면을 고정된 개발 주소에서 확인한다. 회원이 접속하는 운영 화면은
출시할 때까지 유지되어야 한다. 현재 TestFlight도 운영 웹을 열기 때문에 먼저 필요한 분리다.

**독립 검증**: 회원 웹만 바꾸고 개발 배포 후 개발·운영 주소의 배포 식별자를 비교한다.

1. main 검증이 성공하면 영향받은 개발 웹만 갱신되고 운영 주소는 유지된다.
2. 환경별 API 주소를 다르게 설정하면 각 빌드는 지정한 환경으로만 요청한다.
3. 설정만 변경한 뒤 같은 검증 소스를 재배포하면 새 설정이 적용된다.

### US2 — 환경이 섞이지 않는 iOS QA (P1)

테스터는 QA 앱에서 개발 웹·계정·푸시를 확인한다. 운영 앱으로 전환하면 개발 자격 정보가
운영 요청에 사용되지 않아야 한다. 로그인·푸시는 웹과 네이티브가 같은 환경이어야 검증할 수 있다.

**독립 검증**: 환경별 IPA를 같은 기기에 순서대로 설치하고 접속 대상·세션·푸시를 확인한다.

1. QA 앱은 개발 웹과 API, 운영 설정의 앱은 운영 웹과 API에 접속한다.
2. 환경을 구분하지 않던 기존 세션은 재사용하지 않고 재로그인한다.
3. 같은 환경·호환 runtime의 OTA만 적용되고 다른 환경 또는 runtime의 OTA는 적용되지 않는다.
4. QA IPA를 정식 출시 대상으로 사용하지 않고 운영 IPA를 별도 검증한다.

### US3 — 검증한 변경만 선택적으로 출시 (P1)

운영자는 검증된 main 커밋에 공통 릴리스 태그를 붙여 출시한다. 웹과 모바일을 따로 태깅하지
않고 실제 변경이 있는 대상만 배포하여 불필요한 작업과 누락을 줄인다.

**독립 검증**: 배포 명령을 대체한 실행에서 웹만·모바일만·공용 의존성 변경을 구분한다.

1. 정식 태그와 해당 커밋의 main 검증이 확인되면 영향받은 운영 대상만 배포한다.
2. 실패한 이전 배포 뒤 문서만 바뀌어도 아직 반영되지 않은 변경은 다시 선택한다.
3. 태그 번호만 바뀌었다고 앱 표시 버전이나 IPA 빌드를 자동으로 증가·실행하지 않는다.
4. 네이티브 변경에는 앱 버전을 올리고 IPA 생성·제출은 명시적인 수동 작업으로 실행한다.

### US4 — 추적 가능한 재실행과 복구 (P2)

운영자는 무엇이 실제 반영됐는지 확인하고 실패한 대상만 재시도하거나 정상 버전으로 복구한다.
배포 완료 순서가 뒤집혀 이전 변경이 최신 운영 결과를 덮지 않아야 한다.

**독립 검증**: 부분 실패·구버전 재실행·명시적 복구 시나리오에서 대상별 기록을 비교한다.

1. 웹 성공·OTA 실패를 각각 기록하고 성공한 웹의 기준을 잃지 않는다.
2. 오래된 일반 실행은 거절하며 복구는 자동 배포를 중지한 별도 절차로 실행한다.
3. OTA 게시·IPA 생성·업로드·실기기 검증·정식 출시를 서로 다른 상태로 보고한다.

### 경계 사례

- 첫 배포, 기준 기록 조회 오류, 비교 SHA가 이력에 없는 경우를 구분한다.
- 설정 누락·잘못된 URL·Firebase 환경 불일치를 운영 기본값으로 대체하지 않는다.
- 자동·수동 동시 실행, 태그와 실제 SHA 불일치, main 밖 커밋, prerelease를 검증한다.
- 외부 배포 성공 후 결과 기록 실패는 외부 결과 확인 없이 자동 중복 실행하지 않는다.
- 새 runtime의 OTA가 게시되어도 호환 IPA 설치 이전에는 기존 앱에 전달되지 않는다.

## 요구사항

- **FR-001**: 최신 main의 성공 검증은 개발 회원 웹·QA OTA만 자동 갱신해야 한다. (US1, US2)
- **FR-002**: 운영은 main에 포함되고 해당 SHA의 검증이 성공한 정식 릴리스만 허용한다. (US3)
- **FR-003**: 개발 고정 주소는 PR 또는 운영 배포로 갱신되지 않아야 한다. (US1)
- **FR-004**: 웹 환경 설정은 Doppler를 원본으로 관리하고 환경별 배포에 적용한다. (US1)
- **FR-005**: 웹·모바일의 접속·인증·푸시 설정이 대상 환경에 일치해야 한다. (US1, US2)
- **FR-006**: 세션을 환경별로 격리하고 기존 환경 미지정 자격 정보를 재사용하지 않는다. (US2)
- **FR-007**: appVersion과 네이티브 변경 시 버전 증가 검사를 유지한다. (US2, US3)
- **FR-008**: 대상·환경별 마지막 성공 반영 이후의 누적 변경으로 배포 대상을 결정한다. (US3)
- **FR-009**: 최초 배포와 조회 실패를 구분하고 오류를 변경 없음으로 처리하지 않는다. (US3)
- **FR-010**: 자동·수동 실행을 직렬화하고 일반 실행의 구버전 승격을 차단한다. (US4)
- **FR-011**: IPA 빌드·제출은 수동이며 정확한 소스·환경·산출물을 검증한다. (US2, US3)
- **FR-012**: 대상별 결과와 소스를 추적하고 각 전달 단계의 실제 완료 수준을 표시한다. (US4)
- **FR-013**: 자동 배포 중지·정상 배포 복원·검증·명시적 재개의 복구 절차를 제공한다. (US4)
- **FR-014**: 관리자 흐름을 유지하고 기존 설치본과 새 운영 웹의 브리지 호환성을 확인한다. (US1, US4)

### 핵심 개념

환경, 릴리스 후보, 대상별 성공 기록, IPA 출처, 환경별 세션을 구분한다.
상세 계약은 [데이터 모델](data-model.md)과 [배포 계약](contracts/delivery.md)에 정의한다.

## 성공 기준

- **SC-001**: 개발 화면 변경 1건을 배포해도 운영 화면의 배포 식별자가 바뀌지 않는다.
- **SC-002**: 웹만·모바일만·공용 변경의 세 시나리오가 예상한 대상만 선택한다.
- **SC-003**: QA↔운영 설치 전환에서 다른 환경의 저장된 자격 정보 사용이 0건이다.
- **SC-004**: 부분 실패 후 재시도에서 미반영 변경이 누락되지 않고 구버전 일반 재실행은 거절된다.
- **SC-005**: 환경별 로그인·세션 복구·푸시와 호환/비호환 OTA 사례를 실기기 기록으로 확인한다.
- **SC-006**: 웹·OTA·IPA 각각의 정상 결과와 복구 대상을 소스 및 배포 식별자로 추적할 수 있다.

## 전제와 범위

- 회원 웹과 iOS가 대상이다. 관리자 정책, Android, 서버 신설, 자동 IPA 빌드는 제외한다.
- 기존 개발 API·Firebase를 사용한다. 접근·설정 일치는 활성화 전 확인할 외부 준비 작업이다.
- 같은 Bundle ID를 유지하므로 QA·운영 앱의 동시 설치는 지원하지 않는다.
- 기존 [019 명세](../019-mobile-testflight-delivery/spec.md)의 appVersion·수동 빌드 원칙은 유지한다.
  환경·운영 트리거·기록·오류 정책은 이 기능 활성화 시 새 계약으로 대체하며 그전까지 기존 정책이 유효하다.
- 단계별 리뷰를 통과하기 전 다음 단계 구현·외부 설정 적용을 진행하지 않는다.

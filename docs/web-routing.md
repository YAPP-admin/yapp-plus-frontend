# 회원 앱 라우팅과 URL 상태 규칙

회원 앱의 독립 페이지와 페이지 내부 상태를 구분하고, 화면 구현 시 사용할 URL과 이동 규칙을
정의합니다. 작업 이슈는 [#44](https://github.com/YAPP-admin/yapp-plus-frontend/issues/44)입니다.

## 적용 상태와 범위

- **현재 상태**: 1단계 대응표와 2단계의 13개 라우트·화면 슬라이스·레이아웃 경계를 구성했습니다.
  홈 본문은 기존 소개 화면이며 나머지 12개 페이지는 제목과 공통 준비 중 안내를 제공합니다.
  하단 메뉴·화면 간 이동·복귀·개발용 목록과 쿼리 파서는 아직 구현하지 않았습니다.
- **대상**: `apps/web`의 회원 앱입니다. 관리자 앱, 모바일 네이티브 라우팅과 브리지 계약은
  변경하지 않습니다.
- **이번 작업의 최종 결과**: 13개 페이지의 제목·준비 중 안내, 간단한 헤더·하단 메뉴와 기본
  이동을 제공합니다. Figma와 정밀하게 일치하는 본문 UI, 실제 인증·API·업무 처리는 후속 작업입니다.
- **첫 진입과 배포**: `/`에서 준비 중인 회원 홈을 바로 표시합니다. 배포에서도 준비 중
  페이지를 열 수 있으며 인증 가드와 로그인 리다이렉트는 추가하지 않습니다.
- **단계 진행**: 각 단계 완료 후 사용자에게 결과와 검증 내용을 보고하고, 승인 전까지 다음
  단계로 진행하지 않습니다.

제품 목적은 [제품 맥락](./mission.md), 코드 배치는 [웹 작업 가이드](./web-development.md)를
따릅니다. 아래 URL은 이번 작업에서 합의한 웹 경로이며 API 주소나 네이티브 딥링크 계약을
확정하는 것은 아닙니다.

## 기획 기준과 출처

- 기준 확인일: **2026-10-11**. Figma는 이번 작업에서 확인한 노드와 화면 문맥을 기록했습니다.
- [현재 기능명세서][spec]의 **APP 시트**를 기본 기준으로 사용합니다. 로그인·가입의 입력
  항목과 분기는 아래 **2026-10-11 사용자 인터뷰 보완**을 우선합니다. 이 보완은 원문 시트가
  이미 변경되었다는 뜻은 아닙니다.
- [Figma App 페이지][figma-app]는 화면 구성과 상태 분류의 참고 자료로 사용합니다.
- Figma에 남아 있는 예전 전화번호 인증과 공지 질문하기는 현재 APP 명세 우선 결정에 따라
  이번 작업에서 제외합니다. 로그인·가입의 중복 시안이나 플랫폼별 프레임을 서로 다른
  페이지로 만들지 않습니다.
- 일부 프레임 이름이 실제 화면과 다르게 `3. 회원가입/정보 입력 최초`로 남아 있으므로
  프레임 이름만으로 화면을 분류하지 않습니다.

로그인·가입 화면에도 준비 중임을 표시합니다. 화면 제목만으로 실제 가입 완료나 승인 결과를
확인한 것처럼 안내하지 않습니다. `/signup`은 인증 전 회원가입 시작 화면이 아니라 신규
사용자의 추가 정보 입력 위치이며, 소셜 로그인 수단이나 입력 항목별로 경로를 나누지 않습니다.

### 로그인·가입 인터뷰 보완

2026-10-11 사용자 인터뷰에서 다음 정책을 확정했습니다. 현재 코드는 준비 중 화면이며 실제
소셜 버튼·서버 조회·분기·정보 입력은 후속 인증 기능에서 구현합니다.

- `/login`에서 `카카오로 계속하기`, `Apple로 계속하기`로 시작합니다. 로그인과 회원가입
  시작 버튼을 따로 제공하지 않고, 소셜 인증 후 DB/Auth 조회 결과로 분기합니다.
- 기존 회원은 홈으로 이동합니다. 필수 정보가 비어 있다는 이유로 기존 회원을 `/signup`으로
  보내는 정보 보완 흐름은 추가하지 않습니다.
- 신규 사용자의 추가 입력 필수 항목은 **이름·전화번호**입니다. 기수·파트는 서버 회원
  명단에서 가져오며 입력받지 않습니다.
- Apple 신규 사용자는 추가 정보 입력이 필요합니다. 카카오 신규 사용자도 전화번호 제공
  여부 등에 따라 추가 입력이 필요할 수 있으므로 두 수단 모두 `/signup`을 사용할 수 있습니다.
  카카오의 정확한 입력 진입 조건은 서버 계약에서 확인할 후속 항목입니다.
- 신규 사용자 정보가 어드민 회원 정보와 일치하면 자동 승인하고, 일치하지 않으면 운영진
  승인을 기다립니다. `/signup/status`는 승인 대기·거절 결과를 보여주는 화면입니다.
- 운영진은 가입을 거절할 수 있습니다. 거절된 사용자는 `/signup`으로 돌아가 이름·전화번호를
  수정한 뒤 재신청합니다. 별도의 재신청 입력 페이지는 만들지 않습니다.
- 정보 불일치는 곧바로 미등록 회원 오류가 되지 않습니다. `/signup/unregistered`는 기존
  준비 중 경로만 유지하며, 새 가입 정책에서 별도로 필요한 진입 조건은 재검토합니다.
- 실제 정보 비교·전화번호 검증·승인 상태 응답과 재신청 처리는 후속 서버 계약에서 확정합니다.
  이번 변경은 정책 기록과 라우트 구조 정리이며 인증 로직이나 입력·재신청 버튼은 구현하지 않습니다.

```text
/login: 카카오로 계속하기 / Apple로 계속하기
  → 소셜 인증 및 DB/Auth 조회
    → 기존 회원: 홈
    → 신규 사용자: 가입 처리
      → 추가 입력 필요: /signup에서 이름·전화번호 입력
      → 어드민 회원 정보와 비교
        → 일치: 자동 승인 → /signup/complete
        → 불일치: 운영진 승인 대기 → /signup/status
          → 승인: /signup/complete
          → 거절: /signup/status에서 안내
            → /signup에서 이름·전화번호 수정 후 재신청
```

결정하지 않습니다. 외부 링크 목적지는 확인된 값만 사용하며 이번에는 임의 URL을 연결하지
않습니다.

## 경로와 쿼리스트링

### 기본 원칙

- 서로 다른 페이지로 이동하면 경로를 사용합니다. 하단 메뉴가 탭 모양이어도 홈·일정·공지·
  마이페이지는 독립 경로입니다.
- 같은 페이지의 조회 조건은 쿼리스트링으로 표현합니다. 공지 분류마다 별도 경로를 만들지
  않습니다.
- 검색·정렬·페이지 번호는 해당 기능이 확정될 때 추가합니다. 현재 요구에 없는 쿼리 키를
  미리 예약하거나 파서를 만들지 않습니다.
- 이번에는 쿼리 규칙만 문서화합니다. 필터 UI·파서·`nuqs` 의존성과 어댑터는 실제 공지 필터
  구현 작업에서 함께 추가합니다. 준비 중 페이지가 이미 필터 기능을 제공한다는 뜻은 아닙니다.

### 공지 분류 계약

쿼리 키는 `category`이며 값은 소문자 영문으로 정의합니다.

| 선택한 분류 | URL                            | 해석                         |
| ----------- | ------------------------------ | ---------------------------- |
| 전체        | `/notices`                     | 기본값이며 `category`를 생략 |
| 세션        | `/notices?category=session`    | 세션 공지                    |
| 제출        | `/notices?category=submission` | 제출 공지                    |
| 운영        | `/notices?category=operation`  | 운영 공지                    |

`category`가 없거나 비어 있거나 지원하지 않는 값이면 전체로 해석합니다. 전체를 선택하면
`category` 키를 제거합니다. 이 값은 웹 화면의 분류 표현이며 API의 열거형을 새로 정의하는
것은 아닙니다. API 연동 시 공식 계약과 대응시킵니다.

필터 변경은 현재 이력을 `replace`하고, 페이지 이동은 `push`합니다. 따라서 세션 → 제출로
필터를 바꾼 뒤 상세로 이동했다가 뒤로가면 제출 목록으로 돌아가며, 필터 선택 이력을 하나씩
거슬러 올라가지 않습니다.

```text
/notices?category=session
  └─ 필터 변경: replace → /notices?category=submission
       └─ 상세 이동: push → /notices/123
            └─ 뒤로가기 → /notices?category=submission
```

내부 복귀 이력은 경로뿐 아니라 쿼리스트링을 포함한 URL을 보존해야 합니다. 상세를 직접 열어
이전 목록을 확인할 수 없으면 `/notices`로 돌아갑니다. 이때 이전 필터를 추측하거나 상세 URL에
필터·복귀 주소를 임의로 추가하지 않습니다. 상위 메뉴에서 공지로 새로 진입하는 링크는
`/notices`를 사용하며 마지막 필터를 별도 저장하지 않습니다.

향후 `nuqs` 구현 시 [App Router 어댑터][nuqs-adapter], [파서][nuqs-parsers],
[이력 옵션][nuqs-options]을 확인합니다. 실제 데이터 조회 계층에 맞춰 서버 갱신 옵션을 정하고,
이번 문서에서 조회 방식을 미리 확정하지 않습니다.

## 내비게이션과 복귀

- 홈·일정·공지 목록·마이페이지에만 하단 메뉴를 표시합니다. 문구는 `홈 / 일정 / 공지 /
마이페이지`이며 현재 메뉴를 시각적 표시와 `aria-current="page"`로 전달합니다.
- 상세·설정·로그인·가입 화면에는 하단 메뉴를 표시하지 않습니다. Figma의 OS 상태 표시줄과
  홈 인디케이터도 웹 UI로 만들지 않습니다.
- 주요 페이지 이동은 일반 웹 링크처럼 `push` 이력을 남깁니다. 홈 → 일정 → 공지 이후
  브라우저 뒤로가기는 일정 → 홈 순서입니다.
- 상세 화면의 상단 뒤로가기는 확인된 이전 앱 화면으로 복귀합니다. 홈에서 출석 내역을
  열었다면 홈으로, 마이페이지에서 열었다면 마이페이지로 돌아갑니다.
- 직접 접근·새 탭·새로고침 등으로 이전 앱 이력을 확인할 수 없으면 대응표의 대체 목적지로
  `replace` 이동합니다. `history.length`나 외부 referrer만으로 내부 이력을 판단하지 않습니다.
- 브라우저 뒤로가기·앞으로가기를 가로채지 않고 URL과 현재 화면이 일치하도록 합니다.
  Next.js의 history 상태를 덮어쓰거나 필터 `replace`를 새 페이지 방문으로 기록하지 않습니다.
- 이번 복귀 동작은 웹 내부 동작입니다. 네이티브 뒤로가기 버튼·스와이프와 웹 이력의 연결은
  네이티브 계약을 다루는 별도 작업입니다.

## 개발용 접근과 404

- `/dev/routes`는 13개 제품 페이지에 포함되지 않는 로컬 검수용 경로입니다. 전체 화면과
  예시 공지 상세로 이동하는 링크를 제공하며, 로컬 홈에도 개발 전용 진입 링크를 제공합니다.
- 개발용 목록은 `next dev`에서만 열립니다. Preview·Production과 로컬 프로덕션 빌드에서는
  서버에서 404를 반환하고 제품 화면에 목록 링크를 표시하지 않습니다.
- 실제 공지·인증 결과가 필요한 화면은 개발용 목록으로 확인합니다. 예시 ID는 경로 검수용이며
  가짜 공지나 인증 성공 데이터를 제공하지 않습니다.
- 정의하지 않은 경로에는 404 안내와 홈 이동 링크를 제공합니다.

## 단계별 진행과 검증

| 단계            | 결과                                    | 현재 상태    |
| --------------- | --------------------------------------- | ------------ |
| 1. 기준·대응표  | 이슈 연결, 화면·URL·상태·쿼리 규칙 문서 | 완료         |
| 2. 구조         | 라우트·페이지 슬라이스·레이아웃 경계    | 완료         |
| 3. 주요 이동    | 하단 메뉴와 홈·마이페이지 링크          | 진행 승인 전 |
| 4. 상세 복귀    | 내부 이력과 직접 접근 대체 이동         | 진행 승인 전 |
| 5. 준비 중 화면 | 로그인·가입·설정 안내                   | 진행 승인 전 |
| 6. 검수 접근    | 개발용 목록·404                         | 진행 승인 전 |
| 7. 검증         | 테스트·브라우저·품질 게이트             | 진행 승인 전 |
| 8. 최종 대조    | 문서와 구현 대조·검토 결과              | 진행 승인 전 |

2단계에서는 `node --run check`와 `node --run build`가 통과했습니다. 공통 셸과 홈을 함께
렌더링했을 때 헤더·본문이 중복되지 않는 회귀 테스트를 추가했고, 프로덕션 서버의 13개 URL을
각각 두 번 요청해 200 응답·제목·단일 헤더·단일 본문을 확인했습니다. Chrome에서 375px의
일정·공지 상세·미등록 안내와 1440px의 홈을 점검했으며 가로 넘침과 브라우저 경고·오류가
없었습니다. 공지 상세는 브라우저 새로고침도 확인했습니다. 실기기 WebView·스크린 리더와
다크 모드 검증은 아직 수행하지 않았습니다.

2단계 보완에서는 `(tabs)`를 유지하고 `(detail)`을 제거해 공지 상세·출석·설정을 기능별
디렉토리로 옮겼습니다. 기존 13개 URL을 유지했으며 `node --run check`와 `node --run build`가
다시 통과했습니다. 새 프로덕션 서버에서 13개 URL의 200 응답·제목·단일 헤더·단일 본문을
확인했습니다. 이번 폴더 이동에서는 브라우저 시각 검증과 실기기 검증을 다시 수행하지 않았습니다.
승인·거절·재신청은 정책만 기록했으며 실제 인증 동작은 구현하거나 검증하지 않았습니다.

라우트·레이아웃 변경 이후 `mise exec -- node --run check`와
`mise exec -- node --run build`를 실행합니다. 화면 이동·복귀의 인접 테스트와 함께 다음
시나리오를 확인하고 실행하지 못한 환경은 보고합니다.

- 13개 페이지의 직접 접근·새로고침과 고유 제목.
- 하단 메뉴의 이력·활성 표시·키보드 조작과 상세 화면의 메뉴 숨김.
- 홈 → 출석 내역 → 홈 복귀, 마이페이지 → 출석 내역 → 규칙 → 출석 내역 복귀.
- 직접 연 공지 상세 → 공지 목록, 직접 연 설정 → 마이페이지 복귀.
- 쿼리가 포함된 공지 목록 → 상세 → 기존 쿼리를 포함한 목록 복귀. 필터 UI가 없는 동안에는
  직접 URL과 이동 테스트로 복귀 규칙을 확인하고, 실제 분류 변경 검증은 필터 구현 때 추가.
- 개발용 목록은 로컬 개발에서 접근 가능하고 프로덕션 빌드에서는 404.
- 모바일 폭·터치·스크린 리더·safe-area·라이트/다크 모드와 사용 가능한 iOS WebView 환경.

실제 인증 계약·가입 상태 응답, 외부 링크 주소와 네이티브 뒤로가기 연결은 후속 기능의
확인 항목입니다. 준비 중 화면과 이번 문서 작성에는 해당 값이 필요하지 않습니다.

# 기능 명세: 회원 앱 행동 분석과 iOS 오류 모니터링

**작업 브랜치**: `DongjaJ/posthog`

**작성일**: 2026-11-28

**상태**: 1단계 반영 완료 — 후속 구현 진행 승인

**관련 이슈**: [#669](https://github.com/YAPP-admin/yapp-plus-frontend/issues/669)

**입력**: 회원 앱의 PostHog 이벤트 40개 원문과 대화에서 확정한 수집 범위·로그인 기준·알림 구분·iOS 모니터링 계획.

## 사용자 시나리오와 검증

### 시나리오 1 — 회원의 인증·참여 흐름을 정확하게 분석한다 (P1)

운영자는 소셜 인증 성공, 가입 신청, 출석과 팀 인증의 진행·완료를 서로 구분해 확인한다.
우선순위 이유는 승인 대기와 인증 실패를 혼동하거나 중복 행동을 집계하면 핵심 전환율이 왜곡되기 때문이다.
독립 검증은 신규·대기·승인 계정으로 직접 로그인하고 가입·출석을 수행한 뒤 수신 결과를 비교한다.

1. 신규 회원이 직접 소셜 인증을 완료하면 인증 성공 1회와 신규 여부가 기록되고, 가입 정보 제출 성공은 별도 신청 1회로 기록된다.
2. 승인 대기·반려 회원이 직접 소셜 인증을 완료하면 기존 사용자 인증 성공 1회로 기록된다. 운영진 승인 완료로 기록하지 않는다.
3. 자동 로그인·토큰 갱신·취소는 직접 인증 성공으로 집계하지 않는다.
4. 출석 입력 검증·위치 획득에 실패하면 서버 제출 횟수를 늘리지 않는다. 실제 서버 제출은 성공 여부와 시도 횟수를 기록한다.

### 시나리오 2 — 정보 탐색과 알림 유입을 구분한다 (P1)

운영자는 공지·홈·뒤풀이·출석 내역의 실제 노출과 알림 진입 경로를 확인한다.
독립 검증은 화면·탭 전환, 백그라운드 복귀, 푸시 중복 전달을 실행해 기록 횟수와 읽기 시간을 비교한다.

1. 알림 목록에서 누르면 앱 내부 경로, 휴대폰 푸시를 누르면 푸시 경로로 기록한다.
2. 같은 푸시 열기 요청을 재전달해도 1회이며, 이후 사용자가 같은 알림을 다시 누르면 별도 행동으로 기록한다.
3. 숨겨진 탭의 데이터 재조회는 화면 노출로 기록하지 않는다. 공지 읽기 시간에 백그라운드 체류시간을 더하지 않는다.
4. 조회한 결과가 승인·출석 확정·팀 인증 심사 완료를 대신 발생시키지 않는다.

### 시나리오 3 — 민감한 내용을 드러내지 않고 이용 흐름을 살펴본다 (P1)

운영자는 마스킹된 웹 화면 녹화로 사용 흐름을 확인한다. 회원의 이름·연락처·사진·사유 원문은 보이지 않아야 한다.
독립 검증은 가짜 개인정보를 입력하고 실제 수신 데이터와 재생 화면을 확인한다.

1. 입력값·동적 텍스트·사용자 이미지는 숨기며 검토된 고정 버튼·메뉴 문구만 보인다.
2. 개발 환경의 기록은 운영 프로젝트에 유입되지 않는다. 수집 설정이 없거나 전송이 실패해도 기존 기능을 이용할 수 있다.
3. 로그아웃·탈퇴·계정 변경 후 다음 회원의 행동과 녹화가 이전 회원에 연결되지 않는다.

### 시나리오 4 — iOS 장애를 해당 배포 버전의 원본 코드로 추적한다 (P2)

운영자는 웹 콘텐츠 외부의 앱 오류와 크래시를 확인하고 원본 코드 위치 및 영향받은 앱 버전을 찾는다.
독립 검증은 릴리스 빌드의 제어된 테스트 오류·크래시와 재시작으로 진행한다.

1. 처리되지 않은 오류와 네이티브 크래시를 수신하고 코드 위치·앱 버전·업데이트 버전을 확인한다.
2. 앱 업데이트 전후의 오류는 각각 해당 버전의 코드 위치로 표시된다.
3. 네이티브 모니터링 때문에 사용자 행동 이벤트와 화면 녹화가 이중 수집되지 않는다.

### 경계 사례

- 요청 처리 확인 실패·화면 재렌더·앱 재시작을 사용자 재클릭과 구분한다.
- 기록에 필요한 시각·식별자가 없으면 속성을 생략한다. 대체 ID나 가짜 0을 보내지 않는다.
- 빠른 계정 전환 중 이전 계정의 늦은 결과를 현재 계정 행동으로 기록하지 않는다.
- 종료 직전 전송 및 초기화 전 장애의 완전 수집은 보장하지 않는다.
- 사전보고 복수 유형은 report_types 배열로 기록하며 제출 한 번에 이벤트 한 건을 유지한다. 기존 보고 수정 여부는 is_edit로 구분한다.

## 요구사항

### 기능 요구사항

- **FR-001**: 이벤트 원문 40개를 보존하고 현재 기능에 연결할 24개와 후속 16개를 구분한다. 명세 밖의 제품 기능을 새로 만들지 않는다.
- **FR-002**: 직접 소셜 인증의 서버 결과 정상 수신을 인증 성공으로 기록한다. 신규 여부는 서버 결과로만 판단하며 운영진 승인과 분리한다.
- **FR-003**: 가입 신청은 이번 가입 제출로 승인 대기에 처음 진입할 때만 기록한다.
- **FR-004**: 알림 열기 경로를 구분하고 같은 요청의 재처리만 중복 제거한다. 실제 알림 ID가 없는 경로에서는 이를 생략한다.
- **FR-005**: 화면 노출은 실제 활성 화면, 읽기 시간은 전면 체류만 측정한다. 제출·클릭·이탈은 각 이벤트의 발생 조건을 따른다.
- **FR-006**: 확인할 수 없는 속성은 생략하고 원인과 필요한 정보 보완을 문서화한다.
- **FR-007**: 개발·운영 수집을 분리하고 로컬·Preview는 명시적으로 켜기 전까지 수집하지 않는다. 운영 웹 녹화는 100%로 시작하며 운영자가 비율을 조절할 수 있어야 한다.
- **FR-008**: 개인정보와 인증 정보는 행동 기록·자동 수집·녹화·오류 부가 정보에 남기지 않는다. 기본적으로 입력과 텍스트를 마스킹하고 사용자 이미지를 차단한다.
- **FR-009**: 동일 회원의 식별을 유지하되 로그아웃·탈퇴·계정 변경 시 분리한다. 분석 장애가 회원의 기존 업무를 막지 않아야 한다.
- **FR-010**: iOS 앱 오류·크래시를 별도 단계에서 도입하고 실제 배포 코드 위치를 확인할 수 있어야 한다. 네이티브 행동 자동 수집·녹화는 제외한다.
- **FR-011**: 이전 앱 버전과의 호환 및 단계별 수집 중단·복구 방법을 마련한다. 검증된 배포만 운영에 적용한다.

### 핵심 개념

- **행동 기록**: 이벤트명, 알려진 속성, 발생 조건으로 구성된다. 하나의 실제 행동과 재처리는 구분한다.
- **회원 식별**: 내부 회원 번호를 사용한다. 인증 토큰·이름·전화번호를 식별자로 사용하지 않는다.
- **알림 항목과 열기 요청**: 서버에 저장된 항목의 ID와 일시적인 처리 요청 번호는 별개다.
- **오류 기록**: 오류 종류·코드 위치·해당 배포 버전·확인 가능한 회원 식별을 담는다.

## 성공 기준

- **SC-001**: 구현 대상 24개 모두 지정한 재현 시나리오에서 기대한 이름·속성·횟수로 확인되며, 보류 16개는 회원 앱에서 발생하지 않는다.
- **SC-002**: 인증 취소·자동 복원·토큰 갱신과 알림 재처리 시나리오에서 잘못 추가된 인증·열기 기록이 0건이다.
- **SC-003**: 검증용 이름·전화번호·토큰·사유·이미지 주소가 전송 데이터와 녹화에 노출되는 사례가 0건이다.
- **SC-004**: 수집 비활성화·전송 차단 상황에서도 로그인·출석·공지 열기의 기존 완료 시나리오가 모두 통과한다.
- **SC-005**: 제어된 iOS 오류·크래시를 앱 재실행 후 수신하고 앱 업데이트 전후 각각 원본 코드 위치와 배포 버전을 확인한다.

## 가정과 범위

- 회원 앱만 대상이며 관리자 앱, Android 네이티브 수집·출시 검증, 성능 모니터링은 제외한다.
- 정산 8개·소모임 4개·뒤풀이 응답 1개는 미구현, 관리자·서버 확정 3개는 별도 책임이므로 보류한다.
- US 리전의 개발·운영 프로젝트를 사용한다. 실제 프로젝트 접근 권한·설정 값과 iOS 검증 환경은 해당 단계에서 확보한다.
- 공개 웹 녹화는 WebView 콘텐츠까지이며 소셜 로그인 창·사진 선택기 등 네이티브 화면은 제외한다.
- 구체적인 이벤트 계약은 [계약](contracts/events.md), 기술·진행 순서는 [계획](plan.md), 검증 방법은 [검증 안내](quickstart.md)를 따른다.

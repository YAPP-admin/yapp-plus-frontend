# 구현 계획: 어드민 출석 관리

**브랜치**: `tallinn/xoaj3` · **작성일**: 2026-10-29 · [명세](spec.md) · [이슈 #180](https://github.com/YAPP-admin/yapp-plus-frontend/issues/180)

## 요약

기존 출석 화면의 자리 표시자를 상태가 유지되는 모의 서비스 기반 UI로 구현한다.
0단계는 명세·독립 ViewModel·계약 문서만 작성한다. 실제 API 연결은 이번 구현 범위가 아니다.

## 기술 맥락

- 대상: `apps/admin`, TypeScript·React, TanStack Start/Router/Query/Form/Table, Zod.
- UI: 기존 SEED Design, vanilla-extract, overlay-kit과 Snackbar를 사용한다. 새 의존성은 추가하지 않는다.
- 실행: `mise.toml`의 Node 24.20.0, `package.json`의 pnpm 12.3.4.
- 상태: Query는 조회 결과, Form/로컬 상태는 수정 초안, URL은 필터를 소유한다.
- 저장소: 브라우저의 상태 유지 모의 서비스. 새로고침 영속성은 보장하지 않는다.
- 검증: Vitest와 Testing Library, 루트 `node --run check`; 앱 변경 단계에는 `node --run build`도 수행한다.
- 성능: 필터와 페이지 조회가 있어도 마감은 전체 세션에 적용한다. 근거 없는 수치 SLA는 추가하지 않는다.

## 원칙 점검

`.specify/memory/constitution.md`는 미작성 템플릿이다. 실제 제약은 `AGENTS.md`와 사용자 합의를 따른다.
설계 전후 점검: 앱 간 import 없음, 생성 코드 수정 없음, 새 공용 패키지 없음, API 타입과 ViewModel 분리.
데이터 변경은 모의 서비스에 한정하며 실제 서버·인증에는 영향을 주지 않는다.
복구는 모의 데이터 초기화와 해당 기능 변경의 되돌림으로 수행한다. 실제 연결 전에는 별도 계약 검토가 필요하다.

## 구조와 경계

```text
apps/admin/src/
├── routes/_dashboard/attendance/   # 기존 경로와 검색 매개변수 연결
├── pages/attendance/               # 목록·상세·누적 화면 조합
├── pages/sessions/                 # 기존 세션 관리 화면
└── features/session-management/    # 두 페이지가 실제 공유하는 세션·출석 데이터와 동작
    ├── index.ts                   # 공개 진입점
    ├── model/                     # 독립 모델, Query, 모의 데이터
    ├── service/index.ts           # 서비스 공개 진입점
    └── testing/index.ts           # 테스트용 모의 저장소 공개 진입점
```

1단계에서 두 페이지가 공유할 최소 세션 모델·조회·모의 저장소만 옮긴다.
세션 폼·장소 검색 등 화면 전용 코드를 통째로 이동하지 않는다. 다른 page/feature 슬라이스 내부를 import하지 않는다.
출석 UI는 우선 `pages/attendance`에 두고, 재사용이 확인된 동작만 같은 feature에 둔다.
미래 API adapter만 생성 SDK/DTO를 import하여 검증·명시적 매핑한다. 미사용 adapter 추상화는 미리 만들지 않는다.
ViewModel·입력 모델·컴포넌트·모의 데이터에는 API 타입 import, extends, Pick/Omit, indexed access를 사용하지 않는다.

| 단계 | 변경 목적                            | 핵심 검증                             |
| ---- | ------------------------------------ | ------------------------------------- |
| 0    | 명세·독립 모델 설계·백엔드 계약 초안 | 문서 정합성, 링크, 품질 게이트        |
| 1    | 최소 세션 데이터 공유 구조 추출      | 기존 세션 CRUD 동작 유지              |
| 2    | 독립 모델과 모의 점수 규칙           | 감점 구간, 미정, 보고 분리, 명찰 독립 |
| 3    | 상태 유지 모의 서비스                | 세션 생성 연동, 조회·수정·부분 실패   |
| 4    | 세션 목록과 일반 출석 상세·필터      | URL 필터, 전체 요약, 빈 상태          |
| 5    | 사전 보고와 변경 이력                | 유형·시각·이력 분리                   |
| 6    | 출결·명찰 수정 초안과 이탈 처리      | 초안 유지, 취소, 이탈 경고            |
| 7    | 출석 마감·마감 취소                  | 전체 미정 전환, 잠금, 실패 재시도     |
| 8    | 코드 조회·발급·재발급                | 명시적 발급, 만료, 실패               |
| 9    | 팀 목록과 사진 보기                  | 미제출/대기 구분, URL 접근 실패       |
| 10   | 팀 판단·연속 검수·마감 연결          | 개별 수정 보존, 대기 마감 차단        |
| 11   | 누적 점수와 회원 상세                | 합계, 근거, 40점 경계                 |
| 12   | 통합 흐름과 접근성·반응형 검증       | 키보드·스크린 리더·터치, 오류 흐름    |

1단계는 PR 크기 제한에 따라 1-1 모델·공개 진입점 추출과 1-2 서비스·Query·모의 저장소 추출로 나눈다.
0단계 문서는 별도 PR로 분리하고 각 하위 단계도 사용자 리뷰를 받는다.

2단계도 2-1 출결·보고·명찰 모델과 감점 규칙, 2-2 나머지 ViewModel·입력·초안으로 나눈다.
사용자 승인으로 `attendance-core`를 `e073c39`에 생성했다. 2-2단계 코드 PR은 이 브랜치를 base로 분리한다.

3단계는 3-1 세션 생명주기·출석 조회, 3-2 출결 수정·이력·실패 재현으로 나누어 리뷰한다.
사용자 승인으로 `attendance-read`를 `3df9519`에 생성했고 3-2단계의 PR base로 사용한다.

각 단계 후 변경 파일·검증 결과와 미검증 항목·화면 근거·리뷰 항목·변경량을 보고한다.
사용자의 리뷰와 다음 단계 진행 확인 전에는 다음 단계 구현을 시작하지 않는다.
각 PR은 실제 base 대비 추가·삭제 합계 800줄 미만으로 유지하고 650줄부터 분리를 검토한다.
이동·문서·테스트·생성 파일도 계산하며, 필요하면 같은 단계를 더 작은 리뷰 단위로 나눈다.
commit·push·PR 생성은 별도 승인 대상이다.

## 마감 처리 설계

초안 검증 → 변경된 출결·명찰·팀 판단 반영 → 마감 요청 → 상세·목록·누적 조회 갱신 순서다.
팀 판단이 회원 출결에 영향을 줄 때는 팀 판단 후 명시적 개인 수정을 반영한다.
개별 요청의 성공을 기록하여 재시도 시 성공한 작업을 무조건 반복하지 않는다.
변경 반영이 모두 성공한 경우에만 마감하며, 마감 실패와 조회 갱신 실패도 구분한다.
409 검수 대기는 갱신 후 판단을 이어간다. 여러 요청 전체가 원자적이라고 가정하지 않는다.
응답 유실로 성공 여부가 불명확하면 재조회로 확인하며 실제 API의 재시도 계약은 연결 전에 합의한다.

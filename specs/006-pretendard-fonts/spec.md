## 사용자 시나리오와 검증

### US1 — 웹 화면의 일관된 서체 (P1)

사용자는 웹뷰와 관리자 웹에서 같은 Pretendard 서체로 콘텐츠를 읽는다. 개발자는 Storybook에서
동일한 서체와 굵기를 확인한다. 현재 제품 화면에 직접 영향을 주므로 가장 먼저 적용한다.

**독립 검증**: 각 웹 앱을 빌드하고 한글·영문·숫자·기호와 입력 요소의 실제 서체를 확인한다.

1. 처음 접속하면 현재 화면에 필요한 문자 구간만 앱의 출처에서 다운로드한다.
2. 다른 굵기의 텍스트를 표시하면 해당 굵기를 실제 폰트로 표현한다.
3. 폰트를 받지 못해도 시스템 글꼴로 내용을 읽고 버튼과 입력 요소를 사용할 수 있다.
4. 하위 경로에 배포된 Storybook에서도 폰트를 정상적으로 불러온다.

### US2 — 네이티브 화면에서 사용할 가변 서체 (P2)

개발자는 Expo iOS의 텍스트와 입력 요소에서 같은 가변 서체를 사용할 수 있다.
현재 네이티브 텍스트 화면은 없으므로 등록과 사용 안내까지 제공한다.

**독립 검증**: 지원되는 iOS 환경에서 400·500·700 굵기를 표시하고 시작 실패 처리를 확인한다.

1. 로컬 폰트가 준비되면 앱이 시작하고 네이티브 글자에 지정한 굵기가 적용된다.
2. 폰트 로딩이 실패해도 시작 화면에 갇히지 않고 앱을 사용할 수 있다.
3. 변경 후에도 기존 웹뷰 진입과 safe-area 전달이 작동한다.

### 경계 조건

- 서버 콘텐츠와 사용자 이름에 현재 화면에 없던 한글이 포함될 수 있다.
- 네트워크가 느리거나 웹폰트 파일 요청이 실패할 수 있다.
- 네이티브 폰트 등록 실패와 splash 해제 실패를 구분해 진단할 수 있어야 한다.

## 요구사항

- **FR-001**: 웹뷰, 관리자 웹과 Storybook preview에 Pretendard를 기본 서체로 적용한다.
- **FR-002**: 웹폰트는 앱과 함께 배포하고 외부 CDN 런타임 요청을 만들지 않는다.
- **FR-003**: 필요한 문자 구간만 다운로드하며 사용자 콘텐츠를 기준으로 글자를 영구 제외하지 않는다.
- **FR-004**: 네이티브는 공식 가변 폰트의 전체 문자 범위를 유지하고 여러 굵기를 제공한다.
- **FR-005**: 폰트 실패가 콘텐츠 접근이나 앱 시작을 막지 않는다.
- **FR-006**: 폰트 버전·출처·라이선스와 플랫폼별 사용법을 기록한다.
- **FR-007**: 기존 웹뷰·브리지 동작을 보존하고 업그레이드 복구 절차를 기록한다.

## 성공 기준

- **SC-001**: 세 웹 환경에서 한글·영문·숫자 표본과 굵기 400·500·700을 확인한다.
- **SC-002**: 최초 화면에서 전체 문자 조각보다 적은 수의 파일을 요청하고 외부 폰트 요청은 0건이다.
- **SC-003**: 폰트 요청 실패 상황에서도 콘텐츠 읽기와 기본 조작이 가능하다.
- **SC-004**: 지원되는 iOS 환경에서 정상 시작·폰트 실패 후 시작·기존 웹뷰 동작을 확인한다.

## 가정과 범위

- 사용자가 Expo SDK 58의 베타/next 도입을 선택했다.
- 이 저장소의 네이티브 대상은 iOS이며 별도 Android 프로젝트는 수정하지 않는다.
- 제품 화면을 새로 추가하지 않고 기존 글자 크기·배치·색상 체계를 유지한다.
- Xcode 업데이트·스토어 배포는 이번 저장소 구현에 포함하지 않는다.

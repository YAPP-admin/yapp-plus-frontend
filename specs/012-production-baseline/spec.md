# 기능 명세: 앱별 성공 배포 기준으로 누적 변경 판정

**작업 브랜치**: `fix/131-production-baseline`  
**작성일**: 2026-10-29  
**상태**: 구현·로컬 검증 완료, Draft PR 리뷰 대기  
**요청**: #131 — 취소·실패 이후 변경이 다음 Production 배포에서 누락되지 않도록 한다.

## 사용자 시나리오와 검증

### 시나리오 1 — 미배포 변경 보존 (P1)

운영자는 이전 CI 또는 배포가 취소된 뒤 문서만 수정해도 누적된 제품 변경이 배포되기를 원한다.
독립 검증은 성공 A, 미배포 B, 문서 변경 C를 준비해 비교 기준이 A인지 확인한다.

1. A 성공 후 B가 취소되면 C는 A부터 누적 비교한다.
2. Web만 성공하고 Admin이 실패하면 다음 실행은 앱별로 다른 기준을 사용한다.

### 시나리오 2 — 불확실한 실제 배포 상태 복구 (P1)

운영자는 실제 배포는 끝났지만 성공 기록이 실패한 경우에도 변경을 빠뜨리지 않아야 한다.

1. 성공 A 이후 B 배포의 성공 기록이 없고 C가 A로 되돌아가면 배포를 생략하지 않는다.
2. 최초 배포 또는 사용할 수 없는 이력에서는 대상 앱을 강제 배포한다.
3. 수동 Production 성공도 다음 자동 배포의 기준이 된다. Preview는 기준을 바꾸지 않는다.

### 경계 조건

- 이력 조회 실패는 작업을 실패시킨다. 불확실한 이력을 영향 없음으로 처리하지 않는다.
- 최근 시도가 미완료·실패이면 이전 성공 이력을 재사용하지 않는다.
- 기준 commit이 없거나 현재 검증 commit의 조상이 아니면 강제 배포한다.

## 요구사항

- **FR-001**: 앱별 실제 Production 시도와 성공 여부를 검증된 commit에 연결한다.
- **FR-002**: 배포 시작 전에 시도를 기록하며 기록 실패 시 실제 배포를 시작하지 않는다.
- **FR-003**: 최근 시도가 성공한 경우만 해당 commit부터 누적 변경을 비교한다.
- **FR-004**: 실패·취소·배포 생략은 성공 기준을 전진시키지 않는다.
- **FR-005**: 자동·수동 Production은 같은 이력을 사용하고 Preview는 분리한다.
- **FR-006**: 조회 오류는 명확히 실패하고 이력 부재·불확실성은 강제 배포로 복구한다.

### 주요 개체

- 배포 시도: 대상 프로젝트, commit, 성공 여부, 배포 URL, 실행 로그.
- 비교 범위: 대상 앱의 최근 확정된 성공 commit과 이번 CI 검증 commit.

## 성공 기준

- **SC-001**: 취소 후 문서 변경, 앱별 부분 실패, 첫 배포 시나리오에서 변경 누락이 없다.
- **SC-002**: 실제 배포와 기록이 불일치할 수 있는 경우 배포 생략이 0회다.
- **SC-003**: 확정된 이력과 변경 없음이 확인된 경우 기존 배포 생략 기능을 유지한다.

## 가정과 제외 범위

- 기존 main CI 검증과 Vercel 프로젝트 설정을 유지한다. 새 비밀 값은 추가하지 않는다.
- 동시 배포 완료 순서와 과거 CI의 승격 방지는 #132에서 다룬다.
- 외부 콘솔에서 수행한 수동 Vercel 배포는 이력 계약 밖이다. 그런 경우 GitHub 수동
  Production 배포로 검증된 main을 다시 배포해 이력을 복구한다.

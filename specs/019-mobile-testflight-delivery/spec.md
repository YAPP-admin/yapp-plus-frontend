# 기능 명세: TestFlight 자동 OTA와 조건부 iOS 빌드

**기능 디렉터리**: `specs/019-mobile-testflight-delivery`
**작업 브랜치**: `DongjaJ/eas-update-expo-preview`
**작성일**: 2026-11-07
**상태**: 0단계 리뷰 대기; 구현·배포 미완료
**이슈**: [#367](https://github.com/YAPP-admin/yapp-plus-frontend/issues/367)
**입력**: main 변경을 보고 EAS Update 또는 GitHub iOS 로컬 빌드를 실행하며 단계마다 리뷰한다.

## 사용자 시나리오와 테스트

### US1 — 병합 전 호환성 확인과 배포 판정 (P1)

개발자는 모바일 변경의 배포 방법을 확인하고, 새 네이티브 구성을 기존 앱 버전으로 배포하는 실수를 병합 전에 발견한다.
**우선순위 이유**: 잘못된 OTA를 막는 조건이며 외부 게시 없이 독립 검증할 수 있다.
**독립 검증**: 대표 변경을 준비하고 CI 결과와 판정 사유를 확인한다.

1. 네이티브 변경이 있지만 앱 버전을 증가시키지 않은 PR은 CI가 실패한다.
2. 모바일에 영향 없는 변경은 미반영 모바일 변경도 없을 때 배포를 생략한다.
3. 실패·취소된 이전 실행에 모바일 변경이 있으면 다음 main 실행이 이를 누적 판정한다.
4. 기준 정보가 없거나 호환성을 확인할 수 없으면 OTA를 허용하지 않는다.

### US2 — 필요한 IPA만 생성 (P2)

개발자는 새 앱 버전에 필요한 IPA를 자동 생성하고 제출할 대상을 명확히 식별한다.
**우선순위 이유**: 최초 기준과 네이티브 변경을 배포할 수 있어야 OTA를 사용할 수 있다.
**독립 검증**: 새 버전의 검증된 소스로 IPA를 생성하고 출처·식별자·무결성을 확인한다.

1. 최초 도입 또는 새로운 runtime에 호환 IPA가 없으면 GitHub macOS에서 빌드한다.
2. 제출 대기 중 JS만 변경되면 호환 IPA를 재사용하고 재빌드하지 않는다.
3. IPA가 만료되거나 운영자가 재빌드를 요청하면 새 build number로 다시 생성한다.
4. 빌드 성공만으로 TestFlight 제출이나 OTA 활성화가 발생하지 않는다.

### US3 — 수동 제출과 설치 확인 후 활성화 (P2)

운영자는 원하는 IPA를 제출하고 새 네이티브 버전의 핵심 기능을 확인한 뒤 자동 OTA를 허용한다.
**우선순위 이유**: 업로드 성공과 설치 가능·동작 확인은 서로 다르다.
**독립 검증**: 지정 IPA 제출부터 실제 기기 검증과 활성화까지 기록을 따라간다.

1. 제출한 IPA의 출처·digest가 생성 기록과 일치하며 임의의 최신 빌드를 선택하지 않는다.
2. 업로드 완료 이후에도 설치·로그인·WebView·위치 기능 확인 전에는 활성화하지 않는다.
3. 활성화 시 최신 main의 CI가 성공했으면 대기 중 누적 변경을 재평가하고, 미성공이면 기다린다.
4. 이전 버전으로의 활성화나 같은 runtime의 다른 네이티브 구성 등록은 거부한다.

### US4 — 최신 TestFlight 버전의 자동 OTA와 복구 (P3)

테스터는 호환되는 변경을 재설치 없이 받고, 운영자는 문제가 있는 OTA를 복구한다.
**우선순위 이유**: US1~US3의 검증된 기반을 실제 전달에 연결한다.
**독립 검증**: 활성 runtime에 JS 수정을 게시하고 실제 설치본의 적용·롤백을 확인한다.

1. 검증된 최신 main의 호환 변경만 최신 활성 runtime에 자동 게시한다.
2. 같은 SHA의 성공한 게시를 재시도해도 중복 게시하지 않는다.
3. 자동화를 중지한 상태에서 같은 runtime의 정상 OTA 또는 내장 코드로 복귀할 수 있다.
4. 게시 후 이력 기록만 실패하면 외부 결과를 확인하며 확인 불가 시 재게시하지 않는다.

### 경계 사례

- 최초 기준은 기존 배포본을 가져오지 않고 새 앱 버전으로 만든다.
- 새 버전이 준비 중이면 구버전의 자동 OTA를 계속 게시하지 않는다.
- 늦게 끝난 CI, 자동·수동 실행 경합, 대기 실행 취소, artifact 만료를 구분한다.
- 빌드 설정·도구 변경, 환경 불일치, 부분적인 fingerprint 수집 실패도 호환성 확인 실패로 취급한다.
- 정상 OTA가 없는 runtime은 내장 코드 복귀를 사용한다. 네이티브 결함은 수정 빌드가 필요하다.

## 요구사항

### 기능 요구사항

- **FR-001**: 자동 배포는 동일 저장소 main push의 성공한 CI가 검증한 소스만 사용한다.
- **FR-002**: 모바일과 실제 의존 패키지·설정의 영향을 검사하며 마지막 반영 소스부터 누적 비교한다.
- **FR-003**: PR에서 네이티브 구성 변경 시 앱 버전 증가를 요구하고 감소를 거부한다. 배포에서도 재검사한다.
- **FR-004**: `appVersion` 정책을 유지하고 fingerprint 및 별도 빌드 구성 검사를 함께 사용한다.
- **FR-005**: 최초 기준은 새 앱 버전으로 만들며 기준 미등록 상태에서는 OTA를 금지한다.
- **FR-006**: 네이티브 빌드는 GitHub macOS에서 수행하고 build number를 자동 증가시킨다.
- **FR-007**: 호환 IPA가 제출·활성화 대기 중이면 JS 변경으로 다시 빌드하지 않는다.
- **FR-008**: 운영자가 지정한 IPA만 수동 제출하며 출처·식별자·digest를 검증한다.
- **FR-009**: 새 네이티브 버전마다 실제 설치·핵심 기능 확인 후 수동 활성화한다.
- **FR-010**: 최신 활성 runtime만 자동 지원하며 구버전은 마지막 정상 상태를 유지한다.
- **FR-011**: 채널·환경·WebView 대상과 앱 식별자를 빌드·검사·OTA에서 일관되게 검증한다.
- **FR-012**: 자동·수동 작업을 직렬화하며 오래된 실행이 최신 정상 배포를 덮지 못하게 한다.
- **FR-013**: 판정과 빌드·제출·활성화·OTA·복구 결과를 출처와 연결하고 비밀 값을 노출하지 않는다.
- **FR-014**: 불확실한 판정·외부 결과는 자동 게시를 중단하고 사유와 재개 조건을 제공한다.
- **FR-015**: 재시도는 성공 결과를 재사용하고 외부 성공·기록 실패를 확인 없이 반복하지 않는다.
- **FR-016**: 자동화를 정지·재개하고 현재 runtime의 OTA를 정상 update 또는 내장 코드로 복구할 수 있다.
- **FR-017**: 보고 전용 → 빌드 → 수동 제출·활성화 → 자동 OTA 순서로 도입하고 각 단계 리뷰를 받는다.

### 주요 개체

- **배포 후보**: 검증된 소스와 앱 버전, 변경 사유를 가진 전달 대상.
- **기준 빌드**: 설치·검증 후 자동 OTA의 호환성 기준으로 활성화한 빌드.
- **작업 이력**: 소스·산출물·외부 결과·성공 여부를 연결하는 기록.
- **운영 상태**: 보고 전용·빌드 허용·자동 OTA 허용·일시 정지 상태.

## 성공 기준

- **SC-001**: 준비한 네이티브 변경·버전 누락 사례 전부가 병합 전 검사에서 거부된다.
- **SC-002**: 영향 없는 변경 및 제출 대기 중 JS 변경 사례에서 불필요한 IPA 생성이 0건이다.
- **SC-003**: 모든 게시 결과를 검증된 소스·runtime·기준 빌드로 추적할 수 있다.
- **SC-004**: 실패·취소·중복·역순 완료 시나리오에서 변경 누락과 이전 소스의 자동 덮어쓰기가 0건이다.
- **SC-005**: 활성화 전에는 자동 OTA가 0건이며 활성화 후 호환 수정의 전달과 롤백을 실제 기기에서 확인한다.

## 가정과 확정 범위

- 사용자는 TestFlight 전용 배포, 수동 제출·활성화, 새 기준 빌드, 최신 runtime만 지원을 선택했다.
- 최초 버전은 현재 `1.0.1`의 다음 patch `1.0.2`를 기본으로 하며 실제 도입 시 main보다 큰 버전을 사용한다.
- 앱 내 강제 재시작, Android, 구버전 OTA 유지보수, PR Preview, App Store 공개 배포는 제외한다.
- 웹은 독립 배포하며 기존 Web/Admin 결함 #131·#132는 회귀 설계의 참고이지 이번 수정 대상이 아니다.
- Expo·Apple 자격 증명과 GitHub 환경 준비 여부는 [검증 기록](validation.md)의 외부 조건으로 관리한다.

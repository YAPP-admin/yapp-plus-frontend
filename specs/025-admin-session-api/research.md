# 조사 기록: 세션 API 연결

**확인일**: 2026-11-17 | **기준**: `3420a854` | **대상**: [#462](https://github.com/YAPP-admin/yapp-plus-frontend/issues/462)

## R1 — 생성 계약과 장소

- 결정: 저장소의 11월 16일 생성 계약을 기준으로 정규 주소·좌표 필수, 팀 장소 null을 적용한다.
- 근거: `CreateSessionRequest`·`AdminSessionResponse`의 설명과 사용자 최종 확인이 일치한다.
  공개 OpenAPI 재조회는 503·타임아웃으로 실패했다. 실서버 구현·배포 상태까지 확인한 것은 아니다.
- 대안: 생성 파일 직접 수정·팀 안내 필드 발명은 제외한다. `location` 조합은 승인된 프론트 규칙이며
  서버가 주소·상세주소를 조합하거나 같은 방식으로 정규화한다고 가정하지 않는다.

## R2 — 실제 기수와 개발 검증

- 결정: 기수 ID를 환경 설정·페이지 props로 공급하고 미설정이면 요청을 막는다.
- 근거: 관리자용 기수 목록·현재 기수 조회가 생성 계약에 없다. 로그인도 기수를 반환하지 않는다.
  회원 승인 상세의 소속 ID는 전체·현재 기수의 기준이 아니고, 회원용 현재 기수 조회는 다른 인증이다.
- 대안: 표시 번호 33을 DB ID로 추정하거나 실제 환경에 mock ID를 기본값으로 넣지 않는다.
  개발·테스트는 명시적인 기수 ID와 MSW 응답을 사용한다.

## R3 — 조회·입력 모델과 출석 분리

- 결정: 세션 페이지 전용 모델·Query·Mutation을 만들고 기존 출석 모의 흐름을 유지한다.
- 근거: 현재 출석과 세션이 같은 `useSessionsQuery`를 사용한다. 기존 `sessionSchema`는 조회에도
  필수 주소·좌표와 HH:mm을 요구하므로 API 응답의 HH:mm:ss를 그대로 받을 수 없다.
- 대안: 공용 feature의 서비스만 교체하거나 API 응답을 임의 값으로 바꾸지 않는다.

## R4 — 생성 계약과 폼 검증

- 결정: 생성 Zod로 DTO 형식을 검증하고 폼의 discriminated union으로 유형별 장소 조건을 검증한다.
- 근거: 생성 Zod는 null 허용 필드를 표현하지만 REGULAR·TEAM에 따른 필수 조건은 표현하지 않는다.
  현재 폼 스키마는 정규 세션의 주소·좌표를 검증한다.
- 대안: 생성 DTO를 앱 전용 입력 모델로 그대로 쓰거나 생성 SDK 전역 검증 설정을 바꾸지 않는다.

## R5 — 변경 완료와 재조회

- 결정: 확인된 저장 결과와 목록 갱신을 분리하고 Query signal로 이전 조회를 취소한다.
- 근거: 현재 Mutation은 `invalidateQueries()`를 반환해 완료 시점이 재조회와 묶인다. 생성은 ID,
  수정은 204이므로 완성된 서버 항목을 만들 수 없다. 생성 client의 HTTP retry 기본값도 2다.
- 대안: 낙관적 생성·수정, 실패 시 무조건 재저장은 사용하지 않는다. 기본 online 모드의 오프라인 요청 대기는 라이브러리 기본 동작으로 유지한다.

## R6 — 삭제와 화면 수명

- 결정: 시작 상태를 보존해 삭제를 제한하고 409에서는 서버 판정을 따른다. 404는 성공으로 표시하지 않는다.
- 근거: 카드에는 현재 수정만 있고 삭제는 메모리 서비스만 존재한다. 삭제 API는 출석 시작 전 논리 삭제다.
  overlay unmount만으로 이미 실행된 비동기 함수의 탐색·알림은 취소되지 않는다.
- 대안: 집계가 0이면 삭제 가능하다고 추정하거나 pathname 변경 뒤 완료 콜백을 무조건 실행하지 않는다.

## 참고한 가이드

계획 대화에서 `modern-web-guidance@1.0.0`으로 `submit form validation`을 검색하고 `forms`를
조회했다. 제출 후 중복 요청 방지·입력 오류 연결을 참고했다. 이번 단계는 문서만 작성하며,
제품 코드 작업 전에는 해당 단계의 폼·확인 대화상자 가이드를 다시 확인한다.

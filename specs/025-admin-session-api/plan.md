# 구현 계획: 어드민 세션 API 연결

**브랜치**: `DongjaJ/session-management-api-plan` | **작성일**: 2026-11-17
**명세**: [spec.md](spec.md) | **이슈**: [#462](https://github.com/YAPP-admin/yapp-plus-frontend/issues/462)
**상태**: 1단계 문서 작성 — 리뷰 대기. 2단계 이후는 미착수.

## 요약

`/sessions`의 목록·생성·수정과 새 삭제 UI를 생성 SDK로 연결한다. 출석 기능의 모의 서비스는
유지하고 세션 화면의 데이터 소유권만 분리한다. 이번 완료 범위는 SDK·MSW 검증이며 실제 기수
ID 확보와 실서버 쓰기 검증은 후속이다. 변경 성공과 목록 갱신 실패를 구분한다.

## 기술 맥락

- TypeScript·React 19, TanStack Router·Query·Form, Zod, SEED, overlay-kit, vanilla-extract를 유지한다.
- Node 24.20.0·pnpm 12.3.4와 catalog의 고정 버전을 사용한다. 새 패키지·의존성은 없다.
- 대상은 `apps/admin`의 브라우저 UI다. 브라우저 인증을 사용하므로 기존 ClientOnly 경계를 유지한다.
- Vitest·Testing Library·MSW로 검증한다. 캐시는 Query, 초안은 Form과 모달이 소유한다.
- 한 기수 전체 목록을 조회하고 기존 클라이언트 필터·정렬을 유지한다. 새 페이지네이션은 없다.
- 새 성능 수치는 만들지 않는다. HTTP 자동 재시도와 수동 비동기 상태 중복을 피한다.

## 문서와 코드 구조

문서는 이 디렉터리의 `spec.md`, `research.md`, `data-model.md`, `contracts/session-api.md`,
`quickstart.md`, `tasks.md`, `checklists/requirements.md`, `validation.md`로 구분한다.

```text
apps/admin/src/pages/sessions/
├── model/
│   ├── session-config.ts        # 기수 환경 설정 검증
│   ├── session-api.ts           # SDK 호출과 응답 검증
│   ├── session.ts               # 조회·입력 모델과 DTO 변환
│   ├── session-queries.ts       # 목록과 변경 후 캐시 갱신
│   ├── session-error.ts         # ApiError 본문 검증·화면 메시지
│   ├── session-form.ts          # 기존 폼 초안 변환 갱신
│   └── location/               # 기존 검색·좌표 기능 유지
└── ui/                         # 기존 UI 갱신, session-delete-dialog.tsx 추가
```

라우트는 설정을 읽어 `SessionsPage`에 `generationId`를 전달한다. 페이지 공개 진입점만
사용한다. `features/session-management`의 모의 목록·타입·Mutation 소비자를 일괄 교체하지 않는다.
기존 모의 서비스와 테스트는 출석 소비자가 남아 있는 동안 유지한다.

## 데이터 흐름과 인터페이스

- `VITE_ADMIN_GENERATION_ID`가 없으면 설정 안내만 표시한다.
- 테스트 기수 ID는 명시적으로 주입한다. 실제 환경에 임의 ID를 기본값으로 넣지 않는다.
- `find1Options`에 기수 ID·전체 유형을 전달하고 생성 key·signal을 재사용한다.
- 최초 조회는 Suspense 경계를 사용한다. 백그라운드 실패는 기존 data와 갱신 오류를 함께 표시한다.
- 저장 입력과 조회 모델을 분리한다. 변환·시간·ID 규칙은 [data-model.md](data-model.md)를 따른다.
- `create2`, `update1`, `delete1`은 기존 인증·ApiError 처리를 사용한다. 오류 본문은 생성 스키마로 검증한다.
- 변경 Mutation은 `retry: false`, HTTP 요청은 `retry: 0`을 명시한다. TanStack Query의 기본
  `online` 네트워크 모드를 유지해 오프라인에서는 요청을 시작하지 않는다. `networkMode`를 별도로 지정하지 않는다.
- 변경 성공 후 진행 중인 목록을 취소하고 무효화한다. 재조회 Promise를 저장 성공 판정과 묶지 않는다.
- 생성은 ID, 수정은 204만 받으므로 완성된 서버 항목을 만들어 넣지 않는다. 생성·수정의 갱신 실패에는
  이전 목록과 완료 안내를 유지한다. 최초 목록이 없으면 오류 경계와 별개로 완료 안내를 유지한다.
- 삭제 204 후에는 확인된 대상만 캐시에서 제거하고 네 개수를 갱신한 뒤 재조회한다.
- 지연 요청 완료 시 캐시 갱신은 수행하되 unmount된 화면의 탐색·알림은 실행하지 않는다.
  모달 unmount만으로 `mutate` 콜백이 취소된다고 가정하지 않는다.

## 구현 단계와 리뷰

| 단계 | 결과                          | 검증·리뷰 기준                                             |
| ---- | ----------------------------- | ---------------------------------------------------------- |
| 1    | 이슈·명세·계획·계약·작업 목록 | 문서 일관성·링크·품질 게이트, 제품 구현 전 리뷰            |
| 2    | 설정·조회/입력 모델·오류 변환 | 기수·입력 모델·집계 검증, UI 연결 없음                     |
| 3    | US1 목록 연결                 | SDK·인증·필터·빈/오류 상태, 모의 출석 분리                 |
| 4    | US2 공통 폼 준비              | 정규 주소·좌표·길이, 팀 null; 저장 UI는 아직 노출하지 않음 |
| 5    | US2 생성 연결                 | 201·중복 방지·전체 필터·저장/재조회 분리                   |
| 6    | US3 수정 연결                 | 204·필터 유지·제한 오류·지연 콜백                          |
| 7    | US4 삭제 연결                 | 확인·시작 상태·204/404/409·집계 갱신·포커스                |
| 8    | 통합 검증·운영 문서           | 전체 check/build·접근성·후속 실서버 절차                   |

4단계에서 폼 입력 계약을 바꿀 때 사용하지 않는 기존 모의 저장 모달 래퍼도 제거한다.
타입 검사 대상인 래퍼를 단순히 숨겨 두지 않는다. 실제 생성·수정 래퍼는 각각 5·6단계에 연결한다.
매 단계는 해당 테스트와 변경량을 보고한 뒤 리뷰를 기다린다. 미구현 저장 동작을 모의 서비스에
연결하거나 비활성 기능을 완성된 것처럼 노출하지 않는다. 상세 작업은 [tasks.md](tasks.md)를 따른다.

PR 1은 이 문서, 이후는 2~7단계의 독립적인 검토 단위를 기본으로 분리하고 8단계 보완은 별도로
검토한다. 단계 종료가 자동 commit·push·PR 생성 승인은 아니다. 실제 base 대비 650줄부터
분리를 점검하고 모든 파일을 포함해 800줄 미만으로 유지한다. 숫자를 맞추기 위한 파일 제외는 없다.

## 검증과 복구

[quickstart.md](quickstart.md)의 자동·브라우저·실서버 검증을 구분한다. 생성·수정·삭제 오류와
[기존 경합 이슈 #152](https://github.com/YAPP-admin/yapp-plus-frontend/issues/152)는 가까운 계층에서
한 번씩 상세 검증하고 라우트에는 대표 연결 사례만 둔다. 관련 이슈를 이번 문서 작성으로 해결 처리하지 않는다.

이번 변경에는 서버 마이그레이션이 없다. 연결 중단 시 기수 설정을 제거하고 재빌드해 요청을 차단한다.
코드 복구는 검증된 이전 버전으로 수행하되 기존 예시 화면으로 돌아가는 한계를 알린다.
이미 저장·논리 삭제된 서버 데이터는 프론트 롤백으로 복원되지 않는다. 실서버 테스트 데이터의
정리는 별도 승인한 대상·범위로만 수행한다.

# 구현 계획: 회원 코드 출석과 사전 출결 보고

**실제 브랜치**: `DongjaJ/wh3c0` | **갱신일**: 2026-11-17 | **명세**: [spec.md](spec.md)
**상태**: 사전 보고 1단계 문서 리뷰 대기 · [#385](https://github.com/YAPP-admin/yapp-plus-frontend/issues/385)

## 요약

기존 코드 출석 구현을 유지하고 홈·Stackflow 시트·네이티브 인증·생성 API로 사전 보고를 연결한다.
사유 필수·세션 시작 전 마감을 웹에 적용한다. 제출 직전 주간 재조회는 하지 않으며 `mutate`를 사용한다.

## 기술 맥락

- 대상: `apps/web`의 iOS WebView, 개발 MSW 브라우저. TypeScript·React·TanStack Query·SEED·Stackflow·Vitest를 유지한다.
- 생성 클라이언트의 `verify`, `submit1`, 생성 스키마와 `useNativeAuthSession().apiOptions`를 사용한다. 서버·브리지 계약은 수정하지 않는다. mutation key는 생성 설정의 `mutationKeys: true`로 생성한다.
- 저장: 서버만 영구 저장한다. 출석 완료 표시는 계정·세션별 메모리 상태로 관리한다. 새로운 의존성은 없다.
- 제출은 사용자 동작에서 한 번 실행한다. mutation 재시도·오프라인 대기 재생을 끄고 요청 중 버튼을 잠근다.

## 기존 코드 출석 구조 — 이번 변경 대상 아님

- 홈 전용 입력·요청·응답 검증은 `apps/web/src/pages/home/model`과 `ui`에 둔다. 다른 페이지 슬라이스를 직접 import하지 않는다.
- `CurrentWeekCard`의 서버 `attendanceStatus`로 버튼·안내를 구분한다. `AVAILABLE`만 진입 가능하다. 존재하는 현재 주 query를 재사용한다.
- 코드 출석 Activity의 운영 인증 연결과 다른 기능의 현재 동작은 유지한다.
- 제출 시 현재 조회된 세션 ID를 요청 변수로 전달한다. 제출 전 GET을 반복하지 않으며 세션 존재·출석 가능 여부의 최종 판정은 POST의 404·409 응답에 맡긴다. 진입 시점의 ID를 state에 고정하지 않는다. URL에 코드·토큰·사유를 추가하지 않는다.
- 입력 네 자리를 문자열로 검증한 뒤 숫자로 변환한다. `0000`을 임의로 거절하지 않는다. 성공은 `verified=true`와 유효한 시각을 확인해야 한다.
- 생성된 `verifyMutation`의 성공 상태에서 제출한 세션 ID를 읽고 현재 주·내 출석 조회를 갱신한다. 점수나 횟수를 임의로 더하지 않는다. 조회 실패로 제출 성공을 취소하지 않는다.
- 401은 기존 GET 조회 복구 경로로 현재 주 정보를 다시 확인하도록 안내한다. POST를 자동 재전송하거나 공용 인증 client의 GET 전용 정책을 변경하지 않는다. 복구 후 사용자가 다시 제출한다.
- 성공 결과는 생성 mutation key로 구독하고 앱 수명 동안 보존한다. 계정 전환의 화면 초기화·캐시 정리는 공용 인증 계층에 맡기고 출석 전용 owner·assertOwner는 두지 않는다.
- 오류 문구는 확인된 오류 코드에 대응한다. 알 수 없는 응답·네트워크 실패는 결과 확인 불가로 안내하고 성공으로 간주하지 않는다.

## 사전 보고 구조와 동작

- `pages/home/model/attendance-report.ts`에 입력 검증, 마감 판단과 제출 훅을 둔다. 시연 파일의 보고 UI는 `ui/attendance-report-sheet.tsx`로 분리한다. 공유 store·추상화는 추가하지 않는다.
- 홈 버튼을 코드 출석 상태나 완료 여부와 연결하지 않는다. 보고 시트는 기존 `currentWeekQueryOptions`·Query 캐시로 세션명·날짜·시작 시각과 로딩·조회 실패·대상 없음·마감을 표시한다.
- 한국 시간으로 `현재 시각 < 세션 시작 시각`일 때만 세 유형을 제출한다. 진입·화면 복귀·주간 경계에서 조회를 갱신하고 시작 시각 타이머는 화면 수명에 맞춰 정리한다. 제출 시 현재 시각도 검사한다.
- 토요일 마감 뒤 다음 주 세션을 미리 선택하지 않는다. 일요일 00:00에 주간 조회를 갱신한다. 전체 일정 조회·새 API는 추가하지 않는다.
- 주간 데이터는 `useQuery` 또는 `useSuspenseQuery`로 구독한다. 제출 직전 요청·강제 refetch·토큰 재조회와 일정 변경 재확인 화면을 추가하지 않는다. 확보한 유효 데이터·입력·현재 시각을 검사한 뒤 POST한다. 캐시와 서버 사이의 일정 변경은 서버 오류·접수 결과로 처리한다.
- TanStack Form이 유형·사유·검증을 소유한다. 원문 UTF-16 길이는 30 이하이고 `trim()` 결과는 비어 있지 않아야 한다. 전송은 trim한 값이며, 카운터도 원문 UTF-16 기준으로 표시해 SEED의 grapheme 카운터와 섞지 않는다. surrogate pair를 중간에 자르지 않는다.
- 생성 `submit1Mutation`에 인증 옵션을 연결하고 `mutation.mutate({ body }, { onSuccess })`로 제출한다. 현재 화면은 응답 본문을 소비하지 않으므로 별도 `responseValidator`를 두지 않는다. `mutateAsync`·제출 핸들러의 await/try-catch·POST 자동 재시도·오프라인 예약은 사용하지 않는다.
- mutation `onSuccess`는 주간 조회 무효화, 제출 성공 콜백은 시트 닫기·스낵바, `mutation.error`는 오류 표시를 담당한다. 조회 실패로 성공을 취소하거나 출석·점수·횟수를 임의로 바꾸지 않는다.
- 보고 응답은 생성 SDK 타입으로 받고, 현재 화면이 응답 본문을 소비하지 않으므로 앱 측 응답 검증을 추가하지 않는다. 응답 `sessionId`의 별도 제약이나 예상 대상과의 비교를 추가하지 않는다. 접수 불확실 시에는 가능성을 안내한 후 수동 재제출을 허용한다.
- 유형 미선택 → 필수 한 줄 사유·카운터 → 완료 스낵바를 최신 Hand off에 맞춘다. [명세의 규정 안내](spec.md#보고-규정-안내)와 접수·감점 구분을 추가한다. 입력 오류는 제출 시 안내하고 수정 시 해제하며 한국어 조합 중 Enter가 제출하지 않게 한다.
- `AttendanceReport`의 타입에 내부 `step?: 'reason'`을 추가하고 기존 Signup의 `useStepFlow` 방식으로 이동한다. `/attendance/report` 경로·부모 홈 복원은 유지하고 step·유형·사유를 URL에 넣지 않는다. 직접 진입·새로고침은 첫 단계다.
- 사유 단계 뒤로가기는 입력을 유지한 첫 단계 복귀다. 첫 단계 뒤로가기·명시적 닫기는 초안을 폐기한다. 제출 중에는 입력·버튼·시트 닫기를 잠그며 비활성·제거된 화면과 다른 계정에 늦은 결과의 탐색·알림을 적용하지 않는다.
- 기존 계정 경계를 사용한다. 일반 브라우저의 실제 제출과 정적 콘텐츠 모드의 제출은 차단하고, DEV+MSW는 같은 코드 경로의 생성 핸들러로 검증한다.
- 오류별 복구는 [소비 계약](contracts/attendance.md)을 따른다. 대상 변경·충돌 오류 뒤의 복구 재조회와 제출 전 재조회 금지는 별개다.

## 사전 보고 단계와 복구

| 단계         | 작업·산출물                                      | 검증·리뷰 기준                                    |
| ------------ | ------------------------------------------------ | ------------------------------------------------- |
| 1. 문서      | 기존 명세·계획·작업·계약·검증 절차 갱신          | 인터뷰 정책 일치, 링크·형식·변경량, 문서 리뷰     |
| 2. 제출·마감 | 입력·시간 검증, mutate 제출 훅, 오류 변환, MSW   | 인접 회귀·check, 운영 버튼은 아직 활성화하지 않음 |
| 3. 화면·탐색 | Hand off UI, 운영 진입, step 뒤로가기, 성공 안내 | 대표 흐름·탐색·기존 출석 회귀, check/build        |
| 4. 통합 검증 | 브라우저 정상·실패·마감·접근성·모바일 크기 확인  | 화면 근거, 발견 문제 수정과 영향 검사, 최종 기록  |

각 단계 결과·변경량·새 실행/캐시·실패/미실행을 보고하고 사용자 리뷰·다음 단계 확인을 기다린다.
같은 파일을 순차 변경하므로 구현 단계를 병렬 진행하지 않는다. 650줄부터 목적별 분리를 검토하고
PR당 800줄 미만을 유지한다. 문서 단계를 제품 코드 단계와 별도 검토 단위로 둔다.
자동·브라우저 검증이 구현 완료 기준이고 실기기·실서버는 별도 기록한다. 실제 접수는 승인된
테스트 계정·세션에서만 확인하며 운영 출석을 시험 변경하지 않는다.

실패 시 해당 단계의 프런트 연결을 되돌리고 기존 준비 중 상태로 복구한다. DB migration은 없으며 이미 접수된 출석·보고를 롤백 목적으로 삭제하지 않는다.

## 기존 코드 출석의 승인된 구조 수정과 보류한 제안

- 앱 인증은 상위 AccountScreen에 맡기고 시트는 일반 브라우저 실행만 제한한다. 현재 `currentWeekQueryOptions`·`useSuspenseQuery`의 로딩·실패·재시도 경계를 사용한다.
- TanStack Form의 `code` 필드가 네 칸 입력과 제출 후 수정 검증을 관리한다. 별도 코드 값·입력 오류 state는 제거한다.
- 생성 `verifyMutationKey`를 요청 식별 기준으로 그대로 사용한다. 기존 키를 생성 파일에 직접 추가하지 않는다.
- 승인된 단순화: 입력 Activity의 `mutation.isPending`으로 입력·확인·시트 닫기를 막고 제출은 mutate를 사용하며 Form은 검증 중 중복 제출을, mutation은 요청 중 잠금을 담당한다. `useIsMutating`·client.isMutating·닫힘 감시 Effect를 제거한다. 홈 완료 표시·완료 Activity 접근 차단·서버 오류별 복구 UI는 기존 방식을 유지하며 후속 결정한다.

# ID의 JSON 정밀도와 coercion (C08 · #171)

## 새로 실행한 검증

2026-10-29, `7898ee6`의 실제 `zStaffSummaryResponse.shape.id`에 JSON.parse 결과를
전달했다. 합성 ID만 사용했으며 백엔드 데이터는 읽거나 변경하지 않았다.

| JSON 원문          | JSON.parse 후 값 | Zod 결과          |
| ------------------ | ---------------- | ----------------- |
| 9007199254740991   | 9007199254740991 | 9007199254740991n |
| 9007199254740992   | 9007199254740992 | 9007199254740992n |
| 9007199254740993   | 9007199254740992 | 9007199254740992n |
| "9007199254740993" | 문자열 유지      | 9007199254740993n |
| true               | true             | 1n                |
| false              | false            | 0n                |

현재 생성 타입의 ID는 number이고 생성 Zod는 int64 범위를 가진 coerce.bigint다.
JSON 숫자의 정밀도가 파싱 전에 이미 손실되면 bigint로 바꿔도 복구되지 않는다.
문자열·boolean의 수용은 엄격한 wire 타입 검사와 다르다. 위 결과는 합성 경계 실험이며
현재 실제 ID가 안전 범위를 넘거나 사용자에게 잘못된 ID를 표시했다는 증거가 아니다.

근거: [생성 타입](../../packages/api/src/generated/types.gen.ts),
[생성 Zod](../../packages/api/src/generated/zod.gen.ts),
[클라이언트 JSON 파싱](../../packages/api/src/generated/client/client.gen.ts).
기본 SDK validation은 꺼져 있으므로 이 coercion이 모든 호출에서 자동 적용되는 것도 아니다.

## 아직 결정하지 않은 계약

백엔드의 실제 ID 생성 범위·최대값·문자열 직렬화 허용 여부는 미확인이다. 원본 OpenAPI를
임의로 바꾸거나 bigint transformer를 켜서 문제를 해결했다고 하지 않는다. #198의 현재 명세
갱신과 별개로 upstream의 wire 계약 결정이 필요하다.

- ID가 안전 정수 범위로 제한된다면 원본에 정수 범위와 엄격한 타입을 명시하고, 범위 밖 숫자와
  문자열·boolean을 거부하는 경계를 정한다. 제한은 DB·발급 정책까지 보장되어야 한다.
- int64 전체를 써야 한다면 원본에서 십진 문자열 직렬화를 합의하고 응답뿐 아니라 path/query/body,
  캐시 키·폼·화면 표시까지 문자열을 보존하도록 설계한다. JSON bigint 직접 직렬화는 대안이 아니다.

확정 전 Spec Kit으로 영향받는 앱·공용 타입·복구 계획을 작성한다. 확정 후 원본에서 재생성하고
안전 정수 경계·최대 int64·음수·빈 문자열·소수·boolean·null 및 요청/응답 왕복을 검증한다.
정책 변경의 롤백은 이전 원본·생성 설정·소비자 코드를 함께 되돌리는 방식으로 계획한다.

지속 테스트는 실제 소비자 통합 경계에서 추가하며 SDK 테스트 예외를 #158–161 밖으로 넓히지 않는다.
이번 PR은 재현·결정 자료이며 실제 범위 합의와 wire 변경 검증이 끝나기 전 #171을 닫지 않는다.

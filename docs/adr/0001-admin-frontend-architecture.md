# ADR 0001: 어드민 프런트엔드 아키텍처 원칙

- 상태: 승인
- 결정일: 2026-09-11
- 관련 이슈: [#22](https://github.com/YAPP-admin/yapp-plus-frontend/issues/22)

## 배경

어드민은 현재 초기 골격만 존재하며 구체적인 업무 화면 요구사항은 정해지지 않았다. 요구사항보다
앞서 범용 CRUD 생성기나 동적 폼 엔진을 만들면 실제 사용되지 않는 추상화와 의존성이 생길 수 있다.

반면 목록의 필터, 정렬과 페이지 상태처럼 대부분의 어드민 화면에서 필요한 상태 관리 원칙은 미리
정해 두는 편이 구현 간 일관성을 높이고 같은 기술 선택을 반복해서 논의하는 비용을 줄인다.

## 결정

### TanStack 기반 구성

어드민의 기본 기술은 다음과 같이 구성한다.

- 라우팅과 URL 상태: TanStack Start와 TanStack Router
- 서버 상태와 mutation: TanStack Query
- 목록 상태와 렌더링: TanStack Table
- 폼 상태와 제출: TanStack Form
- 런타임 검증과 타입 추론: Zod 4

각 라이브러리는 실제 업무 화면에서 필요해질 때 직접 의존성으로 추가한다. 사용처가 없는 패키지나
공통 추상화는 미리 추가하지 않는다.

### 목록 상태

북마크, 새 탭 열기, 새로고침과 공유에서 보존되어야 하는 목록 상태는 TanStack Router의 search
params에 저장한다.

- URL에 저장하는 상태: 검색어, 필터, 정렬, `page`, `pageSize`
- 기본적으로 로컬에 두는 상태: 행 선택, 펼친 행, 모달 표시 여부, hover와 컬럼 크기

search params는 라우트의 `validateSearch`에서 Zod 4로 검증하고 기본값을 적용한다. 검증된 값은 API
요청, TanStack Query의 `queryKey`, TanStack Table의 controlled state가 함께 사용한다. 서버가 목록
처리를 담당하면 Table의 페이지, 필터와 정렬 기능은 manual 모드로 구성한다.

URL에는 사람이 읽기 쉬운 1부터 시작하는 `page`를 사용하고, 필요한 경우 Table의 0부터 시작하는
`pageIndex`로 경계에서 변환한다. 검색 조건이나 정렬이 변경되면 `page`를 1로 초기화한다.

### `nuqs`

`nuqs`는 현재 도입하지 않는다. TanStack Router가 search params의 파싱, 검증, 타입 추론과 탐색을
이미 제공하므로 같은 URL 상태를 두 계층에서 관리하지 않는다.

결정 시점에 `nuqs`의 TanStack Router adapter는 실험적이며 TanStack Start를 지원하지 않는다.
지원 상태는 [`nuqs` adapter 문서](https://nuqs.dev/docs/adapters)에서 다시 확인할 수 있다.

### 폼

첫 업무 폼부터 TanStack Form의 `createFormHook`을 사용해 어드민 전용 필드 컴포넌트를 바인딩한다.
폼의 데이터 계약과 검증에는 Zod 4를 사용하고, Standard Schema를 지원하는 TanStack Form에 Zod
스키마를 직접 전달한다.

폼은 우선 타입이 있는 React 코드로 명시적으로 작성한다. 필드 컴포넌트와 제출 동작은 실제 폼에서
반복이 확인된 뒤 공통화한다.

### JSON/YAML 동적 폼

JSON이나 YAML 스펙으로 화면을 생성하는 동적 폼 엔진은 현재 도입하지 않는다. 요구사항이 정해지지
않은 상태에서는 스펙 버전, 조건부 필드, 권한, API 연결, 오류 처리와 마이그레이션 정책을 올바르게
설계할 근거가 부족하다.

label이나 select option처럼 단순한 화면 메타데이터가 필요하면 먼저 타입이 있는 TypeScript 설정을
사용한다. 런타임 JSON/YAML 스펙은 아래 재검토 조건이 충족될 때 별도 결정으로 다룬다.

## 영향

### 기대 효과

- 라우트에서 검증한 URL 상태를 목록 조회와 렌더링의 단일 진실 공급원으로 사용할 수 있다.
- TanStack 계열 라이브러리의 headless 구성을 이용하면서 마크업과 디자인을 직접 통제할 수 있다.
- 정적 폼은 Zod와 TypeScript의 타입 추론을 유지한다.
- 실제 반복이 확인되기 전까지 동적 폼과 범용 CRUD 엔진의 복잡성을 부담하지 않는다.

### 감수하는 비용

- 초기 폼과 테이블은 화면별로 명시적인 연결 코드를 작성해야 한다.
- URL 상태 변경은 TanStack Router의 탐색 API를 통해 처리해야 한다.
- 동적 폼이 필요한 요구가 생기면 직렬화 가능한 스키마와 런타임 검증 방식을 별도로 설계해야 한다.

## 재검토 조건

다음 조건 중 하나가 실제 요구사항으로 확인되면 이 결정을 다시 검토한다.

- 개발자 배포 없이 운영자가 폼 필드나 검증 규칙을 변경해야 한다.
- 고객이나 조직별로 서로 다른 필드 구성이 필요하다.
- 구조가 유사한 CRUD 폼이 반복되어 명시적인 구현 비용이 지속해서 커진다.
- 백엔드가 폼 계약을 생성하고 둘 이상의 클라이언트가 이를 소비한다.
- TanStack Start에서 `nuqs`가 안정적으로 지원되고 Router 기본 기능으로 해결하기 어려운 공통 URL
  상태 요구가 생긴다.

재검토 전까지는 실제 업무 화면을 세로로 완성한 뒤 확인된 반복만 추출한다.

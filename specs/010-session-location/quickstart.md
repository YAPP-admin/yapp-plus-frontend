# 실행·검증 가이드

## 현재 상태

1-4는 문서 작성 단계다. 아래 장소 기능 실행 절차는 구현 후 사용할 가이드이며 지금 동작한다고 의미하지 않는다.
현재까지 설치된 것은 기존 lockfile의 의존성뿐이다. 실제 키 발급·지도/좌표 라이브러리 추가는 후속 단계다.

## 환경 준비

저장소 루트에서 실행한다.

```sh
mise exec -- node --version
mise exec -- pnpm --version
mise exec -- pnpm install --frozen-lockfile
mise exec -- node --run check
```

Node.js 24.20.0·pnpm 12.3.4인지 확인한다. 로컬 셸에 mise가 활성화되어 있으면 `mise exec --`는 생략 가능하다.

## 2단계 키 준비 순서

1. 2-1: 기존 조직 소유 앱·승인키·담당자·허용 도메인을 확인한다. 키 자체를 보고서에 적지 않는다.
2. 2-2: [주소 API 신청](https://business.juso.go.kr/jst/jstAddressApiApplicationWrite?uniqKey=cntcInfoApi)에서 개발용 키 신청 조건·유효기간을 확인한다. 90일을 초기 계획으로 잡되 발급 화면의 실제 옵션을 따른다.
3. 2-3: [좌표 API 신청](https://business.juso.go.kr/jst/jstAddressApiApplicationWrite?uniqKey=cntcInfoCoordApi)에서 운영용 신청·본인 확인·사용 목적을 준비한다. 주소 키와 별개이며 발급 시간을 보장하지 않는다.
4. 2-4: 카카오 앱의 Maps 사용 설정과 JavaScript 키·웹 도메인 `http://localhost:3001`을 확인한다. 유료 결제나 앱 소유권 변경은 별도 승인 없이 하지 않는다.
5. 2-5: `apps/admin/.env.local`에 계약 문서의 세 변수를 설정하고 `.env.example`에는 빈 값만 기록한다. 주소→좌표의 실제 호출·JSON 응답 형식·현재 오류 응답과 카카오 도메인 허용을 확인한다.

각 번호는 별도 리뷰 단계다. 신청 과정에서 본인 확인이 필요하면 사용자가 직접 수행한다.

```sh
mise exec -- pnpm --filter @yapp-plus/admin dev
```

개발 화면에서 주소 검색·페이지 이동·좌표 조회·마커 조정 후 생성한다. 화면 이동 후 값 유지와 새로고침 초기화를 확인한다.
수정 시 조정 좌표가 복원되는지, 팀 안내를 비워도 저장되는지 확인한다.
LP-01~~11, ST-01~~15를 순서대로 검증하고 실제 키 테스트와 모의 테스트 결과를 분리 기록한다.
실제 키·네트워크가 없으면 외부 연동 검증은 미완료로 남긴다.

```sh
mise exec -- node --run dev:admin
```

새 워크스페이스도 위 공통 경로 아래에 있으면 인증을 상속한다. 다른 경로의 clone이나 팀원 PC에서는 로그인해야 한다.
다른 워크스페이스에 별도 토큰 설정이 있으면 해당 인증이 우선하며 이번 작업에서 다른 워크스페이스 설정은 바꾸지 않았다.

프로세스에 주소 검색 키·카카오 JavaScript 키가 존재함을 값 출력 없이 확인했다.

환경 변수 관리 방식은 앞선 `.env.local` 직접 입력 안내 대신 Doppler 주입을 사용한다.
변수 변경 후에는 개발 서버를 다시 실행한다. 회원용 앱 스크립트와 Vercel 동기화·배포 설정은 이번 연결에서 변경하지 않았다.

## 3-2 검증 결과 — 리뷰 대기

기존 JSONP·iframe 구현을 `address-request.ts`의 fetch 기반 JSON 요청으로 교체했다.
일반 JSON endpoint를 실제 승인키로 호출하여 HTTP 200, application/json, 오류 코드 0,
검색 결과 10개와 `Access-Control-Allow-Origin: *`를 확인했다.
10초 타임아웃·호출자 취소·동시 요청·본문 읽기 중 취소·HTTP 오류·잘못된 JSON·네트워크 오류·
파라미터 인코딩·SSR 차단·리소스 정리를 단위 테스트로 검증한다.
기존 `.context/session-location-step-3-2.png`는 폐기한 JSONP 구현의 증거이며 현재 구현의 검증 자료가 아니다.
좌표 API·제품 검색 UI·SDK 재시도는 이번 검증 범위에 포함하지 않는다.

교체 후 `node --run check`와 `node --run build`가 통과했다. 전송 단위 테스트 10개가 통과했다.
구현 소스의 TypeScript를 제거하고 SSR=false로 치환한 Node 실행에서 실제 승인키로 1·2페이지를
동시에 조회하여 각각 오류 코드 0과 결과 10개를 확인했다. 교체 후 브라우저 실행은 아직 확인하지 않았다.
제품 화면 변경은 없으며 3-3 ViewModel 변환은 사용자 리뷰 후 진행한다.

### 3-2 ky 전용 인스턴스 적용

행안부 요청은 `juso-client.ts`의 독립적인 ky 인스턴스를 사용한다.
admin에 ky 직접 의존성을 선언하고 기존 packages/api와 버전 2.1.0을 catalog에서 공유한다.

### 3-5 리뷰 반영: TanStack Query 사용

`AddressSearch`의 SearchState·요청 try/catch·pending ref를 제거하고 `useQuery`로 요청 상태를 관리한다.
입력 초안과 제출 검색어·페이지는 로컬 상태로 유지한다. 같은 조건의 명시적 검색과 재시도는 refetch를 사용한다.
Query key에는 검색 조건만 포함하고 승인키를 넣지 않는다. 미사용 캐시는 gcTime 0으로 정리한다.
자동 재시도·포커스·재연결·마운트 재조회는 끄고, 재조회 중과 실패 후에는 이전 결과를 숨긴다.
업무 실패는 기존 응답 계약에 따라 안내하고, 전송 실패는 Query error에서 안전한 문구로 변환한다.

### 3-5 리뷰 반영: 조회 옵션과 정책 분리

승인키 접근과 queryOptions를 `address-search-query.ts`로, 오류 안내를 `address-search-error.ts`의 순수 함수로 옮겼다.
UI는 승인키 값을 다루지 않고 검색 가능 여부만 확인한다. 오류 안내는 const로 계산한다.
재시도·포커스·재연결·마운트 자동 재조회는 QueryClient 생성자의 공통 기본값으로 끈다. 주소·좌표의 staleTime과 gcTime은 각 queryOptions에서 관리한다.
검색어와 페이지를 Query key에 포함하고, 같은 조건의 재조회까지 표시하도록 isFetching을 유지한다.
입력 즉시 검색으로의 전환 여부는 사용자 확인 중이며 기존 버튼·Enter 검색 조건 분리는 유지한다.

### 3-5 확정: 입력 즉시 자동 검색

# 구현 계획: 회원 홈 출석 상태와 팀 사진 출석 연결

브랜치: `DongjaJ/wojt9` · 작성일: 2026-11-20 · [명세](spec.md) · [이슈 #501](https://github.com/YAPP-admin/yapp-plus-frontend/issues/501)

## 요약

현재 주간 API의 다섯 출석 상태를 홈의 기준으로 삼는다. 홈·정규 코드 출석을 먼저 연결하고,
회원용 팀 조회 계약이 준비된 뒤 기존 팀 사진 제출 기능을 운영에 연결한다.
1단계는 문서만 작성한다. 각 단계 종료 후 사용자 리뷰와 다음 단계 확인이 필요하다.

## 기술 맥락

- 언어·도구: TypeScript 6.0.3, Node.js 24.20.0, pnpm 12.3.4.
- 기반: React 19.3.0, Vite, Stackflow, SEED, TanStack Query, Zod. 새 의존성·전역 저장소는 추가하지 않는다.
- 대상: `apps/web` 회원 화면과 `apps/web/stackflow` 내비게이션, 모바일 WebView.
- 저장: 기존 Query 캐시·화면 내 메모리만 사용한다. 사진·접수 정보를 영구 저장하지 않는다.
- 검증: 기존 Vitest·Testing Library·MSW, 관련 Storybook, 실제 WebView 복귀·네이티브 사진 선택.
- 성능: 상시 폴링 없이 진입·복귀·변경 완료 시 조회한다. 기존 사진 제한을 유지한다.
- 범위: 홈 출석 카드, 정규 출석 상태 연결, 팀 안내·사진 제출·접수 완료. 서버·관리자 앱 구현은 없다.

## 헌법 점검

기준: 시작 시 최신 `origin/main`과 동일한 `cc90b35e`; 작업 트리는 깨끗했다.
[AGENTS.md](../../AGENTS.md), [헌법](../../.specify/memory/constitution.md), 제품·프론트엔드·회원 앱 가이드를 기준으로 조사·설계를 점검했다.

| 항목               | 설계 결과와 구현 시 조건                                                              |
| ------------------ | ------------------------------------------------------------------------------------- |
| 제품·최소 범위     | 적용. 제외 기능을 명세에 고정하고 기존 화면을 재사용한다.                             |
| 앱·공용 계약 경계  | 적용. 앱 간 import 없음. API·브리지는 공개 계약을 사용하고 생성 파일 직접 수정 금지.  |
| 도구·의존성        | 적용. 고정 Node·pnpm, 새 의존성 없음. UI 작성 전 Modern Web Guidance 1.0.0 검색·조회. |
| 검증               | 적용. 상태 변환·흐름 회귀를 가까운 계층에서 검증하고 캐시와 실제 실행을 구분한다.     |
| 검토·복구          | 적용. 단계별 리뷰, PR 800줄 미만·650줄부터 분리 검토, 팀 진입 비활성화로 복구.        |
| 외부 계약 준비     | 3단계 확인 필요. 회원용 조회 계약이 없어 운영 연결을 시작할 수 없다.                  |
| 네이티브 계약 변경 | 현재 해당 없음. WebView 복귀 이벤트가 부족하면 별도 설계·리뷰 후 범위를 결정한다.     |

설계상 규칙 예외는 없다. 문서 검토 통과가 3단계 외부 계약 준비 완료를 의미하지 않는다.

## 대상 구조

- `apps/web/src/pages/home/model/`: 주간 응답 검증, 홈 상태 정책, 정규 출석.
- `apps/web/src/pages/home/ui/`: 홈 카드, 코드 화면, 팀 안내.
- `apps/web/src/shared/lib/screen-activity.ts`: 기존 복귀 훅에 홈 전용 항상 재조회 정책을 제공한다.
- `apps/web/src/pages/team-attendance-upload/`, `team-attendance-complete/`: 사진·선택·접수 UI.
- `apps/web/src/features/team-attendance/`: 제출 대상 검증, 기존 업로드·제출 흐름.
- `apps/web/stackflow/src/`: 홈 진입 경로, 팀 흐름의 상태 수명·라우트 연결.
- `packages/api/`: 계약 변경이 도착한 경우에만 원본 갱신·재생성한다.
- `specs/027-home-attendance-flow/`: 명세, 계획, 조사, 데이터 모델, 계약, 검증 가이드, 작업 목록.

## 단계별 전달

### 1단계 — 명세·계획·작업 목록 (이번 범위)

이슈를 생성하고 상태 표, 제외 범위, 외부 선행 조건, 실패 복구, 검증 항목을 문서화한다.
기존 명세의 후속 변경 위치를 연결한다. 문서 정합성·형식·변경량을 검사하고 리뷰를 요청한다.

### 2단계 — 홈과 정규 출석 (US1 → US2)

1. `current-week-schema.ts`의 기존 생성 enum을 유지하고 홈 상태 정책을 작은 순수 함수로 분리한다.
2. 장소 `null` 판별, 다섯 상태, 세션 없음, 조회 중·실패·오프라인 대기, 팀 준비 중 상태를 적용한다.
3. 홈·코드 진입에서 과거 성공 이력의 상태 덮어쓰기를 제거한다. 완료 화면 방어·현재 제출 중복 방지는 유지한다.
4. 홈 재진입은 항상 재조회한다. 공용 복귀 훅의 다른 사용자는 기존 동작을 유지한다.
5. 앱 포그라운드 복귀를 실제 WebView에서 확인한다. 단위 테스트의 `focusManager` 조작만으로 실기기 성공을 주장하지 않는다.
6. MSW·상태 테스트·화면 테스트·기존 출석 회귀·접근성·품질 게이트·빌드를 확인한다.

완료 제출: 상태별 동작, 정규 출석 성공→완료→홈 흐름, 실제/캐시 검증 결과, 화면 증거.
이 단계에서 팀 운영 진입은 준비 중으로 남는다. 사용자 리뷰 전 3단계를 시작하지 않는다.

### 3단계 — 회원용 계약 확인과 팀 운영 연결 (US3)

1. [계약 확인표](contracts/attendance-flow.md)의 조회 경로·권한·멤버십 ID·누락·오류 정책을 실제 OpenAPI와 대조한다.
2. 응답이 요구와 다르거나 의미가 불명확하면 사용자에게 구체적인 선택지를 질문하고 답변을 계약에 반영한다.
3. 생성 API와 Zod 검증으로 실대상을 연결한다. 조회 실패·불일치 때 선택기·제출을 열지 않는다.
4. 안내·사진·완료를 같은 흐름 수명으로 묶고 기존 URL을 보존한다. 안내의 선택 소스를 네이티브 선택기로 전달한다.
5. 선택 취소·교체·팀원 선택·제출·홈 재조회·흐름 이탈 정리를 연결하고 개발용 대상의 운영 사용을 제거한다.
6. 일반 시간 안내를 사용한다. `type`·`endTime` 도착 시 실제 계약에 따라 별도 검토 가능한 변경으로 전환한다.

완료 제출: 운영 대상 계약 근거, 네이티브 사진 흐름, 접수/홈 상태, 오류·취소·직접 진입 증거.
API가 없으면 3단계는 보류하고 2단계 결과를 독립적으로 전달한다.

### 4단계 — 통합 회귀와 출시 검토

각 단계에서 수행한 검증을 중복 반복하지 않고 전체 연결로 새로 생긴 위험을 확인한다.
계정 전환·주차 변경·앱 복귀·제출 결과 불확실·접근성을 확인하고 품질 게이트·빌드 결과를 정리한다.
실제 base 대비 650줄부터 분리하고 모든 PR은 800줄 미만을 유지한다. 분리한 단위마다 리뷰받는다.

## 복구와 후속 전환

홈 오류는 이전 표시를 유지하되 출석 진입을 잠그고 재시도한다. 팀 운영 연결 문제는 홈 진입을
준비 중으로 되돌린다. 접수된 사진을 삭제하거나 제출을 자동 재전송하는 복구는 하지 않는다.
생성 계약 변경은 소비 코드와 함께 되돌릴 수 있게 분리한다. API 서버 배포·데이터 변경은 범위 밖이다.
`session.type` 도입 시 임시 판별 함수와 테스트를 교체하고, `endTime`은 검증된 KST 안내에만 사용한다.

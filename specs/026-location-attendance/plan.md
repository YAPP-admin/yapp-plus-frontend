# 구현 계획: 위치 기반 코드 출석

**브랜치**: `DongjaJ/akax9-stage3` · **작성일**: 2026-11-18 · **명세**: [spec.md](./spec.md)
**상태**: 4단계 오류 복구 화면 구현·검증 완료, 사용자 리뷰 대기. 기준 이슈는
[GitHub #478](https://github.com/YAPP-admin/yapp-plus-frontend/issues/478)이며 통합·실기기 검증은 아직 진행하지 않았다.

## 요약

기존 위치 브리지에서 단발 표본을 받아 회원 웹에서 측정 품질·거리를 검사한 후 기존 출석 SDK를 호출한다.
`geolib.getPreciseDistance(current, target, 0)`을 사용하고 네이티브·브리지·서버 계약은 변경하지 않는다.
공통 판정과 플랫폼별 검증은 [계약](./contracts/location-attendance.md)에 둔다.

## 기술 맥락

- 언어·환경: TypeScript 6, React 19, Vite 8, Stackflow, SEED, TanStack Query·Form, Zod.
- 도구: 저장소의 Node.js 24.20.0·pnpm 12.3.4를 `mise exec --`로 사용한다.
- 의존성: 웹에 `geolib@4.0.2`만 추가하고 pnpm catalog·lockfile로 고정한다. 네이티브 의존성은 그대로다.
- 저장: 위치를 저장하지 않는다. 기존 서버 성공 mutation의 계정별 메모리 수명은 유지한다.
- 검증: Vitest·Testing Library·MSW, Stackflow 통합 테스트, 브라우저와 iOS 실기기.
- 범위: 홈 코드 출석 한 흐름. Android는 동일 정책 전달·비교 기준만 작성하며 구현 완료로 간주하지 않는다.
- 성능·시간: 거리 계산은 로컬 동기 계산이다. 네이티브 측정 제한 15초와 최근 5초 표본 검사를 재사용한다.
  권한 선택 대기는 15초에 포함되지 않으며 브리지 통신 timeout 180초와도 구분한다.

## 단계와 검토 단위

### 1단계 — 요구사항·설계·이슈 초안

문서·작업 목록·체크리스트와 구조 검증 결과를 제출하고 리뷰받았다.
이슈 #478 생성과 2단계 진행을 확인했다.

### 2단계 — 판정 기반 (US1)

geolib를 고정하고 좌표·정밀 권한·오차·거리 판정 순수 함수를 구현한다.
조건 위반과 계산 실패를 구분한 결과만 반환한다. 원문 좌표·거리를 mutation 결과에 넣지 않는다.
고정 기준점과 경계·오류 단위 테스트를 작성하고 결과를 리뷰받는다. 이 단계에서는 제출에 연결하지 않는다.

### 3단계 — 제출과 요청 수명 (US1·US3)

유효한 사용자 제출에 대해 기존 mutation 실행 경로 안에서 위치 판정을 먼저 수행한다.
기존 verify mutation key·성공 context의 sessionId·캐시 무효화를 보존하고 원문 위치는 지역 변수로만 사용한다.
위치 확인과 서버 제출 mutation의 진행 상태를 조합하며 단계 안내는 위치 확인/출석 처리로 구분한다.
위치 확인 mutation은 시작 시점 세션 ID·좌표와 코드를 받아 승인된 서버 제출 입력을 반환한다.
계정 변경은 기존 account boundary의 화면 수명으로 중단하고, 최신 세션 Query를 별도로 다시 비교하지 않는다.
기존 BottomSheet open 상태는 제출 시작 기준으로 사용하고 별도의 Activity 수명 처리는 추가하지 않는다.
단순 화면 버튼 비활성만으로 중복을 막았다고 가정하지 않고 동기 연속 제출을 검증한다.

### 4단계 — 실패 안내와 설정 복구 (US2)

기존 헤더의 무조건 완료를 암시하는 문구를 교체하고 목적·100m 기준과 진행 상태를 알린다.
실패 사유별 수동 재시도·설정 열기·세션 재조회·운영진 문의를 연결한다.
설정 실행은 출석 성공 mutation과 분리하고 결과에 좌표를 넣지 않는다. 복귀 자동 제출은 없다.
위치 오류는 코드 입력의 aria-invalid와 구분하고 기존 코드 입력·서버 오류 동작을 보존한다.
화면·키보드·터치·보조기술 확인 후 리뷰받는다. 재사용 UI 패키지 동작은 변경하지 않는다.

### 5단계 — 통합·실기기·출시 준비

check·build와 브라우저 흐름을 검증한다. 위치 권한·실내 측정·실제 반경·설정·VoiceOver는 실기기로 구분한다.
실제 장소에서 반복 실패가 있으면 기준 완화 여부를 사용자에게 질문하며 미검증 항목을 완료로 표시하지 않는다.
Android 공통 사례는 별도 저장소에서 검증하고 전달·적용·검증 상태를 분리한다. 이 단계의 완료를 Android 완료로 확장하지 않는다.

## 출시·복구와 PR 분리

- 지원 앱의 위치 메서드 제공을 확인한다. iOS 선적용은 가능하며 Android와 다른 적용 기간을 명시한다.
- 기준 좌표 데이터 보완이 필요한 세션은 운영진에 확인한다. 누락을 이유로 코드 출석을 허용하지 않는다.
- 장애 시 이전 검증 웹 커밋으로 복구한다. 위치 차단이 해제되는 영향까지 알리고 별도 배포 승인 후 수행한다.
- 문서/판정 기반/제출·화면·통합을 독립 검토 후보로 둔다. 누적 650줄부터 분리 검토, 실제 base 대비 800줄 미만을 지킨다.
- 단계 리뷰는 commit·push·PR·배포 승인을 대신하지 않는다. 중간 구현 단계만으로 출시 준비 완료를 선언하지 않는다.

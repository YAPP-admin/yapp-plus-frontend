# 검증 절차

## 준비

저장소 고정 mise 도구와 설치된 의존성을 사용한다. 코드 출석은 기존 회귀 범위이고 사전 보고는
[작업 목록](tasks.md)의 네 단계별로 검증한다. 실제 접수는 승인된 테스트 계정·세션에서만 확인한다.

## 자동 검증

1. 인접 Vitest 테스트에서 기존 MSW 응답을 재정의해 출석/보고 성공·실패와 지연 응답을 검증한다.
2. `mise exec -- node --run check`를 실행한다.
3. 배포 가능한 화면을 변경하는 3단계부터 `mise exec -- node --run build`도 실행한다.
4. `git diff --check`와 실제 PR base 대비 numstat을 확인한다. 새 실행과 Turbo 캐시 사용을 구분한다.

## 사용자 흐름

- 출석: 불가/오픈 전/가능 상태, 네 자리 붙여넣기·앞자리 0, 잘못된 코드, 정상 검증, 완료 후 홈 표시.
- 보고: 유형 미선택·세 유형, 빈 사유·공백 차단, 원문 UTF-16 30자·31자·이모지 경계, trim한 요청 본문, 대상 없음·변경·충돌·자격 없음.
- 공통: 중복 클릭, 오프라인 제출·복귀, 성공 응답 유실, 인증 만료 후 복구와 수동 제출, 제출 중 화면 이탈·계정 변경.
- 키보드 포커스·오류 안내·터치 키패드·VoiceOver·safe-area를 확인하고 실제 수행하지 못한 항목을 기록한다.

화면 녹화·스크린샷에는 실회원 이름·코드·사유·토큰을 노출하지 않는다. 자동 검증 성공을 실서버 출석 검증으로 보고하지 않는다.

## 사전 보고 수용 시나리오

| 계층 | 시나리오·기대 결과                                                                                            |
| ---- | ------------------------------------------------------------------------------------------------------------- |
| 모델 | 한국 시간 시작 1ms 전 허용, 정각·직후 차단. 결석 이틀 전 이후도 시작 전이면 허용                              |
| 모델 | 토요일 시작 후·종료 후 모두 해당 주 마감, 일요일 00:00부터 새 주간 조회. 유효 대상 없으면 POST 없음           |
| 요청 | 유효한 기존 Query 데이터를 준비하고 제출. 제출 직전 추가 GET 없이 `{type, reason}` POST 한 번, sessionId 없음 |
| 요청 | 기존 출석 상태 NOT_OPEN이어도 시작 전이면 보고 가능. 세션 ID·일정이 바뀌면 추가 사전 조회 없이 서버 응답 처리 |
| 요청 | 400·401·403·404·409를 계약 표에 맞게 처리. 대상 변경·충돌 오류 뒤 복구 재조회와 수동 제출은 허용              |
| 요청 | 응답 유실·잘못된 응답 형식·시각은 완료 표시 없음. 재제출 의미를 안내한 뒤 수동 재제출                         |
| 화면 | 사유 단계 뒤로가기 시 입력 유지, 닫기·재진입·새로고침 시 초기화. URL에 입력·내부 step 없음                    |
| 화면 | 작성 중 마감·주간 변경은 자동 제출 없음. 조회 실패·마감·제출 중 상태와 중복 클릭 차단                         |
| 탐색 | 홈 → 선택 → 사유 → 성공 → 홈 스낵바, 직접 URL의 부모 홈 복원. 숨김·이탈·계정 변경 뒤 늦은 탐색·알림 없음      |
| 회귀 | 코드 출석·팀 사진·일반 브라우저 인증·정적 모드 제한 유지, 보고만으로 출석·점수·횟수 변경 없음                 |

2단계에서는 모델·요청의 오류 조합을 검증하고, 3단계 화면·탐색에서는 대표 연결만 검증한다.
4단계는 DEV+MSW 브라우저에서 Hand off 대비 UI, 키보드·라디오·오류 접근성, 한국어 조합 중
Enter, 모바일 크기·키보드 겹침을 확인한다. 화면 근거는 `.context/`에 저장한다.
실제 VoiceOver·터치·safe-area·실서버 접수는 별도 실행/미실행으로 기록하며 구현 완료를 막는
필수 조건으로 취급하지 않는다. 실패 시 보고 진입을 준비 중으로 복원하고 서버 보고는 삭제하지 않는다.

# 실행·검증 안내

## 전제

작업 루트에서 고정된 mise·pnpm과 기존 의존성을 사용한다. 실서버 ID나 인증 정보를 문서·로그에
넣지 않는다. 로그인 응답과 현재 어드민 API에는 접근 가능한 기수 ID 목록이 없으므로, 표시 기수
번호를 ID로 추정하지 않고 백엔드·운영 경로에서 실제 DB ID를 확인한다.

## 자동 검증

```sh
mise exec -- pnpm --filter @yapp-plus/admin test
mise exec -- node --run check
mise exec -- node --run build
```

모델·서비스·화면 테스트는 변경과 가장 가까운 계층에서 수행한다. 루트 check의 Turbo 캐시 사용과
별도로 실행한 테스트를 구분한다. 문서만 바뀐 1단계에서는 check와 문서 구조를 확인하며 build는 대상이 아니다.
미래 테스트 파일의 정확한 위치와 단계별 수용 기준은 [tasks.md](tasks.md)를 따른다.

## 개발 브라우저

1. 기존 Doppler `yapp-plus-admin`·`dev` 접근을 준비한다. 인증값을 출력하지 않는다.
2. MSW 확인은 `VITE_API_MOCKING=true`와 명시적인 테스트용 `VITE_ADMIN_GENERATION_ID`로 시작한다.
3. `mise exec -- node --run dev:admin`으로 실행하고 기수·MSW 설정 변경 시 재시작한다.
4. 일반 개발 MSW는 고정 응답이며 CRUD 저장을 보장하지 않는다. 성공 후 변경 목록은 자동 테스트에서
   요청별 응답 순서를 지정해 검증한다. 브라우저 고정 응답을 영속 저장 성공으로 보고하지 않는다.
5. 실제 연결은 모킹을 끄고 확인된 기수 DB ID를 넣는다. 표시 기수 번호를 ID로 추정하지 않는다.
6. 기수 설정이 없거나 숫자가 아니면 `/sessions`가 API를 호출하지 않고 설정 안내만 표시하는지 확인한다.

모델·요청 테스트에서 상세 오류 조합을 확인하고 화면에는 대표 연결만 둔다. UI 증거는 `.context/`에
저장하며 실제 회원·주소·토큰이 담기지 않은 합성 데이터로 캡처한다. 검증하지 않은 조작은 미실행으로 남긴다.

## 후속 실서버 확인·복구

실제 기수 ID와 현재 계약을 먼저 확인하고 별도로 승인한 테스트 세션으로 조회·생성·수정·삭제를
확인한다. 새로고침 후 데이터·좌표 유지, 출석 시작 이후 삭제 거부, 날짜 충돌을 점검한다.
이번 자동 검증 완료에 실서버 성공을 포함하지 않는다. 쓰기·삭제 대상과 정리 범위는 후속 승인에 따른다.
기수 환경 설정 제거 후 재빌드로 요청을 차단할 수 있다. 코드 롤백은 서버 데이터를 되돌리지 않는다.
삭제된 세션 복구나 기존 데이터 일괄 보정 기능은 이번 범위에 없으므로 서버 정리는 별도 운영 절차로
수행한다.

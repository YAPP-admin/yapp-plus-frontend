# 기능 명세: Seed Design 기반 웹 UI 전환

**작업 브랜치**: `feat/seed-design`  
**작성일**: 2026-09-28  
**상태**: 1~5단계 승인 완료. 6단계 구현 완료·리뷰 대기. 브라우저 통합 검증은 미완료

**연결 이슈**: [#28](https://github.com/YAPP-admin/yapp-plus-frontend/issues/28)

**요청**: 당근 공식 스킬을 설치하고 그 지침으로 공용 UI, web, admin, Storybook의 기존 UI를
전환한다. Seed 기본 브랜드 색상과 시스템 테마를 사용하며 각 단계 완료 후 사용자 리뷰를 받는다.

## 사용자 시나리오와 검증

### US1 — 공통 디자인을 사용하는 개발자 (우선순위: P1)

개발자는 공식 스킬과 공용 버튼을 사용해 일관된 상태 표현을 구현하고 재현할 수 있다.

**우선순위 이유**: 앱 전환의 기반이며 자체 버튼과 공식 디자인 사이의 중복을 없앤다.

**독립 검증**: 공용 버튼의 기본, 비활성, 로딩 상태를 테스트하고 공식 스니펫 호환성을 확인한다.

**인수 시나리오**:

1. 공식 스킬이 설치된 상태에서 설정을 진행하면 설치된 스킬과 공식 문서를 기준으로 작업한다.
2. 활성 버튼을 누르면 의도한 동작이 실행되고, 비활성 버튼을 누르면 실행되지 않는다.
3. 로딩 상태는 로딩 표시를 제공하며 비활성 상태와 별도로 제어할 수 있다.

### US2 — 일관된 화면을 사용하는 웹 사용자와 운영자 (우선순위: P1)

웹 사용자와 운영자는 기존 콘텐츠와 이동 경로를 유지하면서 Seed 기준으로 통일된 화면을 본다.

**우선순위 이유**: 디자인 전환이 기존 제품 사용을 방해하지 않아야 한다.

**독립 검증**: web과 admin 각각에서 기존 제목, 문구, 링크, 빈 상태와 모바일 화면을 확인한다.

**인수 시나리오**:

1. 웹 홈에 진입하면 제품명과 소개 문구, 화면 구성이 유지되고 Seed 기본 색상과 서체 규격을 본다.
2. 관리자가 대시보드에 진입하면 기존 메뉴와 빈 상태 안내를 그대로 사용할 수 있다.
3. WebView에서 화면을 열면 기존 안전 영역이 유지되고 콘텐츠가 화면 밖으로 넘치지 않는다.

### US3 — 기기 테마에 맞는 화면을 사용하는 사용자 (우선순위: P1)

사용자는 별도 설정 없이 기기의 라이트·다크 설정에 맞는 화면을 보고 실행 중 변경도 반영받는다.

**우선순위 이유**: 기본 색상 전환과 함께 사용자가 명시적으로 요청한 동작이다.

**독립 검증**: 각 실행 환경에서 라이트·다크 최초 진입과 양방향 시스템 테마 전환을 확인한다.

**인수 시나리오**:

1. 라이트 또는 다크 설정으로 처음 진입하면 해당 테마로 화면이 표시된다.
2. 페이지를 연 상태에서 기기 테마를 변경하면 새로고침 없이 배경과 텍스트가 함께 바뀐다.
3. 테마를 감지할 수 없는 환경에서는 라이트 화면으로 사용을 계속할 수 있다.

### US4 — 변경을 검토하고 유지하는 개발자 (우선순위: P2)

개발자는 컴포넌트 사례와 사용 문서로 설치 방법, 상태별 동작과 테마를 재현하고 검토할 수 있다.

**우선순위 이유**: 이후 화면 개발과 의존성 갱신에서 같은 설정을 반복 사용하기 위함이다.

**독립 검증**: Storybook에서 버튼 상태를 확인하고 사용 문서의 절차로 검증을 재현한다.

**인수 시나리오**:

1. 컴포넌트 문서를 열면 버튼 variant, 크기, 비활성, 로딩 상태를 비교할 수 있다.
2. Storybook preview의 컴포넌트는 기기 테마를 따르며 키보드와 터치로 버튼을 사용할 수 있다.
3. 각 작업 단계가 완료되면 사용자가 결과를 리뷰한 뒤 다음 단계 진행 여부를 결정한다.

### 경계 조건

- 시스템 테마 감지가 없거나 실패해도 초기 화면이 사라지거나 실행이 중단되지 않는다.
- 서버가 만든 초기 화면과 브라우저가 적용한 테마 차이로 화면 복구 오류가 발생하지 않는다.
- 로딩만 설정한 버튼은 자동으로 비활성화된 것으로 취급하지 않는다.
- 웹 안전 영역의 브리지 값이 없을 때 기존 브라우저 기본 처리 방식이 유지된다.
- 화면 스타일 전환 과정에서 의미 있는 제목, 랜드마크, 링크와 버튼 이름을 잃지 않는다.

## 요구사항

### 기능 요구사항

- **FR-001**: 공식 `seed-design` 스킬을 프로젝트에 설치하고 실제 설치본을 설정 작업에 사용한다.
- **FR-002**: 공용 버튼의 기본·비활성·로딩 상태를 Seed 기준으로 제공한다.
- **FR-003**: 기존 web·admin 화면과 Storybook을 Seed의 기본 브랜드 색상 및 디자인 토큰으로 전환한다.
- **FR-004**: 기존 화면 구성, 콘텐츠, 라우팅, 기능과 WebView 안전 영역을 유지한다.
- **FR-005**: 모든 대상 화면은 최초 진입과 실행 중 시스템 테마 변경을 반영한다.
- **FR-006**: 테마를 감지할 수 없으면 라이트를 기본으로 표시한다.
- **FR-007**: 키보드, 스크린 리더와 터치로 기존 조작을 계속 수행할 수 있다.
- **FR-008**: 컴포넌트 사례와 설치·추가·검증 절차를 제공한다.
- **FR-009**: 단계별 결과를 사용자에게 보고하고 승인 전에는 다음 단계 작업을 시작하지 않는다.

## 성공 기준

- **SC-001**: web·admin·Storybook 세 환경 모두에서 기존 자체 색상 대신 Seed 기준 화면을 확인한다.
- **SC-002**: 세 환경에서 라이트·다크 최초 진입과 양방향 전환의 네 시나리오가 모두 통과한다.
- **SC-003**: 기존 문구·이동 경로·빈 상태·안전 영역의 회귀가 없고 390px·1280px 너비에서 가로 넘침이 없다.
- **SC-004**: 버튼의 활성·비활성·로딩 동작과 접근 가능한 이름을 검증하고 키보드·터치 조작을 유지한다.
- **SC-005**: 새 개발자가 저장소 문서만으로 공용 버튼 사례와 테마 검증을 재현할 수 있다.

## 가정과 제외 범위

- 적용 대상은 공용 웹 UI, web, admin, Storybook이다. Expo 네이티브의 설정·의존성은 제외한다.
- 기존 초록색을 보존하는 브랜드 재정의와 별도 테마 선택 UI는 추가하지 않는다.
- 화면 재설계, 새 화면, 새 폰트 배포, 인증·API·배포 정책 변경은 포함하지 않는다.
- Storybook 테마 적용 대상은 컴포넌트 preview이며 관리 화면의 테마는 변경하지 않는다.
- 검증을 위해 가상의 저장 기능이나 비동기 업무 흐름을 추가하지 않는다. 버튼 테스트는 사용자 조작과 공용 계약에 한정한다.
- 저장소 내부 소비자를 함께 이전하며 예전 버튼 API를 위한 호환 래퍼는 만들지 않는다.
- 단계별 리뷰는 로컬 변경 검토이며 commit·push·PR·배포 승인을 포함하지 않는다.

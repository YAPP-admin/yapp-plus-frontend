# 기능 명세: OpenAPI 클라이언트와 MSW 개발 환경

**브랜치**: `DongjaJ/api-docs-implementation-check`
**작성일**: 2026-10-26
**이슈**: [#107](https://github.com/YAPP-admin/yapp-plus-frontend/issues/107)
**상태**: 1~8단계 완료 — 최종 사용자 리뷰 승인
**요청**: 같은 OpenAPI에서 API 코드와 MSW 기반을 만들고, 단계마다 리뷰 후 다음으로 진행한다.

## 사용자 시나리오와 검증

### US1 — 같은 계약으로 API 코드 재생성 (P1)

어드민·회원 웹 개발자는 서버 명세를 기준으로 호출 코드와 모의 요청 처리를 함께 갱신한다.
타입을 따로 작성하면서 발생하는 계약 불일치를 줄이는 것이 가장 먼저 필요한 결과다.

**독립 검증**: 화면 연결 없이 생성 명령을 실행하고 명세의 operation과 생성 결과를 대조한다.

1. 유효한 명세가 주어지면, 한 번의 생성으로 모든 operation의 호출 코드와 모의 핸들러가 제공된다.
2. 명세의 필수 여부·null 허용·경로 변수가 바뀌면, 재생성 결과에도 같은 계약이 반영된다.
3. 같은 명세와 도구 버전을 사용하면, 생성 파일을 직접 고치지 않고 같은 결과를 얻는다.

### US2 — 백엔드 없이 대표 응답 확인 (P2)

개발자는 어드민·회원 웹의 로컬 브라우저에서 대표 응답과 실패 상태를 확인한다.
기존 화면을 일괄 전환하지 않고, 앞으로 생성 API를 사용하는 코드를 개발할 기반을 마련한다.

**독립 검증**: 모킹을 켠 두 앱에서 대표 API 요청을 보내 응답과 실서버 미접속을 확인한다.

1. 모킹을 켜면 준비 완료 뒤에 화면의 첫 요청을 허용한다. 시작 실패 시 요청하지 않고 안내한다.
2. 운영진 로그인·로그아웃, 어드민 세션 목록, 회원의 이번 주 세션, 공지 수신자를 조회할 수 있다.
3. 세션 없음과 공지 미열람 상태를 계약에 맞게 표현하며 실제 회원·인증 정보를 사용하지 않는다.
4. 모의 응답이 준비되지 않은 대상 요청은 실패하고 실제 서버로 전달되지 않는다.
5. 모킹을 끄거나 프로덕션으로 실행하면 기존 화면 동작을 유지한다.

### US3 — 기능 테스트용 MSW 기반 (P3)

개발자는 두 앱의 테스트에서 동일한 모의 계약을 사용하고 테스트마다 필요한 응답으로 바꾼다.
실서버 가용성이나 앞서 실행된 테스트의 결과에 의존하지 않아야 한다.

**독립 검증**: 테스트 서버의 시작·응답 초기화·종료 설정을 확인하고 기존 기능 테스트를 실행한다.

1. 두 앱에 기능 테스트에서 사용할 모의 서버와 공통 수명주기를 제공한다.
2. 응답 교체는 해당 테스트에만 적용되도록 테스트 종료 후 핸들러를 초기화한다.
3. 성공·오류 응답에 대한 제품 동작 검증은 해당 기능을 구현할 때 추가한다.
   SDK·fixture·모킹 초기화 자체를 위한 별도 테스트 묶음은 만들지 않는다.

### 경계 상황

- 명세 서버에 연결할 수 없으면 생성 성공으로 처리하지 않고 기존 생성물을 유지한다.
- 알려진 API에 응답 데이터가 없으면 501로 실패하고, 미등록 대상 경로도 실서버로 보내지 않는다.
- 정적 자원·개발 서버 통신·주소 검색 등 다른 서비스 요청은 모킹 대상에서 제외한다.
- 모킹 초기화 중 반복 렌더링이 발생해도 중복 시작하지 않는다.
- 모킹을 켠 개발 모드의 서버 렌더와 첫 클라이언트 렌더는 같은 준비 상태를 표시한다.
- 서버에서 먼저 실행되는 데이터 요청은 이번 브라우저 모킹으로 처리되지 않는다.

## 요구사항

### 기능 요구사항

- **FR-001**: 하나의 OpenAPI 입력에서 전체 operation의 클라이언트·타입·모의 핸들러를 생성한다.
  도구가 지원하는 명세의 응답 예제와 Faker 응답 factory를 활용하고, 의미 관계가 필요한 사례는 수동 보완한다.
- **FR-002**: 생성 계약은 필수 필드, null 허용, 경로 변수, 성공·오류 응답을 반영한다.
- **FR-003**: 생성 파일과 수동 응답 데이터를 분리하고 일반 API 사용 경로에 모킹을 섞지 않는다.
- **FR-004**: US2의 다섯 대표 API와 세션의 빈 결과·공지 미열람 사례를 제공한다.
- **FR-005**: 개발 모킹은 기본 비활성이며 명시적으로 켜야 한다. 프로덕션에서는 시작하지 않는다.
- **FR-006**: 모킹 준비 완료 전과 초기화 실패 시 자식 화면의 API 요청을 진행하지 않는다.
- **FR-007**: 모킹 대상의 미구현 요청은 실서버로 전달하지 않고 외부 서비스는 방해하지 않는다.
- **FR-008**: 양쪽 앱 테스트에서 같은 응답을 사용하며 응답 교체 상태를 테스트마다 초기화한다.
- **FR-009**: 재생성·실행·응답 추가·모킹 해제 방법을 한국어로 문서화한다.
- **FR-010**: 각 단계 종료 시 결과와 검증을 보고하고, 명시적 리뷰 승인 전에는 다음 단계로 가지 않는다.

### 주요 개념

- **API 계약**: 서버가 제공하는 operation, 요청·응답, 인증 명세. 별도 가짜 명세를 작성하지 않는다.
- **대표 응답**: 계약을 만족하는 고정 데이터와 상황별 오류. 실제 인증이나 저장 상태를 재현하지 않는다.
- **실행 범위**: 어드민·회원 웹의 개발 브라우저와 자동 테스트. 각 실행 환경이 시작과 종료를 관리한다.

## 성공 기준

- **SC-001**: 생성 입력의 operation 100%에 호출 코드와 모의 핸들러가 대응한다.
- **SC-002**: 다섯 대표 API를 두 앱의 개발·테스트 환경에서 실서버 없이 호출할 수 있다.
- **SC-003**: 대표 응답은 생성 타입으로 확인하고, 모의 JSON 응답은 실행 시 생성 Zod로 검증한다.
- **SC-004**: 브라우저에서 미구현 대상 요청·초기화 실패 시 실서버 요청이 차단되며, 테스트 설정에 응답 초기화가 연결된다.
- **SC-005**: 프로덕션에서 모킹이 시작되지 않고 앱 실행 번들에 수동 모의 데이터가 포함되지 않는다.
- **SC-006**: 모든 단계에 검증 기록과 사용자 리뷰 상태가 남는다.

## 전제와 제외 범위

- 대상 독자는 어드민·회원 웹 개발자다. 제품 목적은 [제품 맥락](../../docs/mission.md)을 따른다.
- 기존 화면의 직접 모의 데이터 호출, 실제 인증, 전체 CRUD 상태, 저장소를 이번에 전환하지 않는다.
- SSR 요청, route loader, 네이티브·실기기 WebView, Storybook 모킹은 포함하지 않는다.
- API 수는 명세에 따라 달라진다. 48개는 앞선 확인 결과이며 영구 고정된 요구가 아니다.
- 성능 지표를 임의로 만들지 않는다. 초기 요청 경쟁과 불필요한 프로덕션 모듈 포함을 검증한다.

## 5단계 리뷰 반영 — 모킹 전용 테스트 제외

사용자 “그렇게 수정해”에 따라 모킹 자체를 위한 테스트와 전용 보조 코드를 제거한다.
생성 타입 검사·응답의 실행 시 Zod 검증·브라우저 확인을 유지한다. 6단계는 기능 테스트가
사용할 MSW server와 공통 수명주기 설정으로 제한하며, SDK·모킹 전용 회귀 테스트는 추가하지 않는다.

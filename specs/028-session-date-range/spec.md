# Feature Specification: 세션 시작일·종료일 분리

**Feature Branch**: `028-session-date-range`

**Created**: 2026-11-27

**Status**: Ready for implementation

**Input**: User description: "세션 생성할때 날짜 하나만있는데 이거 세션 시작일, 세션 종료일 두개로 나누도록 수정하고싶어"

## User Scenarios & Testing

### User Story 1 - 세션 기간 입력 (Priority: P1)

운영진은 세션을 추가하거나 수정할 때 시작일과 종료일을 각각 입력해 여러 날에 걸친 세션 일정을 저장한다.

**Why this priority**: 날짜를 하나만 입력하는 현재 화면으로는 세션 기간을 표현할 수 없으므로 핵심 가치다.

**Independent Test**: 세션 추가 화면에서 서로 다른 시작일·종료일과 시간을 입력해 저장하고, 요청 본문과 목록 카드에 두 날짜가 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 세션 추가 화면이 열려 있을 때, **When** 운영진이 시작일·종료일·시작 시간·종료 시간을 입력하면, **Then** 두 날짜 입력란이 각각 입력값을 유지한다.
2. **Given** 시작일이 종료일보다 빠른 일정이 입력되어 있을 때, **When** 저장하면, **Then** 시작일·종료일·시간이 함께 전송되고 저장된 기간이 목록에 표시된다.
3. **Given** 기존 세션을 수정할 때, **When** 목록 응답의 시작일·종료일을 불러오면, **Then** 두 입력란에 각각 원래 값이 표시된다.

### User Story 2 - 일정 경계 검증 (Priority: P1)

운영진은 종료 일시가 시작 일시보다 빠르거나 같은 잘못된 기간을 저장하지 않는다.

**Why this priority**: 날짜가 분리되면 날짜와 시간이 함께 일정의 유효성을 결정하므로 데이터 충돌을 방지해야 한다.

**Independent Test**: 시작일·종료일과 시간을 조합한 경계값을 입력해 저장 가능 여부와 종료 필드 오류 위치를 확인한다.

**Acceptance Scenarios**:

1. **Given** 시작일과 종료일이 같은 날일 때, **When** 종료 시간이 시작 시간보다 빠르거나 같으면, **Then** 종료 시간 필드에 오류가 표시되고 저장되지 않는다.
2. **Given** 종료일이 시작일보다 빠를 때, **When** 저장하면, **Then** 종료일 필드에 기간 오류가 표시되고 저장되지 않는다.
3. **Given** 종료일이 시작일보다 늦을 때, **When** 시간 순서가 역전되어 있어도, **Then** 전체 종료 일시가 시작 일시보다 늦으면 저장할 수 있다.

## Edge Cases

- 시작일과 종료일이 같은 날인 일정은 기존처럼 시간 순서가 엄격하게 검증된다.
- 종료일이 시작일보다 빠른 일정은 종료일 필드에서 안내한다.
- 기존 API의 단일 날짜 응답을 임시로 읽는 경우에는 시작일과 종료일을 같은 날짜로 복원해 기존 세션 수정이 중단되지 않도록 한다.
- 날짜와 시간은 한국 시간 기준의 날짜·벽시계 값으로 다루며 브라우저 시간대 변환으로 날짜가 바뀌지 않는다.

## Requirements

### Functional Requirements

- **FR-001**: 세션 추가·수정 화면은 날짜 입력을 `세션 시작일`과 `세션 종료일` 두 입력으로 제공해야 한다.
- **FR-002**: 생성·수정 요청은 `startDate`, `endDate`, `startTime`, `endTime`을 함께 전송해야 한다.
- **FR-003**: 조회 응답은 세션의 `startDate`와 `endDate`를 제공해야 하며, 화면은 이를 기간으로 표시해야 한다.
- **FR-004**: 시작일·종료일·시간을 조합한 종료 일시는 시작 일시보다 늦어야 한다.
- **FR-005**: 같은 날짜의 세션에서는 종료 시간이 시작 시간보다 늦어야 한다.
- **FR-006**: 저장 실패 시 날짜 입력 초안과 필드 오류를 유지하고 사용자가 수정할 수 있어야 한다.
- **FR-007**: 세션 목록 정렬은 시작일과 시작 시간을 기준으로 최신 일정부터 유지해야 한다.
- **FR-008**: 기존 단일 날짜 응답을 받더라도 두 날짜를 같은 값으로 복원해 수정 화면을 열 수 있어야 한다.

### Key Entities

- **SessionSchedule**: 세션의 `startDate`, `endDate`, `startTime`, `endTime`으로 구성된 한국 시간 기준 일정 범위.
- **Session**: 이름·유형·장소·출석 집계와 `SessionSchedule`을 가진 관리자 세션.

## Success Criteria

### Measurable Outcomes

- **SC-001**: 운영진은 시작일과 종료일이 다른 세션을 한 번의 저장 흐름으로 등록할 수 있다.
- **SC-002**: 유효하지 않은 기간 입력은 저장 요청 전에 100% 차단되고 종료 날짜 또는 시간 필드에 안내된다.
- **SC-003**: 목록과 수정 화면에서 저장된 시작일·종료일이 각각 원래 값과 일치한다.
- **SC-004**: 기존 단일 날짜 세션은 수정 화면에서 날짜 유실 없이 열리고, 동일 날짜 세션으로 표시된다.

## Assumptions

- 시간 입력은 기존처럼 `HH:mm` 형식을 사용하고 API의 초 단위 값은 수정하지 않았을 때 보존한다.
- 시작일과 종료일은 날짜만 표현하는 ISO `YYYY-MM-DD` 값이며 특정 순간으로 변환하지 않는다.
- 이 작업의 API 계약 변경은 관리자 세션 생성·수정·목록 응답에 적용하며 회원용 조회의 기존 `date` 계약은 별도 작업으로 다룬다.
- 백엔드 OpenAPI 원본은 이 저장소 밖에서 관리되므로 생성 코드 갱신은 새 계약이 반영된 명세를 기준으로 수행한다.

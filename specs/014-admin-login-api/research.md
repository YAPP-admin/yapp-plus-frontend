# 기술 조사: 관리자 로그인 API와 세션 연동

## 결정 1 — 로그인 계약

- **결정**: 생성된 `POST /api/admin/auth/sessions`와 `StaffLoginResponse`를 그대로 사용한다.
- **근거**: 요청은 `loginId`·`password`, 응답은 `staff`·`accessToken`이며 refresh token과 만료
  정보가 없다. API 명세가 시스템 경계의 단일 진실 공급원이다.
- **검토한 대안**: 앱 전용 HTTP 호출과 수동 타입은 생성 계약과 중복되어 제외했다.

## 결정 2 — token 수명과 저장 위치

- **결정**: `yapp-plus-admin.access-token.v1` key로 localStorage에 access token만 저장한다.
- **근거**: 사용자가 브라우저 재시작 뒤에도 세션 유지를 선택했다. versioned key는 이전 앱과의
  충돌과 복구 범위를 줄인다.
- **검토한 대안**: 메모리는 새로고침에, sessionStorage는 탭 종료에 세션이 사라져 요구와 다르다.
  HttpOnly cookie는 현재 Staff API 계약이 제공하지 않는다.

## 결정 3 — token 적용 범위

- **결정**: client auth callback이 요청 시점마다 저장소를 읽고 `staffBearerAuth`에만 반환한다.
- **근거**: 재시작·다른 탭의 변경을 별도 동기화 없이 반영하며 Staff token의 회원 인증 유출을
  막는다. 서버에서는 저장소를 읽지 않아 요청 간 token 공유를 피한다.
- **검토한 대안**: 고정 header는 token 교체를 반영하기 어렵고 모든 요청에 유출될 수 있다.

## 결정 4 — 성공 응답과 오류 매핑

- **결정**: 성공 응답은 생성 Zod로 검증한다. 401만 자격 증명 실패, 나머지는 서비스 실패다.
- **근거**: 외부 응답을 신뢰 경계에서 검증하고 수정 가능한 실패와 운영 오류를 구분한다. 저장
  실패도 후속 요청이 인증될 수 없으므로 성공으로 보지 않는다.
- **검토한 대안**: 모든 오류를 합치면 기존 UX 계약을 잃고, 오류 body만 판정하면 네트워크·비 JSON
  오류를 안정적으로 분류하기 어렵다.

## 결정 5 — 기존 세션 교체

- **결정**: 새 응답 검증과 저장이 성공한 뒤에만 기존 token을 교체한다.
- **근거**: 잘못된 입력이나 일시 장애가 유효한 기존 세션을 파괴하지 않는다.
- **검토한 대안**: 제출 시작 시 삭제는 네트워크 실패에도 로그아웃된다. 계정별 캐시 정리는 후속
  인증 흐름에서 함께 다룬다.

## 결정 6 — 늦은 성공과 화면 이동

- **결정**: 세션 저장은 mutation 함수가 끝내고 화면 이동은 제출별 observer callback이 담당한다.
- **근거**: 로그인 화면이 unmount되면 observer callback은 실행되지 않아 #157을 막으면서 인증
  결과 자체는 보존한다.
- **검토한 대안**: hook-level callback은 화면을 떠난 뒤에도 이전 navigate를 실행한다. 요청 취소는
  서버 성공 여부와 세션 결과를 불필요하게 버릴 수 있다.

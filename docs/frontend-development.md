# 프론트엔드 개발 가이드

이 문서는 `apps/admin`, `apps/web`과 이들이 사용하는 `packages/*`에서 프론트엔드 화면·상태·
테스트를 작성할 때 공통으로 적용하는 원칙을 정리합니다. 모바일 앱의 WebView 안에서 렌더링되는
웹 화면에도 이 원칙을 적용합니다. 제품 목적과 출시 범위는 [제품 맥락](./mission.md)과 기능별
명세를 먼저 확인하고, 앱별 라우팅·폴더 구조·플랫폼 규칙은 [관리자 앱 가이드](./admin-development.md),
[웹 작업 가이드](./web-development.md)에서 확인합니다.

이 문서에는 여러 앱에서 반복될 수 있는 기술 선택과 경계만 둡니다. 관리자 전용 TanStack
Router·Form·Table 규칙, 웹 전용 Stackflow·Vite 규칙, 특정 화면의 제품 정책은 각 앱이나 기능 명세에
작성합니다.

`apps/admin`과 `apps/web`은 모두 SEED 기반의 DOM UI를 사용하므로 이 문서의 디자인 시스템과
웹 접근성 원칙을 공통으로 적용합니다. WebView에서 표시되는 `apps/web` 화면도 같은 기준을
사용합니다.

`apps/mobile`의 React Native 네이티브 코드에는 DOM·SEED React 컴포넌트 규칙을 그대로 적용하지
않습니다. 네이티브 화면은 React Native의 의미 있는 컴포넌트, 접근성 props와 터치 규칙을 따르고,
WebView로 띄우는 `apps/web` 화면은 이 문서와 웹 작업 가이드를 따릅니다.

## 작업 시작과 변경 범위

화면을 만들기 전에 다음 순서로 확인합니다.

1. [제품 맥락](./mission.md)에서 대상 사용자와 제품 목적을 확인합니다.
2. 연결된 기획 원문과 기능 명세에서 화면 상태·문구·수용 기준을 확인합니다.
3. 기존 공용 패키지와 유사한 화면의 공개 진입점을 확인합니다.
4. 현재 요구사항을 충족하는 가장 작은 화면·모델·테스트 변경을 작성합니다.
5. 실제 사용처가 둘 이상 확인되기 전에는 공용 추상화·새 패키지·전역 상태를 추가하지 않습니다.

확인되지 않은 API, loading·error 정책, 출시 범위와 화면 상태를 구현자가 추측해 확정하지
않습니다. 불확실한 정책은 명세에 남기고, 구현에서는 확인된 계약만 사용합니다.

## 모노레포와 공개 경계

- `apps/*`는 독립적으로 실행·배포하는 제품 단위입니다.
- `packages/*`는 둘 이상의 실제 소비자가 있거나 API·브리지·디자인 토큰처럼 저장소 차원의
  안정된 계약일 때만 사용합니다.
- 앱 사이에서 내부 파일을 직접 import하지 않고 패키지의 공개 진입점을 사용합니다.
- 화면 슬라이스 밖에서는 해당 슬라이스의 공개 `index.ts`만 사용하고 내부 `ui`·`model` 파일을
  직접 import하지 않습니다.
- 생성된 OpenAPI 클라이언트, route tree와 같은 파일은 직접 수정하지 않습니다. 생성 설정·원본
  명세·템플릿을 수정한 뒤 생성 명령으로 갱신합니다.

의존성 방향과 화면별 배치 규칙은 앱 가이드에서 정하되, 상위 레이어가 하위 레이어의 공개
계약을 사용하고 하위 레이어가 앱의 내부 구현에 의존하지 않는 구조를 유지합니다.

## API 계약과 개발용 입력

외부 데이터는 시스템 경계에서 검증하고 화면에서 읽기 쉬운 ViewModel로 변환합니다.
OpenAPI 생성 타입과 브리지 타입을 시스템 경계의 단일 진실 공급원으로 사용하며, 임의의 HTTP
경로·DTO를 화면 구현에서 발명하지 않습니다.

API 계약이 아직 준비되지 않은 화면은 다음 경계를 지킵니다.

- 개발용 입력은 읽기 전용 fixture로 만들고 페이지 props 또는 명시적인 개발 진입점으로만
  공급합니다.
- 운영 빌드에 fixture를 노출하지 않고, 실제 API가 준비되지 않았다면 확인된 준비 안내를
  표시합니다.
- fixture를 위해 별도 모의 저장소·가짜 CRUD API·가짜 Query/Mutation·네트워크 지연 타이머를
  추가하지 않습니다.
- 실제 API 계약이 확정되면 route 또는 공급부를 생성 SDK·Query로 교체하고, 화면의 표시·입력
  계약은 가능한 한 유지합니다.

fixture의 정상·빈·오류 입력은 모델·화면 테스트에서 직접 공급해 검증합니다. fixture가 실제
서버의 loading·재시도·저장 수명을 흉내 내야 한다고 가정하지 않습니다.

## 상태와 비동기 작업

상태는 가장 가까운 소유자에 둡니다.

| 상태 종류                                                   | 기본 소유자                            |
| ----------------------------------------------------------- | -------------------------------------- |
| 서버 조회·캐시·재조회                                       | TanStack Query                         |
| 서버 변경·파일 처리 등 비동기 작업                          | 화면에서 분리한 Query `useMutation` 훅 |
| 입력값·검증·제출 초안                                       | 폼 라이브러리 또는 해당 폼             |
| 모달·선택·파일 등 화면 수명 상태                            | 페이지·컴포넌트·화면 전용 훅           |
| 여러 화면에서 공유하거나 새로고침 후에도 보존해야 하는 상태 | 요구사항 확인 후 URL 또는 전역 store   |

서버 상태와 같은 의미의 loading·error·결과를 별도 state·ref로 중복 관리하지 않습니다.
요청 식별자, 이전 결과 보존용 ref, 수동 경합 플래그는 실제 요구와 재현 가능한 실패가 있을
때만 추가합니다. 파일 객체처럼 특정 화면 수명에만 필요한 값은 전역 store나 URL에 저장하지
않습니다.

전역 store는 다음 조건을 모두 검토한 뒤 도입합니다.

- 둘 이상의 화면이 동일한 상태를 동시에 읽고 변경해야 합니다.
- URL·Query 캐시·상위 컴포넌트로 소유할 수 없습니다.
- 상태 수명과 초기화·복구 정책을 문서로 설명할 수 있습니다.

단순히 컴포넌트가 길거나 props가 많다는 이유로 Zustand와 같은 전역 상태를 도입하지
않습니다.

## UI와 디자인 시스템

- 기존 `packages/ui` 공개 컴포넌트와 SEED 컴포넌트·토큰을 먼저 확인합니다.
- 같은 UI를 앱마다 복제하지 않고, 실제 소비자가 둘 이상일 때만 공용 패키지로 승격합니다.
- 아이콘은 기존 아이콘 패키지와 `lucide-react`를 우선 사용하며, 기능을 위해 임의의 SVG를
  새로 만들지 않습니다.
- 래퍼 컴포넌트의 HTML props는 가능한 경우 `React.ComponentProps` 기반으로 추론하고, 임의의
  중복 타입을 만들지 않습니다.
- 색상·간격·타이포그래피는 기존 디자인 토큰을 사용하고 화면마다 임의의 값을 복제하지
  않습니다.
- 빈 결과·오류·준비 중 상태는 기존 공통 컴포넌트의 계약을 확인한 뒤 사용합니다. 같은 의미의
  Empty State를 화면마다 새로 만들지 않습니다.

React Compiler가 적용된 영역에서는 먼저 읽기 쉬운 일반 코드를 작성합니다. 측정된 병목이나
라이브러리 계약상 필요한 경우가 아니면 `React.memo`, `useMemo`, `useCallback`을 선제적으로
추가하지 않습니다.

React 19를 사용하는 새 로컬 컴포넌트는 `ref`를 일반 prop으로 받고, 기존 라이브러리 호환 계약이
없는 한 `forwardRef`를 새로 추가하지 않습니다. 문서 metadata는 JSX의 `<title>`·`<meta>`로
선언하고 `useEffect`에서 `document.title`을 직접 변경하지 않습니다.

## 접근성과 상호작용

- 입력에는 연결된 label과 명확한 accessible name을 제공합니다.
- 표·폼·버튼·링크는 의미에 맞는 HTML과 SEED 컴포넌트를 사용합니다.
- 키보드·스크린 리더·터치에서 실제 사용자가 도달하고 조작할 수 있는 순서를 확인합니다.
- 비상호작용 요소에 `tabIndex`를 추가해 상호작용처럼 만들거나 lint 예외로 숨기지 않습니다.
  가로 스크롤처럼 키보드 진입이 필요하면 브라우저가 제공하는 시맨틱·포커스 가능한 구조를
  먼저 사용합니다.
- `aria-*` 속성은 시각적 모양을 맞추기 위한 장식이 아니라 의미와 상태를 전달할 때만
  추가합니다.

접근성 검증에서는 외부 라이브러리 내부 DOM 구조보다 애플리케이션이 제공하는 이름·역할·상태·
키보드 흐름을 확인합니다.

## 테스트 원칙

테스트는 정책과 앱 경계를 검증하고, 외부 라이브러리의 내부 구현을 복제하지 않습니다.

- 순수 변환·스키마·ViewModel은 인접한 모델 테스트에서 검증합니다.
- 입력·검증·초안·중복 제출 차단은 폼 또는 화면 테스트에서 검증합니다.
- 사용자 상호작용은 `userEvent`를 기본으로 사용합니다.
- `fireEvent`는 `userEvent`로 표현할 수 없는 실제 이벤트(예: 파일 드롭)에만 제한적으로
  사용하고 이유를 남깁니다.
- 컴포넌트 mock은 router·디자인 시스템 전용 prop을 명시적으로 소비한 뒤 유효한 HTML prop만
  DOM에 전달합니다. 알 수 없는 prop 경고를 숨기기 위해 콘솔을 mock하지 않습니다.
- 라우팅·모달·업로드처럼 여러 컴포넌트가 연결되는 기능은 route tree 기준의 대표 흐름을
  추가합니다.
- 같은 실패 조합을 모델·컴포넌트·페이지에서 반복하지 않고, 오류가 처음 변환되거나 연결되는
  가장 가까운 계층에서 검증합니다.
- 외부 라이브러리의 내부 DOM 속성·타이머 개수·기본 자동 종료 시간은 직접 설정한 정책이
  아닌 이상 검증하지 않습니다.

변경 후 기본 품질 게이트는 `node --run check`입니다. 배포 가능한 앱·빌드 설정을 변경하면
`node --run build`도 실행하고, 결과에는 새 실행과 Turbo 캐시 재사용을 구분해 기록합니다.

## 코드 주석과 공개 계약

프로젝트가 관리하는 코드 주석은 한국어로 작성합니다. 파일의 첫 주석은 해당 파일의 책임과
다른 레이어와의 경계를 설명합니다. 공개 타입·스키마·함수·컴포넌트에는 이름만 반복하지 않고
입력·출력, 상태 수명, 검증 규칙, 원본 보존, 외부 계약과의 차이처럼 호출자가 알아야 하는
조건을 주석으로 기록합니다.

함수 이름과 타입만으로 동작이 명확한 내부 구현에는 주석을 반복하지 않습니다. 대신 시간이 지나면
잊기 쉽거나 잘못 바꾸기 쉬운 제품 정책, 접근성 연결, 상태 초기화·폐기, API 변환 경계와 같은
이유를 가까운 코드에 남깁니다. 주석은 현재 동작을 설명해야 하며 임시 계획·추측·사용하지 않는
대안을 남기지 않습니다. 외부 도구가 생성한 파일에는 직접 주석을 추가하지 않습니다.

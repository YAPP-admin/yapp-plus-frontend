# 기능 명세: 관리자 회원 관리 화면

**브랜치**: `brussels-v2/member-management-fixtures` | **작성일**: 2026-10-29
**상태**: 1·2a·2b단계 리뷰 완료 · 3단계 완료·리뷰 대기 · [이슈 #182](https://github.com/YAPP-admin/yapp-plus-frontend/issues/182)
**요청**: 지정된 Figma 기준 회원 관리 구현. 팀 매핑은 제외하고 단계마다 사용자 리뷰를 받는다.
**제품 맥락**: [제품 목적과 범위](../../docs/mission.md)

## 사용자 시나리오와 수용 기준

### US1 — 회원 조회와 탐색 (P1)

운영진이 회원 목록을 직군·이름·팀으로 좁히고 가입 대기 빈 화면과 명단 업로드로 이동한다.
**우선순위 이유**: 회원 관리의 진입점이며 수정·업로드의 결과를 확인할 기본 화면이다.
**독립 검증**: 읽기 전용 예시 명단으로 탐색·검색·필터·빈 상태를 검증할 수 있다.

1. 회원 목록에서 이름 검색을 제출하고 직군·팀을 선택하면 교집합과 총원이 표시된다.
2. 뒤로가기·새로고침하면 URL의 검색 조건과 화면이 일치한다.
3. 팀 매핑 전에는 안내를 표시하고 팀 열·필터를 숨긴다. 매핑 후에는 팀과 필터를 표시한다.
4. 가입 신청 메뉴는 대기 0건과 지정된 빈 화면을 표시하며 승인·거절을 제공하지 않는다.
5. 명단 업로드에서 브라우저 뒤로가기는 이전 조건을, 명시적 목록 복귀는 기본 조건을 표시한다.

### US2 — 회원 수정 화면 검토 (P2)

운영진이 회원 정보와 변경 이력을 확인하고 이름·기수·직군·권한을 편집해 입력 오류를 확인한다.
**우선순위 이유**: 저장 계약 전에도 입력 정책과 수정 화면을 검토할 수 있다.
**독립 검증**: 모달 초기값·입력·기수 정정 제한·취소를 확인하며 실제 저장은 발생하지 않는다.

1. 더보기의 정보 수정에서 초기값과 기존 변경 이력을 확인한다.
2. 팀·출석 기록이 연결되어 있거나 동일 전화번호·기수 활동이 있으면 기수 정정을 차단한다.
3. 취소·닫기·목록 조건 변경은 초안을 폐기한다. 재진입하면 원본 값을 표시한다.
4. 저장·비활동 버튼은 비활성이고 기능 준비 중 안내가 보인다. Enter도 제출하지 않는다.

### US3 — 실제 명단 파일 검토 (P2)

운영진이 양식을 내려받아 실제 파일을 읽고 오류·중복과 반영 예정 수를 확인한다.
**우선순위 이유**: 서버 반영 전에도 명단 정리와 업로드 UI의 적합성을 검증할 수 있다.
**독립 검증**: XLSX·XLS·CSV의 실제 내용을 검증하고 중복 처리 선택을 바꿀 수 있다.

1. 유효한 파일을 선택하거나 드롭하면 첫 시트의 내용과 원본 행 번호가 표시된다.
2. 오류·정상·중복 수가 실제 내용과 일치하고 모든 행에 접근할 수 있다.
3. 기존 활동 중복은 기본 건너뛰기이며 덮어쓰기를 선택하면 반영 예정 수가 달라진다.
4. 다시 올리기는 파일·결과·중복 선택을 초기화한다. 실제 명단 반영은 비활성이다.

### 경계 사례

- 회원 자체가 없는 경우와 검색 결과가 없는 경우, 점수·팀 정보 없음은 구분한다.
- 잘못된 검색 값·존재하지 않는 팀 ID, 긴 이름·과거 기수 여러 개를 처리한다.
- 손상·빈 파일, 크기 초과, 잘못된 헤더·필드, 첫 행 오류 후 동일 조합의 유효 행을 처리한다.
- 파일 교체·화면 이탈 뒤 늦게 끝난 읽기가 현재 결과를 바꾸지 않는다.
- 개발용 명단은 프로덕션 화면에 나타나지 않는다. 개발 SSR과 클라이언트는 같은 고정 입력을 사용한다.

## 기능 요구사항

- **FR-001**: 행 형태 목록과 사이드바의 회원 목록·가입 신청 탐색을 제공한다.
- **FR-002**: 이름·직군·과거 기수 이력·권한·출석 점수·가입일·더보기를 표시한다.
- **FR-003**: 이름 검색·직군·팀 필터, URL 복원, 결과 총원을 제공한다.
- **FR-004**: 매핑 전후 표시와 팀별 인원을 제공하되 팀 매핑 메뉴·이동 버튼·변경 기능은 제외한다.
- **FR-005**: 가입 대기 빈 화면과 0건 표시만 제공한다. 실제 신청 조회·승인·거절은 제외한다.
- **FR-006**: 회원 수정 초안·기수 정정 제한·기존 변경 이력·초안 폐기를 제공한다.
- **FR-007**: 저장·비활동·명단 반영은 비활성이고 준비 중임을 알린다. 성공 안내·가짜 저장을 하지 않는다.
- **FR-008**: 최대 10MB의 XLSX·XLS·CSV 파일 하나를 읽고 첫 시트만 처리한다고 안내한다.
- **FR-009**: 양식 다운로드와 이름·전화번호·기수·직군·권한 순서의 헤더 검증을 제공한다.
- **FR-010**: 빈 행을 제외하고 원본 행 번호, 필수 값·기수·직군·권한·전화번호 오류를 표시한다.
- **FR-011**: 010-1234-5678과 01012345678을 모두 허용하고 같은 전화번호로 비교한다. 앞자리 유실은 복구하지 않는다.
- **FR-012**: 파일 내부는 전화번호·기수의 첫 유효 행만 인정하고 이후 행은 오류로 표시한다.
- **FR-013**: 읽기 전용 명단과 비교해 신규 회원·새 기수 활동·기존 활동 중복을 구분한다.
- **FR-014**: 정상·오류·중복과 반영 예정 수를 구분하고 모든 중복 행에서 처리 방법을 선택할 수 있게 한다.
- **FR-015**: 파일 교체·다시 올리기·이탈 시 이전 결과와 선택을 정리한다.
- **FR-016**: 키보드·스크린 리더·375px에서 탐색·표·입력·파일 선택을 사용할 수 있게 한다.
- **FR-017**: 예시 명단은 개발 화면에서만 사용하며 파일·전화번호를 로그·영속 저장에 기록하지 않는다.
- **FR-018**: 이번에는 실제 저장과 API 연동을 제외하고 확정한 정책과 필요한 계약을 후속 작업으로 남긴다.

### 주요 개체

회원과 기수별 활동, 조회용 팀, 출석 요약, 기존 변경 이력, 업로드 검증 행을 표시한다.
이름은 회원 공통 정보이고 직군·권한·활동 상태는 기수별 정보다. 구현 모델은 [데이터 모델](data-model.md)을 따른다.

### 사용자 확정 정책

| 항목           | 기준                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 비활동         | 현재 기수 활동만 변경하며 과거 이력은 유지한다. 실제 처리는 후속이다.                          |
| 중복 덮어쓰기  | 이름·해당 기수 직군·권한만 변경하고 팀·출석·가입일·활동 상태는 보존한다. 실제 반영은 후속이다. |
| 다음 기수 참여 | 명단 업로드로 기존 회원의 새 기수 활동을 추가한다. 실제 반영은 후속이다.                       |
| 기수 오입력    | 수정 모달의 정정으로 구분하고 팀·출석 연결 또는 대상 기수 중복 시 막는다.                      |
| 파일           | 첫 시트만 읽으며 전화번호 하이픈 유무를 허용하고 첫 유효 중복 행만 인정한다.                   |

## 성공 기준

- **SC-001**: 8개 Figma 참조의 포함 요소가 화면과 검증 항목에 연결된다.
- **SC-002**: 검색·필터 조합 및 URL 복원 결과와 표시 총원이 모두 일치한다.
- **SC-003**: 수정·비활동·반영 조작에서 원본 명단 변경과 저장 요청이 0건이다.
- **SC-004**: 세 파일 형식의 실제 입력에서 행별 판정·집계·반영 예정 수가 기대 결과와 일치한다.
- **SC-005**: 개발 명단이 프로덕션에서 노출되지 않고 데스크톱·375px의 주요 조작을 완료할 수 있다.

## 가정과 범위

운영 기수는 기존 예시인 33기다. 기수 전환·생성, 실제 인증·운영 권한 정책은 변경하지 않는다.
목록은 이름 오름차순이며 별도 사용자 정렬·페이지네이션·가상화를 추가하지 않는다.
이번 중복 판정은 읽기 전용 예시 명단과의 비교이며 실제 서버의 최종 판정이 아니다.
기수별 운영진·비활동 상태와 명단 반영 계약은 실제 API 연결 전에 백엔드와 확인한다.
[디자인·조사 근거](research.md), [화면 계약](contracts/member-ui.md), [계획](plan.md), [작업 목록](tasks.md)을 함께 따른다.

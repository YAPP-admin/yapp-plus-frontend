# 구현 계획: 관리자 세션 관리

**브랜치**: `DongjaJ/gihc4` | **작성일**: 2026-10-15 | **상태**: 7단계 구현 완료 — 사용자 리뷰 대기
**명세**: [spec.md](spec.md) | **이슈**: [#68](https://github.com/YAPP-admin/yapp-plus-frontend/issues/68)

## 요약과 기술 맥락

기존 관리자 셸과 `/sessions`를 확장한다. React 19·TypeScript 6, TanStack Router·Query·Form,
Zod 4, vanilla-extract 및 SEED 컴포넌트·토큰을 적극 사용한다. 새 의존성이나 공용 패키지를 추가하지 않는다.
Node 24.20.0·pnpm 12.3.4, Vitest·Testing Library·happy-dom을 유지한다.
브라우저 메모리의 개발용 데이터만 사용하며 서버 API, 영속 저장소, 페이지별 추가 로딩은 없다.
성능 목표 숫자를 새로 만들지 않고 모든 예시 세션에 접근 가능한 네이티브 스크롤을 제공한다.

## 저장소 원칙 검토

- 헌법은 미작성 템플릿이므로 AGENTS.md를 기준으로 검토했다. 제품 목적과 한국어 문서 원칙을 따른다.
- 코드와 타입은 admin 내부에 둔다. 다른 앱이나 패키지 내부를 import하지 않는다.
- 기존 공용 `ActionButton`과 `@seed-design/react` 공개 컴포넌트를 사용한다. 필요한 공식 snippet은 admin 내부에 둔다.
- 둘 이상의 실제 소비자가 생긴 경우에만 packages/ui 공개 진입점으로 공통화하고 해당 테스트·Storybook 사례를 추가한다.
- 실제 API 연동 시 생성된 계약을 기준으로 교체한다. 가짜 HTTP 명세나 미래용 adapter를 만들지 않는다.
- 새 라우트는 필요 없다. 생성된 routeTree 파일은 직접 편집하지 않는다.
- 설계 후 재검토: 데이터 마이그레이션·권한·배포 변경이 없고 공용 계약 변경도 없다.

## 코드 책임과 데이터 흐름

- `apps/admin/src/app/ui/`: 관리자 셸, 내비게이션과 반응형 스타일.
- `apps/admin/src/pages/sessions/`: `model/`의 스키마·필터·Query·모의 서비스와 `ui/`의 페이지·카드·모달.
- `apps/admin/src/routes/_dashboard/sessions.tsx`: URL 검색값을 읽고 페이지에 값·탐색 콜백을 전달한다.
- `index.ts`는 라우트가 필요한 페이지와 검색 스키마만 공개한다. 서비스·폼·카드 내부 구현은 공개하지 않는다.
- 모달은 종류와 선택한 세션 ID로 관리한다. 여러 모달을 동시에 열지 않고 정보는 현재 목록에서 찾는다.
- Query는 전체 목록 하나를 캐시하고 유형 필터·정렬·개수는 그 목록에서 계산한다.
- 생성·수정·삭제 성공 때만 캐시를 갱신한다. 실패 시 데이터는 유지하며 낙관적 변경은 사용하지 않는다.
- 생성 성공 → 캐시 반영 → 필터 전체 전환 → 모달 종료·완료 안내 순서로 처리한다.
- 수정 성공 → 같은 ID의 캐시 항목 교체 → 현재 필터에서 정렬·개수 재계산 → 모달 종료·완료 안내 순서로 처리한다.
- 생성 폼은 12-1단계에서 초기값·제출 콜백을 받는 공통 폼으로 추출하여 수정 폼과 재사용한다.
- 삭제 성공 → 캐시에서 제거 → 모달 종료 → 남은 카드 또는 제목으로 포커스를 이동한다.
- 요청 오류는 화면에 표시하고 재시도할 수 있게 한다. 자동 재시도는 끄고 사용자 재시도를 제공한다.

구체적인 필드와 함수는 [data-model.md](data-model.md), UI·URL 경계는
[contracts/session-ui.md](contracts/session-ui.md)에 정의한다.

## 화면·접근성 구현

- 관리자 셸 안에만 어두운 테마를 적용한다. 로그인은 별도 레이아웃을 유지한다.
- 와이어프레임의 영역 구성과 정보 우선순위를 유지하되 색상·간격·타이포그래피·모서리·상태 표현은 SEED 기준으로 정돈한다.
- 사이드바 240px, 헤더 68px, 본문 최대 1200px·여백 44px은 초기 배치 참고값이며 정보 밀도와 SEED 토큰에 맞게 조정할 수 있다.
- 1180px 미만은 버튼으로 여는 메뉴, 768px 미만은 세로 배치·본문 여백 16px을 사용한다.
- 로고는 대시보드로 이동한다. 기존 메뉴와 출석 상세의 출석부 활성 상태를 유지한다.
- 사용자·기수 표시는 개발용임을 드러내고 전환·로그아웃 같은 미구현 동작을 작동 가능한 버튼으로 제공하지 않는다.
- 필터는 선택 상태를 읽을 수 있는 SEED 선택 컴포넌트를 우선 사용한다. 목록은 1열로 표시하고 카드 본문은 비대화형 `article`로 구성한다. 카드의 작업 진입점은 케밥 메뉴로 한정한다.
- 카드 작업은 SEED Menu를 우선 사용하고 제공되는 키보드 탐색·포커스·ARIA 동작을 유지한다.
- 생성·수정 모달과 삭제 확인은 SEED의 적합한 Dialog 계열 컴포넌트를 우선 사용한다. 포커스 격리를 직접 재구현하지 않는다.
- 입력·유형 선택·배지·로딩·오류 안내에도 현재 버전에서 지원하는 SEED 컴포넌트를 우선 적용한다.
- 사용 전 고정 버전의 공개 API와 snippet 호환성을 확인한다. 지원하지 않는 요구만 네이티브 요소로 보완하며 임의로 메이저 업그레이드하지 않는다.
- 생성 모달은 680px을 초기 참고값으로 삼고 입력 밀도와 SEED 규격에 맞게 조정하며 높이는 viewport 안에서 스크롤한다. 입력 글자 크기는 16px 이상이다.
- 모달 제목을 연결하고 열 때 제목에 포커스를 둔다. 닫을 때 트리거 복귀를 보장한다.
- Form으로 값·필드 오류, Mutation으로 제출 상태를 관리한다. 첫 제출 이후 변경 시 재검증한다.
- 첫 오류 필드로 이동하고 오류를 입력과 연결한다. 제출 중에는 입력·닫기·중복 제출을 막는다.
- 테스트 환경에서 지원되지 않는 브라우저 동작은 최소 보완하되 실제 포커스·Esc 동작은 브라우저에서 확인한다.

## 개발용 데이터와 운영 환경

- 환경 가드 안에서만 모의 모듈을 동적으로 가져온다. SSR에서 모의 저장소를 초기화하지 않는다.
- 클라이언트 mount 이후에만 조회를 활성화하여 서버 렌더링과 초기 hydration 결과를 맞춘다.
- 브라우저 탭의 모의 모듈이 목록을 유지한다. Query 캐시가 만료되어도 서비스가 변경된 목록을 반환한다.
- 테스트마다 별도 저장소를 만들어 데이터가 새지 않게 한다. 오류·대기 상태는 테스트 대역으로 제어한다.
- 프로덕션은 “세션 관리 기능을 준비 중입니다.”를 표시하고 생성·수정·삭제를 노출하지 않는다.
- 프로덕션 client/server 산출물에 모의 fixture와 저장소 구현이 없는지 확인한다.

## 검증·PR·복구

세부 작업과 매 단계 리뷰 중단점은 [tasks.md](tasks.md), 실행 방법은 [quickstart.md](quickstart.md)를 따른다.
시각 리뷰는 픽셀 일치보다 레이아웃·정보 위계·SEED 일관성·상태 완성도를 평가한다.
각 단계는 해당 동작 테스트와 화면 근거를 남긴 뒤 멈추고 사용자 확인을 받는다.
문서·스타일·테스트·생성 파일을 포함한 PR 추가·삭제 합계는 800줄 미만이며 650줄에서 분리를 점검한다.

| PR  | 단계      | 검토 목적                    | 예상 변경량 | 초과 시 분리 경계         |
| --- | --------- | ---------------------------- | ----------- | ------------------------- |
| 1   | 1~2       | 요구사항·구현 계획·작업 목록 | 400~650줄   | 명세 / 구현 계획          |
| 2   | 3~4       | 관리자 공통 레이아웃         | 450~750줄   | 데스크톱 / 좁은 화면      |
| 3   | 5~6       | 모델·모의 데이터·필터 URL    | 300~600줄   | 모델·서비스 / 필터·라우트 |
| 4   | 7~8       | 카드·목록·상태 안내          | 450~750줄   | 목록 / 오류·빈 상태       |
| 5   | 9~10      | 생성 폼과 검증               | 400~700줄   | 입력 UI / 검증·상태       |
| 6   | 11        | 생성과 목록 연결             | 200~400줄   | 성공 연결 / 실패 복구     |
| 7   | 12-1~12-2 | 수정 폼·저장 연결            | 350~650줄   | 폼 재사용 / 수정 연결     |
| 8   | 13~14     | 삭제·최종 검증               | 350~650줄   | 삭제 / 최종 수정          |

- 첫 PR base는 main, 종속 PR base는 직전 PR이다. 아래부터 병합하고 남은 PR의 base와 diff를 재확인한다.
- 각 PR은 자체 check/build가 통과하고 비활성 버튼이나 깨진 화면을 노출하지 않아야 한다.
- 폼만 작성하는 PR 5까지는 테스트로 검증하며 생성 버튼은 PR 6에서 실제로 연결한다.
- 브랜치 생성·전환·commit·push·PR 작업은 대상과 초안이 준비된 뒤 별도 승인받는다. 현재 브랜치는 변경하지 않는다.
- 기능 복구는 관련 PR을 의존성 역순으로 되돌린다. 외부 데이터 변경과 마이그레이션이 없어 별도 데이터 복구는 없다.

3단계 리뷰에서 추가된 라우트 디렉터리 전환은 생성 파일 변경량을 포함하여 별도 PR로 분리한다.
명세 → 라우트 구조 → 공통 레이아웃 순서의 stacked PR로 두고, 각 PR의 추가·삭제 합계를 별도로 확인한다.

# 기능 명세: 현재 서버 OpenAPI 계약 동기화

**브랜치**: `chore/openapi-server-spec-refresh`
**작성일**: 2026-10-29
**상태**: 초안
**관련 이슈**: #198
**요청**: 변경된 서버 OpenAPI는 SDK 결함과 별도 브랜치에서 반영한다.

## 사용자 시나리오와 검증

### 1. 서버 계약에 맞는 SDK 사용 (P1)

개발자는 현재 서버의 경로·필드·오류 타입을 생성 SDK로 사용한다.
같은 입력의 재생성 결과가 같아야 하며 생성 파일을 손으로 보정하지 않는다.

- 서버 원본을 저장한 뒤 전체 플러그인으로 생성하면 타입·SDK·Query·Zod·MSW·Faker가 같은 계약을 가리킨다.
- 기존 함수명 충돌로 번호가 바뀌면 이름이 아닌 API 경로를 기준으로 기존 소비자를 연결한다.

### 2. 기존 개발 mock 보존 (P1)

개발자는 기존 출결보고·공지 이미지 업로드 URL·관리자 출결 목록 모킹을 계속 사용한다.
새 operation의 성공 mock이나 실제 제품 기능을 자동으로 추가하지 않는다.

- 기존 세 경로의 요청은 해당 응답 스키마에 맞는 성공 JSON을 반환한다.
- 연결하지 않은 새 operation은 기존 명세 예제 또는 501 정책을 유지한다.

## 요구사항

- FR-001: 원본은 서버에서 받은 OpenAPI를 그대로 사용한다. 과거 명세를 추측 복원하지 않는다.
- FR-002: 생성 파일 직접 수정 없이 기존 고정 도구 버전으로 생성한다.
- FR-003: 신규 API 전체를 최종 결과에 포함하고 공개 진입점도 동기화한다.
- FR-004: 단계별 PR은 같은 원본과 공식 operation filter로 일관되게 생성한다.
  800줄 미만의 안전한 분리가 불가능하면 크기 예외를 승인받기 전 commit·push·PR을 보류한다.
- FR-005: SDK #158~#161의 런타임 수정과 분리한다.

## 완료 기준

- 최종 결과가 필터 없는 전체 재생성과 파일별로 동일하다.
- 기존 mock 경로 회귀와 `node --run check`, `node --run build`가 통과한다.
- 실제 백엔드 호출·브라우저 검증과 로컬 메모리 검증을 구분한다.
- 각 PR의 base·변경량과 되돌릴 단위를 기록한다.

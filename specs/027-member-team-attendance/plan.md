# 구현 계획: 최신 API와 회원 팀 출석 운영 연결

**실제 브랜치**: DongjaJ/api-v4 | **작성일**: 2026-11-23 | **명세**: [spec.md](spec.md)
**상태**: 0단계 문서 리뷰 대기. 1A 이후 제품 구현은 시작하지 않았다.

## 요약

동일한 OpenAPI 원본으로 생성물을 단계별 갱신하고 기존 사진 입력·전송 흐름을 실제 팀 조회에 연결한다.
사진 선택 즉시 presign·PUT을 실행하고 최종 버튼은 imageKey·참석 명단만 전송한다.
홈과 코드 제출 경계 모두 REGULAR/TEAM을 구분하고 최신 서버 출석 상태를 따른다.

## 기술 맥락

- Node 24.20.0, pnpm 12.3.4, TypeScript 6.0.3, Hey API 0.99.0을 유지한다.
- React 19.3.0, TanStack Query 5.102.8·Form 1.33.5, Zod 4.5.4, SEED·Stackflow·ky를 재사용한다.
- 대상은 iOS WebView 회원 웹과 공용 API다. 관리자는 함수명 변경 호환만 수정한다.
- Vitest·Testing Library·MSW와 실제 iPhone 수동 검증을 사용한다. 새 성능 수치·의존성·저장소는 없다.
- 서버 조회는 Query, 전송은 Mutation, 사진·키·참석자 초안은 활성 화면 흐름에서 소유한다.
- 공용 사진 브리지·네이티브 설정·로그인·기존 정규 출석 100m 판정은 변경하지 않는다.
- API 원본·변경 근거는 [조사](research.md), 상태·수명은 [데이터 모델](data-model.md),
  공개 인터페이스는 [계약](contracts/team-attendance.md), 검증은 [실행 절차](quickstart.md)를 따른다.

## 문서와 코드 구조

현재 디렉터리는 명세·계획·조사·데이터 모델·계약·작업·검증·체크리스트를 소유한다.

- packages/api: 생성물, 기존 mock과 소비자 호환. 원본은 .context/api-027-openapi.json에 보관한다.
- apps/web/src/features/team-attendance: 실제 대상·사진 조회, 업로드와 최종 접수, 검증된 공개 입력.
- apps/web/src/pages/team-attendance-upload: 사진 입력·미리보기와 참석자 폼.
- apps/web/src/pages/home: 유형·상태 판정, 안내 시트, 정규 코드 제출 조건.
- apps/web/stackflow/src/activities: 대상 ID·일회성 도구 선택·접수 결과의 화면 수명과 탐색.
- apps/web/src/mocks: 개발·테스트 시나리오. 다른 앱·같은 레이어 내부 import는 추가하지 않는다.

모든 행은 사용자 리뷰 단위다. 0단계가 끝나도 1A를 자동 시작하지 않는다.
1A~1D도 각 소비자 수정·검증을 포함하고 리뷰 후 이어간다. 운영 진입은 6단계에서만 연다.
제품 변경 전 Modern Web Guidance 1.0.0을 조회하며 새 파일·공개 export의 한국어 책임 주석을 확인한다.

## 생성 분할과 기존 PR

1A는 주간 find4→find6, 일정 find5→find7, 내역 find6→find8, 보존 이력 find7→find9를 이관한다.
1B는 관리자 세션 find1→find2, 프로필 find2→find3, 알림 find3→find4를 이관한다.
사용자 요청으로 1C·1D는 분할하지 않고 팀원 GET(find5)·사진 GET(find1)을 한 번에 포함한다.
최종 생성 설정에는 operation 필터·이름 변환을 남기지 않는다. 원본 파일은 편집하지 않는다.

기존 [PR #503](https://github.com/YAPP-admin/yapp-plus-frontend/pull/503)은 참고·재사용 대상이다.
서버 상태 표시·복귀 훅 확장은 겹치지만 장소 판별, 코드 제출의 유형 제한 누락,
심사 중에 한정한 강제 갱신은 이번 계약과 다르다. 선행 머지를 전제하지 않고 실제 구현 직전
main 반영 여부를 확인해 중복 변경을 피한다. 이 문서 작성은 PR 수정·머지 승인이 아니다.

## 검증과 복구

각 단계에서 인접 회귀 테스트와 node --run check, 배포 앱·공용 SDK 변경에는 node --run build를 수행한다.
문서만 바꾸는 0단계는 check와 문서 링크·작업 형식을 확인하고 build·실기기는 수행하지 않는다.
네이티브 설정·의존성을 실제 바꿀 경우에만 expo:doctor를 추가한다.
신규 실행·Turbo 캐시·실패·미실행을 분리하고 650줄부터 분리를 검토한다.
각 PR의 실제 base 대비 추가·삭제 합계는 문서·생성물까지 800줄 미만이어야 한다.
0단계 문서와 후속 생성물을 같은 PR에 누적하지 않고, 브랜치·PR 작업은 별도 승인 후 수행한다.

실패 시 팀 인증 운영 진입을 차단하고 기능 변경을 되돌린다. SDK 복구에는 소비자도 함께 포함한다.
서버 사진은 프런트 롤백으로 삭제되지 않는다. 미접수·교체 사진 정리는 백엔드 정책에 맡기며
에이전트가 실제 제출·삭제·배포를 자동 실행하지 않는다.

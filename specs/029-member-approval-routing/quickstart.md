# 검증 안내

## 준비

고정 Node.js·pnpm과 설치된 의존성을 사용한다. API 원문은 .context/approval-openapi.json에 두며
재생성 입력 해시를 validation.md에 기록한다. 실제 서버 쓰기·계정 변경·배포는 별도 승인 대상이다.
자동 테스트는 합성 계정과 MSW·브리지 대역을 사용하고 토큰·개인 정보를 로그에 출력하지 않는다.

## 단계별 명령

```sh
pnpm --filter @yapp-plus/app-bridge test
pnpm --filter @yapp-plus/mobile test
pnpm --filter @yapp-plus/web test
node --run check
node --run build
```

개별 테스트는 변경 경계에 필요한 것만 먼저 실행한다. check가 이미 실행한 검사를 이유 없이 반복하지 않는다.
문서 단계는 형식·링크·작업 추적 확인과 기본 check를 수행한다. build는 제품 단계부터 적용한다.
모바일 설정·의존성을 변경한 경우에만 `node --run expo:doctor`를 실행한다.

## 계층별 수용 시나리오

| 계층   | 입력·행동                                 | 기대 결과                                         |
| ------ | ----------------------------------------- | ------------------------------------------------- |
| native | Google·Apple PENDING, 가입 PENDING        | 제한 결과, 새 SecureStore 토큰 기록 0회           |
| native | APPROVED, 신규 가입 APPROVED              | 기존 세션 저장·확정                               |
| native | REJECTED·null·필드 누락·잘못된 값         | 세션 확정 없음, 제한 또는 INVALID_RESPONSE        |
| native | PENDING → 복귀 → 같은 계정 APPROVED       | 승인 전환 1회, 이력 소비                          |
| native | 다른 계정 승인·취소·일시 실패             | 이력 오적용 없음, 취소·일시 실패는 성공 소비 없음 |
| native | 삭제·저장 실패, 늦은 응답, 로그아웃 경합  | 복구 정책 유지, 이전 세션 부활·새 계정 삭제 없음  |
| native | 기존 저장 세션·refresh                    | 기존 자동 로그인 유지                             |
| 웹     | 상태별 브리지 결과                        | 계약 표의 목적지로 한 번만 이동                   |
| 웹     | 제한 상태의 직접 URL·pop·딥링크           | 보호 화면 렌더·업무 Query 실행 없음               |
| 웹     | 대기 뒤로가기 확인·취소·실패·연타         | Login 또는 대기 유지, 중복 정리 없음              |
| 웹     | 에러 뒤로가기·구버전 결과                 | Login 복귀·기존 로그인 호환                       |
| 실기기 | 대기 후 백그라운드 복귀                   | 대기 유지, 자동 서버 재조회 없음                  |
| 실기기 | 대기 후 완전 종료·재실행                  | Login, 승인 로그인 시 홈                          |
| 실기기 | 같은 실행 중 같은 대기 계정 재로그인 승인 | SignupComplete → 시작하기 → 홈                    |
| 접근성 | 뒤로가기·Dialog 키보드·터치·VoiceOver     | 이름·포커스·취소·오류 전달 정상                   |

서버 발급 토큰·계정 상태 분기는 native 단위에서, 화면 이동은 웹 통합에서 검증한다.
같은 토큰 파싱 실패를 모든 계층에 복제하지 않는다. 실기기 미실행은 자동 테스트 통과로 대체하지 않는다.

실기기 검증은 사용자 요청에 따라 배포 후 사용자가 진행한다. 위 실기기·실기기 접근성 시나리오는
그때 실행하고 결과를 기록하며, 현재 자동 검증 통과와 구분한다. 이 결정은 배포 실행 승인이 아니다.

## 배포 전 확인

웹의 새 계약 소비 SHA가 운영 대상 URL에 있는지 먼저 확인한다. 그 뒤 native 적용 SHA·runtime을 기록한다.
새 native+새 웹, 구 native+새 웹 조합을 검증하며 새 native+구 웹 조합은 배포하지 않는다.
실패 시 native 활성화 전은 웹 복구, 활성화 후는 새 계약 소비 웹 유지 또는 native 선복구 순서다.

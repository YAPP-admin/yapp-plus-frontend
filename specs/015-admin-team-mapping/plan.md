# 구현 계획: 관리자 팀 매핑 화면

**실제 브랜치**: `DongjaJ/team-mapping-plan` | **작성일**: 2026-11-02
**명세**: [spec.md](spec.md) | **상태**: 6단계 팀 생성 폼 구현·사용자 리뷰 대기

## 요약과 기술 맥락

개발·운영 모두 같은 읽기 전용 fixture를 공급하고 화면·입력·변경 예정만 구현한다.
최종 실행은 비활성이며 API·Query/Mutation·모의 저장소·localStorage를 추가하지 않는다.

- TypeScript 6·React 19·TanStack Start/Router/Form·Zod 4·SEED·vanilla-extract·overlay-kit을 유지한다.
- Node.js 24.20.0·pnpm 12.3.4, Vitest·Testing Library와 실제 브라우저로 검증한다.
- 관리자 데스크톱·375px 대상이다. 기본 사례는 52명·8팀, 새 성능 SLA·페이지네이션·가상화는 없다.
- 새 의존성·공용 패키지는 없다. 기존 UI 공개 진입점과 SEED Dialog·SidePanel·Menu·Select를 사용한다.
- 문서·모델·UI 단계는 [tasks.md](tasks.md), 사용자 경계는 [화면 계약](contracts/team-mapping-ui.md)을 따른다.

설계 후에도 위 경계를 유지한다. 외부 계약 검증은 후속이며 현재 원본 OpenAPI 확인 완료로 주장하지 않는다.

.specify/feature.json은 명세 위치만 지정한다. setup-plan 출력의 feature 이름은 실제 Git 브랜치 변경이 아니다.

## 구조와 책임

- `apps/admin/src/features/team-management/`: 읽기 전용 화면 타입·집계·검색·입력/예정 검증·fixture, index.ts와 fixtures.ts 공개 진입점.
- `apps/admin/src/pages/team-mapping/`: URL 스키마·입력·패널·체크·변경 예정·이탈 확인. 파일은 model/와 ui/로 나눈다.
- `apps/admin/src/routes/_dashboard/members/teams.tsx`: 환경 분기 없는 공급과 URL 연결. 기존 app/ui/는 탐색 연결만 수정한다.
- 기존 회원 목록 안내에 진입 링크만 추가한다. 회원 fixture 공급·기존 공지 이탈 처리는 변경하지 않는다.
- 실제 필요한 작업별 상태를 둔다. 다른 팀 초안을 누적하는 저장소·예상 통계 캐시는 만들지 않는다.

## 단계와 PR 경계

각 행 완료 후 결과를 제출하고 사용자 확인 전 다음 행을 구현하지 않는다.
예상 추가+삭제 줄 수는 테스트·스타일·문서를 포함한 계획치이며 실제 diff로 재판정한다.

| 단계 | 검토 결과                             | 관련 요구      | 예상 줄 수 |
| ---- | ------------------------------------- | -------------- | ---------- |
| 1    | 명세·설계·작업·검증·이슈 초안         | 전체           | 450~650    |
| 2    | 화면 모델·집계·검색·예정 검증         | FR-003~008     | 350~650    |
| 3    | 합성 fixture·상태 공급                | FR-001         | 200~400    |
| 4    | 경로·하위 메뉴·진입 링크·빈 화면      | FR-001~002     | 350~650    |
| 5    | 팀 카드·필터·개수·URL 복원            | FR-003·005     | 350~650    |
| 6    | 생성 폼·필수 입력·초안 비교           | FR-004·011     | 300~550    |
| 7    | 후보 검색·선택·구성·최소 인원         | FR-004·007     | 350~650    |
| 8    | 상세 패널·회원 메뉴·변경 예정         | FR-006~007·011 | 400~650    |
| 9    | 미배정 개별·일괄 대상 선택            | FR-008         | 350~650    |
| 10   | 작업 종료·URL 이동·브라우저 이탈 보호 | FR-009         | 350~650    |
| 11   | 확정 요약·이력·팀원 편집 모드         | FR-010~011     | 350~650    |
| 12   | Figma·개발/운영·접근성·회귀 증거      | FR-001·012     | 200~450    |

4단계는 생성 진입 의도/callback을 검증하고 실제 폼 연결은 6단계에서 검증한다.
5단계의 상세 진입도 callback까지, 실제 패널은 8단계, 미배정 본문은 9단계에서 완성한다.
중간 화면에서 미구현 조작은 비활성으로 표시하며 임시 빈 handler를 완성 동작처럼 노출하지 않는다.
6~9단계의 초안은 메모리에 두고 이탈 보호 통합 완료 여부를 10단계까지 미완료로 보고한다.

650줄부터 분리를 검토하고 800줄 이상은 제출하지 않는다. 초과가 예상되면 단계 구현 전 하위 리뷰 단위를 제안한다.
각 단계 PR은 기본 main, 선행 변경 병합 후 다음 PR 진행이다. commit 분리로 PR 크기를 우회하지 않는다.
브랜치 생성·변경·commit·push·PR 작업은 각각 명시적 승인을 받은 뒤 수행한다. 1·2단계 변경은 승인된
commit과 Draft PR로 분리했으며, 이후 단계도 같은 검토 단위를 유지한다.

## 검증과 복구

[quickstart.md](quickstart.md)의 검증을 실행하고 [validation.md](validation.md)에 실제 결과를 기록한다.
UI 구현 시 Figma context를 재확인하고 정확히 일치하는 기존 자산·컴포넌트를 재사용한다.
고유 정적 자산이 필요하면 공식 응답의 다운로드 지침으로 로컬화하고 화면 캡처를 제품 자산으로 쓰지 않는다.
데이터·인증·배포 변경과 마이그레이션은 없다. 복구는 해당 독립 변경을 되돌리는 방식이다.

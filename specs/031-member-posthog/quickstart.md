# 검증 안내

이 문서는 향후 구현 검증 절차다. 현재 구현·PostHog 프로젝트 생성·실기기 검증 완료를 뜻하지 않는다.

## 준비

- 저장소 mise 도구와 의존성을 준비하고 이슈 및 해당 단계 리뷰를 확인한다. [계획](plan.md)의 기준 commit과 현재 main 차이를 다시 점검한다.
- 개발 프로젝트 수집 키만 로컬 검증에 사용한다. 모킹 모드는 수집하지 않으므로 수신 검증은 개발 환경의 실제 흐름에서 진행한다.
- 소스맵 업로드 권한은 CI/EAS 비밀 값으로 설정한다. 키·회원 개인정보가 포함된 화면이나 로그를 증거로 저장하지 않는다.
- iOS native 변경은 새 개발/릴리스 바이너리를 준비한다. JS OTA만으로 새 native SDK 설치를 검증하지 않는다.

## 단계별 자동 검증

| 단계   | 가장 가까운 검증 계층                | 확인할 결과                                                                                     |
| ------ | ------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 기반   | 설정·전송·식별·활성 상태 단위 테스트 | 설정 누락·Preview·모킹 비활성화, 계정 분리, 구형 브리지 fallback, SDK 오류 격리                 |
| 인증   | 기존 인증 mutation·이동 통합 테스트  | SIGNUP_REQUIRED/REVIEW_REQUIRED/SIGNED_IN 각 1회, 취소·복원·갱신 0회, 가입 신청 별도 1회        |
| 출석   | 기존 시트·mutation 테스트            | 실제 서버 제출만 횟수 증가, 실패·재시도 결과, 제출 성공과 닫기 이탈 구분                        |
| 조회   | 활성 화면·탐색 테스트                | 숨겨진 탭·refetch 0회, 홈 복귀 1회, 공지 전면 시간, 푸시 ack 재시도 0회 추가                    |
| 모바일 | 설정·배포 정책 테스트                | iOS 오류만 활성화, Android 비활성화, 공개 extra에 비밀 없음, runtime 구분·동일 산출물 맵 업로드 |

실제 SDK 내부 구현을 다시 시험하지 않고 프로젝트의 변환·설정·사용자 흐름을 검증한다.

```sh
mise exec -- node --run check
mise exec -- node --run build
mise exec -- node --run expo:doctor
```

check는 기본 게이트다. build는 배포 가능한 앱·빌드 설정 변경, expo:doctor는 모바일 설정·의존성 변경 시 실행한다.
문서 초안 단계는 문서 구조·계약 개수·로컬 링크를 별도로 검사하며 build·doctor는 해당하지 않는다.

## 실제 수신·녹화

1. 개발 프로젝트에서 구현 대상 24개를 각각 재현하고 이름·속성·횟수를 [이벤트 계약](contracts/events.md)과 대조한다. 누락 속성이 null/0/임의 ID로 대체되지 않았는지 확인한다.
2. 알림 목록 클릭은 in_app, 푸시는 push다. 같은 푸시의 재전달·처리 확인 실패는 추가 기록이 없고 같은 알림을 다시 누른 실제 클릭은 별도 기록이어야 한다.
3. 공지를 전면 5초→백그라운드 10초→전면 5초 후 확인하면 read_seconds는 약 10초이며 20초가 아니다. 실측 허용 오차는 ±1초로 둔다.
4. 가짜 이름·전화번호·사유·사진과 query/hash 토큰을 사용해 전송 payload와 실제 녹화를 확인한다. 동적 aria-label/title·링크·이미지 주소도 검사한다.
5. 계정 A→로그아웃→계정 B에서 B의 기록·녹화가 A에게 붙지 않는지 확인한다. 탈퇴도 동일하게 확인한다.
6. 개발 수신이 운영 프로젝트로 가지 않는지 확인한다. 수집 off·네트워크 차단에서도 로그인·출석·공지 흐름이 완료되어야 한다.
7. 브라우저와 iOS WebView를 확인하고 기존 Android WebView 웹 수집은 가능 환경에서 별도로 기록한다. Android native 모니터링 출시 검증은 이번 범위가 아니다.

## iOS 오류·OTA

1. 검증 전용 릴리스 빌드에서 처리되지 않은 JS 오류와 native crash를 각각 1회 발생시킨다. 테스트 트리거는 운영 UI에 남기지 않는다.
2. 다음 실행 후 개발 프로젝트에 오류가 수신되는지, 원본 함수·파일·라인 및 앱 버전·build·runtime·update ID가 맞는지 확인한다.
3. 같은 오류를 새 OTA에서도 재현해 이전/새 업데이트 소스 위치를 각각 확인한다. 다른 export의 맵이 연결되면 실패다.
4. 업로드 실패 시 배포가 중단되는지, 새 runtime OTA가 구형 바이너리 대상이 아닌지 배포 정책 테스트와 실제 채널로 확인한다.
5. native 행동·화면·생명주기 이벤트와 녹화가 추가로 수집되지 않는지 확인한다. SDK 초기화 전 장애·강제 종료의 수신 보장은 검증 완료 조건에 넣지 않는다.

## 증거와 종료

단계별 결과에 기준 SHA, 신규 실행/캐시 재사용, 통과/실패/미실행, 실제 환경과 재현 결과를 기록한다.
외부 서비스·실기기가 없으면 해당 항목을 미실행으로 남기며 수신·마스킹·크래시 검증을 완료 처리하지 않는다.
운영 전환 전 웹 비활성화·호환 OTA 복구·새 바이너리 복구 경로를 리뷰하고 검증된 main SHA에 연결한다.

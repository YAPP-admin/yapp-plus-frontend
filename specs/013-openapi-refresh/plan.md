# 구현 계획: 현재 서버 OpenAPI 계약 동기화

**브랜치**: `chore/openapi-server-spec-refresh` | **작성일**: 2026-10-29
**명세**: [spec.md](./spec.md)

## 요약

서버 원본을 한 번 받아 재생성하고 기존 소비자의 API 경로 의미를 보존한다.
생성 파일별 분할은 하지 않는다. 기능군별 operation filter가 각 단계의 일관성과
800줄 제한을 만족하는지 조사한 뒤 PR 구성을 결정한다.

## 기술 맥락

TypeScript 6.0.3, Node.js 24.20.0, pnpm 12.3.4, Hey API 0.99.0을 사용한다.
대상은 `packages/api`와 해당 공개 API를 사용하는 관리자·웹이다.
지속 데이터 변경과 새 의존성은 없다. 검증은 기존 Vitest와 root check·build를 사용한다.

## 지침 확인

헌장 파일은 아직 템플릿이므로 검증 통과로 간주하지 않고 AGENTS.md를 적용한다.
생성 코드 직접 수정 금지, 한국어 문서, 공개 진입점, 고정 도구 버전을 지킨다.
전체 생성 diff 3,244줄을 기능군별 재생성 스택으로 분리한다. 기존 계약 갱신은 466줄이며
후속 신규 operation 추가도 각각 650줄 미만이었다. 각 최종 PR은 문서·소비자 변경을 합산해 다시 확인한다.

## 변경 위치

- `packages/api/src/generated`: 같은 서버 원본에서 도구가 생성한다.
- `packages/api/src/mocks/handlers.ts`: 기존 경로의 새 operation 이름으로 연결한다.
- `apps/admin/src/mocks`: 기존 경로와 응답 스키마 회귀를 검증한다.
- `packages/api/README.md`: 원본 기준일과 미연결 신규 mock 범위를 갱신한다.

## 작업 순서

1. 원본 SHA-256·도구 버전·기존 및 신규 operation을 기록한다.
2. 공식 filter 기반 단계별 생성 diff 크기를 조사한다.
3. 각 단계의 기존 mock 연결을 갱신하고 check·build를 실행한다.
4. 최종 전체 결과와 재생성 일치를 확인하고 Draft PR을 만든다.
5. SDK 결함 수정은 이 계약 갱신 위의 별도 브랜치에서 수행한다.

## 롤백

생성 결과와 mock 연결을 같은 PR 단위로 되돌린다. 서버 자체를 변경하지 않는다.
함수명 변경을 소비한 후속 PR이 있으면 함께 되돌리거나 이전 공개 이름으로 소비자를 복구한다.
실제 인증·데이터 마이그레이션은 이 작업에 포함하지 않는다.

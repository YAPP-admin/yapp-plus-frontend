# 구현 계획: 로그인 응답 기반 가입 승인 처리

**브랜치**: `DongjaJ/yapp-approval-screen` · **날짜**: 2026-11-26 · [명세](spec.md)
**상태**: 이슈 #599 연결 완료. native·웹 승인 분기 구현 후 자동 검증을 보완 중이며,
실기기·접근성 검증과 PR 분리·배포 조합 확인은 남아 있다. 세부 완료 상태는 tasks.md를 따른다.

## 요약

로그인·가입 응답의 승인 상태를 native에서 세션 저장 전에 판정한다. 웹은 토큰 없는 제한 결과로
기존 대기·에러 화면을 연결한다. APPROVED만 새 정상 세션을 저장하되 기존 저장 세션은 유지한다.

## 기술 맥락

- 언어·플랫폼: TypeScript, iOS Expo/React Native WebView, React·Stackflow 회원 웹.
- 기존 의존성: 생성 API·Zod, TanStack Query, SEED Dialog, SecureStore. 새 의존성 없음.
- 도구: Node.js 24.20.0, pnpm 12.3.4. 실행 시 저장소 고정 버전을 재확인한다.
- 저장: 기존 승인 세션 저장 형식 유지. 승인 제한 결과와 대기 계정 ID는 native 메모리만 사용한다.
- 검증: Vitest·Testing Library·MSW, check·build, iOS 실기기. 다른 계층에서 같은 실패를 중복 검증하지 않는다.
- 성능·범위: 승인 확인용 HTTP 호출·타이머를 추가하지 않는다. API·브리지·mobile·web만 영향받는다.

## 구조와 공개 계약

문서는 이 디렉터리의 spec·research·data-model·contracts·quickstart·tasks·validation을 사용한다.
실제 수정 대상은 아래 기존 경계다. 구체 작업 파일은 [작업 목록](tasks.md)에 적는다.

- `packages/api`: 고정 OpenAPI 입력으로 생성 타입·스키마·fixture 갱신.
- `packages/app-bridge`: REVIEW_REQUIRED와 필수 승인 전환 정보 추가. 누락된 전환 값은 INVALID_RESPONSE로 거부하고 AuthSession·RPC 메서드는 유지.
- `apps/mobile/src/auth`: 로그인·가입 판정, 메모리 제한 상태·대기 이력, 기존 세대·정리 경계 재사용.
- `apps/web`: 인증 결과 소비·계정 캐시·진입 가드·화면 복귀. 마이페이지 Query는 변경하지 않는다.

## 단계별 구현

### 0단계 — 문서와 이슈 초안

정책·계약·단계·테스트·호환 예외를 문서화한다. 관련 이슈 조회 후 별도 초안을 준비한다.
완료 기준: 문서 품질·링크·작업 형식 확인, 크기 및 검증 결과 보고, 사용자 리뷰.

### 1단계 — 생성 API 계약

최신 OpenAPI를 .context에 고정하고 생성 명령으로 reviewStatus 타입·스키마를 갱신한다.
기존 인증 정상 fixture에 APPROVED를 명시한다. 실제 인증 동작은 아직 변경하지 않는다.
무관한 생성 변경이 있으면 원인을 분리해 보고하며 생성 파일을 손으로 고치지 않는다.
완료 기준: 동일 입력 재생성 일치, 관련 인증 테스트·타입 검사·check 통과 및 리뷰.

### 2단계 — 브리지 계약과 웹 소비부

새 제한 결과와 필수 승인 전환 정보를 정의하고 모든 소비부의 분기를 갱신한다. 새 native는 모든
SIGNED_IN에 NONE 또는 PENDING_TO_APPROVED를 보내며, 웹 수신 경계에서도 누락된 값은 INVALID_RESPONSE로 거부한다.
실제 native는 아직 새 결과를 내보내지 않는다. 웹은 fixture로 대기·에러·완료 이동을 검증한다.
제한 결과도 인증 의도 확정으로 처리해 이전 업무 캐시·늦은 조회를 정리한다.
로그인 자동 이동과 가입 callback은 같은 이동 판단을 사용해 홈/완료 화면 경쟁을 막는다.
진입 가드·pop 복원 경계는 제한 상태의 보호 내용과 업무 Query를 차단한다.
완료 기준: 새 결과의 필수 필드 검증과 구버전 누락 거부 모두 처리, typed 경계·통합 탐색 테스트·check·build 통과 및 리뷰.

### 3단계 — 기존 뒤로가기 연결

대기 화면의 기존 뒤로가기에 SEED 확인 Dialog를 연결한다. 제목은 “로그인 화면으로 돌아갈까요?”,
버튼은 “취소”와 “로그인으로 돌아가기”다. 확인 후 정리에 성공하면 Login으로 replace한다.
정리 실패는 대기에 머물며 “로그인 화면으로 돌아가지 못했어요. 다시 시도해 주세요.”로 재시도를 안내한다.
에러 화면의 뒤로가기도 가입 입력·보호 화면이 아닌 Login으로 연결한다.
공통 BackButton의 다른 소비자, 대기 일러스트·애니메이션·하단 구성은 유지한다.
완료 기준: 확인·취소·중복 방지·실패 복구·왕복 방지, 터치·키보드·VoiceOver, check·build 및 리뷰.

### 4단계 — native 승인 판정 활성화

응답의 result를 먼저 구분한다. SIGNUP_REQUIRED는 유지하고 SIGNED_IN은 사용자·reviewStatus를 검증한다.
APPROVED만 자격 검증 후 establish한다. 나머지는 기존 세션을 정리하고 토큰 없는 결과를 반환한다.
정리 중 세대 변경·저장 실패를 감추지 않는다. 취소된 이전 응답이 새 계정을 지우지 않게 한다.
getSession은 실행 중 제한 결과를 복원하되 refreshSession은 정상 세션을 만들 수 없다.
마지막 PENDING 계정 ID는 메모리에만 두고 같은 계정의 승인 전환을 한 번 전달한다. 그 외 정상
SIGNED_IN에는 항상 NONE을 전달한다.
제한 결과에서는 정상 세션 구독자가 실행되지 않아 푸시 등록도 시작하지 않는다.
완료 기준: 상태·저장·이력·경합·기존 복원 회귀 테스트, check·build와 사용자 리뷰.

### 5단계 — 통합 검증과 배포 준비

[검증 안내](quickstart.md)의 계층별 시나리오를 수행하고 실행 SHA·결과·미실행을 기록한다.
모바일 설정·의존성 변경 시에만 expo:doctor를 추가한다. 이번 계획에는 해당 변경이 없다.
완료 기준: 자동·실기기 결과와 호환 조합 확인, 사용자 최종 리뷰. 실제 배포는 별도다.

## 변경 크기와 의존성

0 → 1 → 2 → 3 → 4 → 5 순서로 리뷰한다. 제품 단계별 수용 기준은 [작업 목록](tasks.md)에서 추적한다.
한 단계가 한 PR을 보장하지 않는다. 생성 코드·문서·테스트 포함 650줄부터 분리를 검토하고
800줄 이상이면 다음 구현 전에 독립 검토 단위로 나눈다. 분리용 Git 작업은 별도 승인받는다.
US1의 웹 분기는 2단계에서 독립 검증하되 사용자에게 실제 기능이 완성되는 시점은 4단계 이후다.

## 호환 배포와 복구

1. 새 결과를 이해하는 웹을 먼저 배포한다. 기존 앱의 필드 없는 SIGNED_IN은 INVALID_RESPONSE로 거부한다. OTA 적용 전 로그인 실패는 허용하며 강제 업데이트 흐름은 추가하지 않는다.
2. 그 웹 SHA가 실제 대상 URL에서 제공되는 것을 확인한 뒤 native 판정을 활성화한다.
3. 기존 모듈의 TypeScript 변경만이면 현재 호환 runtime의 JS 업데이트 경로를 사용한다.
4. 설정·모듈 변경이 필요해지면 범위를 재검토하고 새 빌드 여부를 결정한다. 이번에 미리 변경하지 않는다.
5. native 활성화 후 웹만 이전 계약으로 되돌리지 않는다. 필요하면 native 분기를 먼저 복구한다.

롤백은 새 승인을 확인하지 않던 기존 동작을 복원할 수 있다. 서버 업무 권한은 항상 별도 책임이다.
새 앱이 복원하는 기존 세션의 승인 미검사와 승인 후 상태 변경의 미반영은 사용자 확정 예외다. 복구 시 웹과 native의 계약을 함께 확인한다.

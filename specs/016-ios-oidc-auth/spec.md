## 사용자 시나리오와 검증

### US1 — 기존 회원 로그인 (P1)

회원은 iOS 앱에서 Apple 또는 Google 계정으로 로그인하고 자신의 활동 화면에 진입한다.
두 제공자 중 하나만 사용해도 같은 회원 경험을 제공하므로 최우선이다.

**독립 검증**: 각 제공자의 성공·취소·실패 응답을 주입하고 화면과 인증 상태를 관찰한다. 실제 계정 인증 성공은 후속 실기기 검증으로 구분한다.

1. 로그아웃 상태에서 기존 회원 인증이 성공하면 인증 화면을 벗어나 회원 화면으로 이동한다.
2. 사용자가 인증을 취소하면 가입이나 회원 화면으로 이동하지 않고 다시 로그인할 수 있다.
3. 인증 실패 또는 네트워크 장애가 발생하면 성공으로 표시하지 않고 오류에 맞는 재시도 안내를 제공한다.
4. 지원하지 않는 앱 버전이나 일반 브라우저에서는 가짜 로그인 대신 지원 환경 안내를 제공한다.

### US2 — 신규 회원 가입 (P1)

신규 사용자는 소셜 인증 후 이름과 한국 휴대전화번호로 가입한다. 계정 생성과 활동 권한을 구분한다.

**독립 검증**: 가입 필요 상태를 주입해 입력 오류·중복·만료·가입 성공을 확인한다.

1. 신규 인증 결과를 받으면 이름·휴대전화번호 입력 화면을 표시한다.
2. 필드 오류가 있으면 해당 필드에 안내하고 입력 내용을 보존한다.
3. 가입 자격이 만료되거나 앱 종료로 사라졌으면 소셜 인증부터 다시 시작한다.
4. 가입 성공이면 가입 완료 화면을 표시한다. 서버가 제공하지 않은 승인 상태는 표시하지 않는다.
5. 가입 응답 유실로 완료 여부를 알 수 없으면 소셜 재인증으로 상태를 확인한다.

### US3 — 로그인 유지와 로그아웃 (P1)

회원은 앱 재실행 후 유효한 세션을 복구하며, 로그아웃한 뒤 이전 계정 화면으로 돌아갈 수 없다.

**독립 검증**: 유효·무효·일시 장애 세션과 지연된 응답을 주입한다.

1. 유효한 세션은 앱 재실행과 웹 화면 새로고침 뒤 복구된다.
2. 일시 장애는 세션 만료와 구분해 재확인을 제공한다. 보호된 화면은 확인 전 노출하지 않는다.
3. 여러 요청이 동시에 만료되어도 세션 갱신은 중복 실행되지 않는다. 갱신 후 늦게 도착한 이전 인증 정보의 오류는 불필요한 추가 갱신을 만들지 않는다.
4. 로그아웃 후 늦은 인증 응답이나 뒤로가기가 이전 계정을 복원하지 않는다. 계정 변경 뒤 이전 요청을 새 계정으로 재전송하지 않는다.
5. 서버 로그아웃 실패와 기기 내 로그아웃 완료를 구분하여 안내한다.

### US4 — 실제 계정 탈퇴 (P2)

회원은 탈퇴 범위를 확인하고 계정 탈퇴를 요청한다. 단순 화면 이동으로 탈퇴를 대신하지 않는다.

**독립 검증**: 탈퇴 성공·실패·응답 유실을 주입한다. 실제 삭제는 별도 테스트 계정으로 검증한다.

1. 확인 화면은 모든 기수 소속이 탈퇴 대상임을 알리고 취소를 허용한다.
2. 서버의 탈퇴 성공을 확인한 경우에만 완료를 표시하고 기기 내 인증·사용자 데이터를 정리한다.
3. 오류나 응답 유실이면 성공으로 표시하거나 파괴적 요청을 자동 반복하지 않는다.

### 경계 사례

- 로그인 중 중복 탭, 웹 새로고침, 화면 이탈, 로그아웃, 늦은 SDK 응답.
- 인증 응답 누락·잘못된 값, 안전한 저장소 쓰기 실패, 이미 사용된 갱신 토큰.
- 전화번호 중복과 소셜 계정 중복: 클라이언트가 다른 계정을 임의로 연결하지 않는다.
- 활동 권한 부족은 인증 만료가 아니다. 자동 로그아웃이나 무한 갱신으로 처리하지 않는다.
- 앱 재설치만으로 로그아웃됐다고 보장하지 않는다. 남아 있는 자격 증명은 서버 검증 후 복구한다.

## 요구사항

### 기능 요구사항

- **FR-001**: 두 제공자의 로그인 결과와 사용자 취소를 구분해야 한다. (US1)
- **FR-002**: 매 인증 시도는 새 확인값을 사용하고 이전 인증 결과를 재사용하지 않아야 한다. (US1)
- **FR-003**: 신규 가입은 이름과 `010-0000-0000` 형식의 한국 휴대전화번호만 받고 필드 오류·중복·만료를 구분해야 한다. 전송 직전에만 API가 요구하는 E.164 형식으로 변환한다. (US2)
- **FR-004**: 갱신·가입용 자격 증명은 웹 저장소·URL·로그에 노출하지 않아야 한다. (US1–US4)
- **FR-005**: 세션 복구·갱신과 일시 장애를 처리하고 로그아웃 뒤 늦은 응답을 무효화해야 한다. (US3)
- **FR-006**: 로그아웃·계정 변경 시 사용자별 캐시와 화면 기록을 정리해야 한다. (US3)
- **FR-007**: 탈퇴는 서버 성공에 따라 처리하고 오류·응답 유실을 성공으로 표시하지 않아야 한다. (US4)
- **FR-008**: 지원하지 않는 환경·버전은 기능 안내를 제공하고 인증을 우회하지 않아야 한다. (US1)
- **FR-009**: 인증 유효성과 활동 권한을 구분하고 승인 정책을 임의로 구현하지 않아야 한다. (US1–US2)
- **FR-010**: 자동 검증 완료, 실기기 연동 완료, 내부 배포 완료를 별도로 기록해야 한다. (전체)

### 주요 개체

- 인증 시도: 제공자, 진행 상태, 일회용 확인값, 현재 세션 변경 여부.
- 서비스 세션: 유효기간과 갱신 자격, 현재 사용자 식별값.
- 가입 대기: 제한된 유효기간 동안 이름·전화번호 입력을 완료할 자격.
- 오류 결과: 취소, 잘못된 입력, 재인증 필요, 일시 장애, 결과 불명확, 지원하지 않는 환경.

## 성공 기준

- **SC-001**: 두 제공자의 성공·취소·실패 시나리오가 각각 기대한 상태와 화면으로 끝난다.
- **SC-002**: 가입 필드 오류·중복·만료·응답 유실 시 잘못된 가입 완료 표시가 0건이다.
- **SC-003**: 동시 갱신 및 로그아웃 뒤 늦은 응답 시나리오에서 이전 계정 복원이 0건이다.
- **SC-004**: 탈퇴 실패·응답 유실을 성공으로 표시하는 사례가 0건이다.
- **SC-005**: 실기기·백엔드 미확인 항목이 검증 기록에 명시되고 다음 단계 승인 없이 구현이 진행되지 않는다.

## 가정과 범위

- 대상은 YAPP 구성원의 iOS 앱과 내부 테스터다. dev 백엔드를 사용한다.
- 가입 승인·반려·재신청 UI, Android, 일반 브라우저 로그인, 운영 출시·OTA는 제외한다.
- 내부 실제 활동 검증에는 승인된 테스트 계정을 사용한다. 권한 검사를 우회하지 않는다.
- 백엔드 CORS·Apple 오류 명세 수정은 요청 후 대기 중이다. 선행 구현과 자동 검증을 막지 않는다.
- 실기기는 현재 사용할 수 없다. 실제 로그인·서명·TestFlight 설치 성공을 가정하지 않는다.

## #329 보완 요구사항 — 2026-11-05

기준은 `origin/main`과 HEAD `9186dc6`이다. 기존 체크 완료는 아래 결함의 해결 증거가 아니다.

| ID  | 대상                  | 수용 기준                                                                                                                                                                      |
| --- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | US1·US2·US3 인증 경합 | 로그인·가입·복구·갱신의 늦은 결과가 로그아웃 이후 메모리·SecureStore를 복원하지 않는다. 저장·삭제 경합과 이전 finally도 새 작업을 훼손하지 않는다.                             |
| R2  | US3 갱신 오류         | 해당 세션의 renew 401만 자격을 정리한다. 네트워크·timeout·5xx는 보존하고, 잘못된 응답·저장 실패를 구분한다. 이전 세션의 오류는 새 세션을 지우지 않는다.                        |
| R3  | US1 Google iOS 설정   | 명시적 iOS client ID와 URL scheme이 대응하며, 별도 plist가 없는 깨끗한 iOS 생성·빌드에서 초기화 경로를 확인한다. 실제 로그인 성공은 별도 검증한다.                             |
| R4  | US1 Google nonce      | 매 시도 새 nonce에 대응하는 새 ID token을 얻는 안전한 silent 경로의 가능성을 조사한다. 구현 방안 리뷰 전 인증 UX·SDK를 변경하지 않으며 조사만으로 결함 해결을 표시하지 않는다. |
| R5  | US3 브리지 복구       | 조회 불가를 SIGNED_OUT으로 확정하지 않는다. 준비 후 재조회하고, 오류 중 보호 화면을 차단하며, 오래된 query·mutation이 최신 인증 결과를 덮지 않는다.                            |
| R6  | 공통 API mock         | 관리자 공지 상세 URL이 detail1 계약에 맞는 200을 반환한다. 기존 회원 detail handler는 보존한다.                                                                                |

R1의 직렬화에는 `p-mutex@1.0.0`을 사용한다. Android는 조건부 교체·직렬 저장·지연 테스트의 참고이며 수정하지 않는다.
R4는 기존 nonce 재사용·캐시 token의 nonce 역추출·서버 검증 완화로 해결하지 않는다. YAPP refresh 기반 세션 복구는 유지한다.
웹 전체 계정 캐시·화면 수명·업무 API 401 재시도는 [#328](https://github.com/YAPP-admin/yapp-plus-frontend/issues/328)의 소유 범위다.
R1·R5의 웹 결과 반영은 그 공통 경로를 재사용하고 중복 coordinator를 만들지 않는다. 연계 전에는 웹 통합 해결을 선언하지 않는다.
실제 iPhone·Google/Apple 서버·TestFlight 검증은 미확인이다. 기존 배포본의 실패를 단정하지 않는다.
